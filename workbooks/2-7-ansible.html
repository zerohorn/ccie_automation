Target: IOSv/IOSvL2 + Cat8000V, three connection plugins (network_cli, netconf, httpapi)  ·  Weight: 2.7 is one of nine sub-items inside 2.0 IaC (30% of the exam)

PrereqBefore Task 1

1network_cli connection + facts (2.7.d — CLI leg)

Requirement

Build a cli_devices inventory group for IOSv/IOSvL2 using the network_cli connection plugin. With no cisco.ios collection installed, there's no IOS-specific cliconf — fall back to ansible_network_os: ansible.netcommon.default, the generic cliconf/terminal plugin. Then run a "facts" play using ansible.netcommon.cli_command to issue show version and pull the IOS version out of the raw text with a Jinja2 filter — this proves connectivity/auth before you configure anything.

Reference (verify locally — this is the part most likely to need adjustment)

  • Connection vars: ansible_connection: ansible.netcommon.network_cli, ansible_network_os: ansible.netcommon.default
  • ansible.netcommon.cli_command: runs one CLI command over an existing network_cli connection, returns raw text in stdout — no vendor-specific parsing, since that's what a platform collection (cisco.ios) would normally supply and isn't installed here
  • The generic cliconf handles basic >/# prompts and paging reasonably for IOS-like CLIs, but doesn't know IOS-specific quirks (e.g. enable secret handling, config-mode prompt variants) the way cisco.ios's cliconf would — if a command hangs or mis-detects the prompt, that's the likely cause

Docs

  • ansible.netcommon.network_cli
  • ansible.netcommon.cli_command

Verification

ansible-playbook -i inventory.yml facts.yml

Registered output should show a version string matching the device's actual IOS version, extracted from raw show version text.

Hint

Without cisco.ios, there's no fully-qualified vendor ansible_network_os to set — ansible.netcommon.default is the actual value, not a placeholder.

cli_command's output lands in stdout as one big string; pull the version line with a regex filter, e.g. | regex_search('Version ([0-9.]+)', '\1'), rather than expecting structured facts.

Put connection vars once under group_vars/cli_devices.yml rather than repeating per host.

Solution
# inventory.yml
all:
  children:
    cli_devices:
      hosts:
        iosv-1:
          ansible_host: 10.0.0.11
        iosvl2-1:
          ansible_host: 10.0.0.12
      vars:
        ansible_connection: ansible.netcommon.network_cli
        ansible_network_os: ansible.netcommon.default
        ansible_user: "{{ vault_ios_user }}"
        ansible_password: "{{ vault_ios_password }}"

# facts.yml
- name: Gather IOS facts via generic CLI command
  hosts: cli_devices
  gather_facts: false
  tasks:
    - name: Run show version
      ansible.netcommon.cli_command:
        command: show version
      register: show_version_out

    - name: Extract IOS version
      set_fact:
        ios_version: "{{ show_version_out.stdout | regex_search('Version ([0-9.()A-Za-z]+)', '\\1') | first }}"

    - name: Show version
      debug:
        var: ios_version

2NETCONF connection plugin (2.7.d — NETCONF leg)

Requirement

Add a netconf_devices group for Cat8000V using the generic netconf connection plugin, then use ansible.netcommon.netconf_get with a subtree filter to read its running config — the same NETCONF agent you already validated in Phase 0, just driven through Ansible instead of a raw NETCONF client.

Reference (verified against collection source)

  • Connection var: ansible_connection: ansible.netcommon.netconf (port defaults to 830; no platform-specific ansible_network_os needed — this module is platform-agnostic)
  • ansible.netcommon.netconf_get: takes source (running/candidate/startup) and a raw XML filter, returns the matching subtree

Docs

  • ansible.netcommon.netconf connection
  • ansible.netcommon.netconf_get

Verification

ansible-playbook -i inventory.yml netconf_facts.yml

Output should show raw XML for the requested container, not an error about the connection type.

Hint

The filter argument is a subtree filter matching a YANG container — same concept as the XPath filters from 2.5, just wrapped as a plain string here instead of built with a NETCONF client library.

Solution
# add to inventory.yml
    netconf_devices:
      hosts:
        cat8000v-1:
          ansible_host: 10.0.0.21
      vars:
        ansible_connection: ansible.netcommon.netconf
        ansible_user: "{{ vault_xe_user }}"
        ansible_password: "{{ vault_xe_password }}"

# netconf_facts.yml
- name: Read Cat8000V native config via NETCONF
  hosts: netconf_devices
  gather_facts: false
  tasks:
    - name: Get native config subtree
      ansible.netcommon.netconf_get:
        source: running
        filter: |
          
            
          
      register: netconf_out

    - name: Show result
      debug:
        var: netconf_out.output

3HTTPAPI/RESTCONF connection plugin (2.7.d — HTTPAPI leg)

Requirement

Add an httpapi_devices group for the same Cat8000V using the httpapi connection plugin backed by the generic restconf httpapi implementation, then use ansible.netcommon.restconf_get to fetch the same data as Task 2, this time as RESTCONF JSON.

Reference (verified against collection source)

  • Connection vars: ansible_connection: ansible.netcommon.httpapi, ansible_network_os: ansible.netcommon.restconf
  • ansible.netcommon.restconf_get: takes a path (RESTCONF resource URI relative to /restconf/data/) and a content type

Docs

  • ansible.netcommon.httpapi connection
  • ansible.netcommon.restconf httpapi plugin
  • ansible.netcommon.restconf_get

Verification

ansible-playbook -i inventory.yml restconf_facts.yml

Output should be JSON describing the same underlying config Task 2 returned as XML.

Hint

path is the same resource identifier you already used with curl against Cat8000V's RESTCONF endpoint in Phase 0 — just without the /restconf/data/ prefix, which the plugin adds for you.

Solution
# add to inventory.yml
    httpapi_devices:
      hosts:
        cat8000v-1:
          ansible_host: 10.0.0.21
      vars:
        ansible_connection: ansible.netcommon.httpapi
        ansible_network_os: ansible.netcommon.restconf
        ansible_httpapi_use_ssl: true
        ansible_httpapi_validate_certs: false
        ansible_user: "{{ vault_xe_user }}"
        ansible_password: "{{ vault_xe_password }}"

# restconf_facts.yml
- name: Read Cat8000V native config via RESTCONF
  hosts: httpapi_devices
  gather_facts: false
  tasks:
    - name: Get native config resource
      ansible.netcommon.restconf_get:
        path: /Cisco-IOS-XE-native:native
        content: config
      register: restconf_out

    - name: Show result
      debug:
        var: restconf_out.response

4Variables, templating & loop control (2.7.a, 2.7.c)

Requirement

Define a variable representing a set of VLANs (map or list, your choice), then provision them on cli_devices by pushing raw config lines with ansible.netcommon.cli_config — no cisco.ios.ios_vlans resource module is installed, so the config text itself has to be built. Drive the provisioning with Ansible's own loop keyword (not a single multi-line config block) and build at least one field with Jinja2 templating.

Reference (verified against collection source)

  • ansible.netcommon.cli_config: takes config (a string or list of config-mode lines), diffs it against running config, and pushes only what's missing — idempotent like a resource module, just without structured state tracking

Docs

  • ansible.netcommon.cli_config
  • Loops · Variables · Templating (Jinja2)

Verification

ansible-playbook -i inventory.yml vlans.yml

Follow with an ansible.netcommon.cli_command task running show vlan brief to confirm each VLAN landed with the expected id/name.

Hint

cli_config takes one block of config text per call — to exercise the loop keyword tested by 2.7.a, call it once per dict entry with loop: "{{ vlans | dict2items }}" rather than building one big multi-VLAN block up front.

Build the name field with a Jinja2 filter (e.g. {{ item.value.name | upper }}) to hit 2.7.c's templating angle in the same task.

Solution
# group_vars/cli_devices.yml
vlans:
  students: { id: 100, name: students }
  staff:    { id: 200, name: staff }
  mgmt:     { id: 999, name: mgmt }

# vlans.yml
- name: Provision VLANs via loop + templating
  hosts: cli_devices
  gather_facts: false
  tasks:
    - name: Create one VLAN per loop iteration
      ansible.netcommon.cli_config:
        config: |
          vlan {{ item.value.id }}
           name {{ item.value.name | upper }}_VLAN
      loop: "{{ vlans | dict2items }}"
      loop_control:
        label: "{{ item.key }}"

5Conditionals (2.7.b)

Requirement

Add a task that only runs on a subset of your inventory — e.g. apply a config change only when a host-level variable flags it as eligible, or only for hosts in a specific group. Run the play against the full inventory and confirm the task is skipped where the condition is false.

Reference (verified against docs)

  • when evaluates a Jinja2 expression without the surrounding {{ }}
  • Group membership is checkable via inventory_hostname in groups['cli_devices']

Docs

  • Conditionals

Verification

ansible-playbook -i inventory.yml vlans_conditional.yml -vv

Verbose output should show skipping: [host] for hosts that don't meet the condition, and normal execution for the rest.

Hint

A host var like lab_role: study set on only one host in cli_devices, checked with when: lab_role is defined and lab_role == "study", is the simplest way to produce a real skip/apply contrast without touching group membership logic.

Solution
- name: Conditionally set a banner
  hosts: cli_devices
  gather_facts: false
  tasks:
    - name: Apply banner only on flagged hosts
      ansible.netcommon.cli_config:
        config: |
          banner motd ^C
          Managed by Ansible - CCIE Automation lab
          ^C
      when: lab_role is defined and lab_role == "study"
