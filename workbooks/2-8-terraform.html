1Provider config + connectivity check (2.8.d Resource retrieval)

Requirement

Write a terraform block declaring the CiscoDevNet/iosxe provider, and a provider "iosxe" block pointing at your device over NETCONF. Then write a data source that reads the existing config for VLAN 1 — this proves connectivity/auth before you provision anything.

Reference (verified against the registry docs)

  • Provider source: CiscoDevNet/iosxe
  • Provider args include: host, username, password, protocol (netconf or restconf, defaults to netconf)
  • Data source iosxe_vlan requires: vlan_id (number)

Verification

terraform init
terraform plan

Should complete with no errors and resolve the data source. Note the returned VLAN 1 name.

Hint

Provider block needs three connection args plus one protocol arg — you already have all four from the prereqs checklist.

The data source block name is iosxe_vlan — same type name as the resource you'll provision in Task 3, just declared with data instead of resource.

Solution
terraform {
  required_version = ">= 1.13.0"
  required_providers {
    iosxe = {
      source  = "CiscoDevNet/iosxe"
      version = "~> 0.18"
    }
  }
}

provider "iosxe" {
  host     = var.device_host
  username = var.device_username
  password = var.device_password
  protocol = "netconf"
}

data "iosxe_vlan" "existing_default" {
  vlan_id = 1
}

2Variables (2.8.c)

Requirement

Externalize everything Task 1 hardcoded: device connection vars (mark credentials sensitive = true), plus a variable representing a set of VLANs you'll provision in Task 3 — you decide the type.

Verification

terraform validate

Should pass with no type errors. Sketch a terraform.tfvars entry for your VLAN variable before moving on.

Hint

If you go with map(object({...})), each object needs at least an id (number) and name (string) to match what iosxe_vlan expects.

Solution
variable "device_host" {
  type = string
}

variable "device_username" {
  type      = string
  sensitive = true
}

variable "device_password" {
  type      = string
  sensitive = true
}

variable "device_hostname" {
  type    = string
  default = "CAT8000V-01"
}

variable "domain_name" {
  type    = string
  default = "ccie-lab.local"
}

variable "access_vlans" {
  type = map(object({
    id   = number
    name = string
  }))
  default = {
    students = { id = 100, name = "STUDENTS" }
    staff    = { id = 200, name = "STAFF" }
    mgmt     = { id = 999, name = "MGMT" }
  }
}

3Provisioning + loop control (2.8.a, 2.8.e)

Requirement

Using for_each (not count — for_each keys resources by a stable identifier, so removing one VLAN from your map doesn't force-recreate the others; count reindexes by position and will), provision each VLAN as an iosxe_vlan resource. Separately, provision one iosxe_system resource setting hostname and domain name.

Reference (verified)

  • iosxe_vlan: vlan_id (number), name (string), shutdown (bool)
  • iosxe_system includes: hostname (string), ip_domain_name (string)

Verification

terraform plan

Resource count in the plan should equal (number of VLANs) + 1.

Hint

for_each = var.access_vlans — address the current item as each.value.id / each.value.name.

iosxe_system is a singleton — no for_each needed.

Solution
resource "iosxe_system" "device" {
  hostname       = var.device_hostname
  ip_domain_name = var.domain_name
}

resource "iosxe_vlan" "access" {
  for_each = var.access_vlans

  vlan_id  = each.value.id
  name     = each.value.name
  shutdown = false
}

output "provisioned_vlans" {
  value = { for k, v in iosxe_vlan.access : k => v.vlan_id }
}

4Resource graph (2.8.b)

Requirement

Run the graph command against your Task 3 config (no dependency between VLANs and system). Then add an explicit depends_on from your VLAN resources to the system resource, re-run, and compare.

terraform graph | dot -Tsvg > graph_before.svg
# add depends_on, save
terraform graph | dot -Tsvg > graph_after.svg

Needs Graphviz — apt install graphviz on the CWS if missing.

Reflection (your own notes, not for me)

  • What edge appeared in graph_after.svg that wasn't in graph_before.svg?
  • When would Terraform infer this ordering without an explicit depends_on?
Hint

depends_on takes a list even for one dependency: depends_on = [resource_type.resource_name]. On a for_each resource it goes inside the block once and applies to every instance.

Solution
resource "iosxe_vlan" "access" {
  for_each = var.access_vlans

  vlan_id  = each.value.id
  name     = each.value.name
  shutdown = false

  depends_on = [iosxe_system.device]
}

5Apply + state management (2.8.f)

Requirement

  1. terraform apply — confirm success.
  2. Verify on the device itself — show vlan brief. A clean apply doesn't guarantee the device did what you think.
  3. terraform state list and terraform state show on one VLAN instance.
  4. Drift exercise: manually rename one VLAN via device CLI (not Terraform). Run terraform plan — what shows? Then terraform apply -refresh-only — what's different?

A lab partner or your own mid-troubleshooting CLI edit is a far more likely drift source on a network device than on cloud infra. Knowing "detect drift" vs. "overwrite drift" under time pressure is a real exam skill.

Commands
terraform state list
terraform state show 'iosxe_vlan.access["staff"]'
terraform show
terraform apply -refresh-only

-refresh-only updates state to match reality without touching the device or your .tf files — "acknowledge drift," not "fix drift." A normal apply afterward pushes your .tf config back onto the device, overwriting the manual change.

6Stretch — interface assignment via schema discovery

Requirement

Assign one of your VLANs to an interface. Field names for iosxe_interface_switchport / iosxe_interface_vlan aren't given — this task is finding them yourself, which is closer to the real exam than memorized syntax.

terraform providers schema -json | jq '.provider_schemas["registry.terraform.io/ciscodevnet/iosxe"].resource_schemas.iosxe_interface_switchport'

No solution provided — this one's intentionally open-ended. Verify against the schema output itself.
