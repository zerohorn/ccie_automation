PrereqBefore Task 1

1Provider config + connectivity check (2.8.d Resource retrieval)

Requirement

Write a terraform block declaring the CiscoDevNet/aci provider, and a provider "aci" block pointing at your APIC over HTTPS. Then write a data source that reads the built-in common tenant — this proves connectivity/auth before you provision anything, without risking any object that matters.

Reference (verified against the CiscoDevNet/terraform-provider-aci docs)

  • Provider source: CiscoDevNet/aci
  • Provider args include: username, password, url, insecure (APIC's default cert is self-signed in most labs)
  • Data source aci_tenant requires: name (string)

Docs

  • Provider configuration (index.md)
  • aci_tenant data source

Verification

terraform init
terraform plan

Should complete with no errors and resolve the data source. Note the returned tenant DN (uni/tn-common).

Hint

Provider block needs three connection args plus one TLS-handling arg — you already have all four from the prereqs checklist.

The data source block name is aci_tenant — same type name as the resource you'll provision in Task 3, just declared with data instead of resource.

Solution
terraform {
  required_version = ">= 1.13.0"
  required_providers {
    aci = {
      source  = "CiscoDevNet/aci"
      version = "~> 2.17"
    }
  }
}

provider "aci" {
  username = var.apic_username
  password = var.apic_password
  url      = var.apic_url
  insecure = true
}

data "aci_tenant" "existing_common" {
  name = "common"
}

2Variables (2.8.c)

Requirement

Externalize everything Task 1 hardcoded: APIC connection vars (mark credentials sensitive = true), plus a variable representing a set of EPGs you'll provision in Task 3 — you decide the type.

Verification

terraform validate

Should pass with no type errors. Sketch a terraform.tfvars entry for your EPG variable before moving on.

Hint

If you go with map(object({...})), each object needs at least a name (string) to match what aci_application_epg expects; a description field is a natural second attribute.

Solution
variable "apic_url" {
  type = string
}

variable "apic_username" {
  type      = string
  sensitive = true
}

variable "apic_password" {
  type      = string
  sensitive = true
}

variable "lab_tenant_name" {
  type    = string
  default = "CCIE_LAB"
}

variable "app_profile_name" {
  type    = string
  default = "STUDY_AP"
}

variable "epgs" {
  type = map(object({
    name        = string
    description = string
  }))
  default = {
    web = { name = "WEB", description = "Web tier EPG" }
    app = { name = "APP", description = "App tier EPG" }
    db  = { name = "DB",  description = "DB tier EPG" }
  }
}

3Provisioning + loop control (2.8.a, 2.8.e)

Requirement

Using for_each (not count — for_each keys resources by a stable identifier, so removing one EPG from your map doesn't force-recreate the others; count reindexes by position and will), provision: one aci_tenant, one aci_application_profile underneath it, and one aci_application_epg per entry in your map.

Reference (verified)

  • aci_tenant: name (string), description (string, optional)
  • aci_application_profile: parent_dn (string — the tenant's DN), name (string)
  • aci_application_epg: parent_dn (string — the application profile's DN), name (string), description (string, optional)

Docs

  • aci_tenant, aci_application_profile, aci_application_epg
  • for_each meta-argument (Terraform language docs)

Verification

terraform plan

Resource count in the plan should equal 1 (tenant) + 1 (application profile) + (number of EPGs).

Hint

for_each = var.epgs — address the current item as each.value.name / each.value.description.

Every child object's parent_dn is just the parent resource's .id — ACI resources use their DN as the resource ID.

Solution
resource "aci_tenant" "lab" {
  name        = var.lab_tenant_name
  description = "CCIE Automation study tenant - safe to destroy/recreate"
}

resource "aci_application_profile" "study" {
  parent_dn = aci_tenant.lab.id
  name      = var.app_profile_name
}

resource "aci_application_epg" "tier" {
  for_each = var.epgs

  parent_dn   = aci_application_profile.study.id
  name        = each.value.name
  description = each.value.description
}

output "provisioned_epgs" {
  value = { for k, v in aci_application_epg.tier : k => v.name }
}

4Resource graph (2.8.b)

Requirement

Run the graph command against your Task 3 config.

terraform graph | dot -Tsvg > graph.svg

Needs Graphviz — apt install graphviz on the CWS if missing.

Docs

  • terraform graph, depends_on (Terraform language docs)

Find the edges tenant → application profile → each EPG. You never wrote a depends_on anywhere in Task 3 — they're there anyway.

Reflection (your own notes, not for me)

  • Why does Terraform already know the ordering, with zero explicit dependency declarations?
  • Now add a redundant depends_on = [aci_tenant.lab] to one EPG resource and regenerate the graph — does a new edge appear? Why or why not?
  • Contrast this with a scenario like iosxe_system hostname vs. an iosxe_vlan — two resources with no shared attribute to reference. When is explicit depends_on actually load-bearing, vs. redundant noise on top of a reference Terraform already tracks?
Hint

parent_dn = aci_tenant.lab.id is an attribute reference, not just a string you typed — Terraform's dependency graph is built from these references automatically. depends_on only matters when there's an ordering requirement without a data dependency to infer it from (e.g. a side-effect ordering, like configuring a device's hostname before its VLANs when neither resource reads the other's attributes).

5Apply + state management (2.8.f)

Requirement

  1. terraform apply — confirm success.
  2. Verify on APIC itself — GUI: Tenants → your tenant → Application Profiles → EPGs, or curl -k against /api/mo/uni/tn-<tenant>.json. A clean apply doesn't guarantee APIC did what you think.
  3. terraform state list and terraform state show on one EPG instance.
  4. Drift exercise: manually change one EPG's description via the APIC GUI (not Terraform). Run terraform plan — what shows? Then terraform apply -refresh-only — what's different?

A lab partner or your own mid-troubleshooting GUI edit is a realistic drift source on ACI. Knowing "detect drift" vs. "overwrite drift" under time pressure is a real exam skill.

Docs

  • terraform state, -refresh-only (Terraform CLI docs)
Commands
terraform state list
terraform state show 'aci_application_epg.tier["web"]'
terraform show
terraform apply -refresh-only

-refresh-only updates state to match reality without touching APIC or your .tf files — "acknowledge drift," not "fix drift." A normal apply afterward pushes your .tf config back onto APIC, overwriting the manual change.

6Stretch — contract binding via schema discovery

Requirement

Create an aci_contract under your tenant, then bind two of your EPGs to it — one as provider, one as consumer — so traffic between tiers is explicitly permitted. Field names for the EPG-to-contract relationship aren't given here — this task is finding them yourself, which is closer to the real exam than memorized syntax.

terraform providers schema -json | jq '.provider_schemas["registry.terraform.io/ciscodevnet/aci"].resource_schemas.aci_application_epg.block.attributes'

No solution provided — this one's intentionally open-ended. Verify against the schema output itself, and confirm on the APIC GUI (Application Profiles → EPG → Contracts) that both sides show up correctly.

Docs

  • aci_contract — deliberately not linking the EPG-to-contract relation doc here; find it via the schema command above
