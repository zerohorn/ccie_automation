Mental snapshot

  • Theme of the week: every tool has a read-only check, and each check compares exactly one pair of things. Name the pair and you know the blind spot.
  • Design (1.1) decides failure behaviour up front. NSO HA Raft needs at least three nodes. Kubernetes splits "restart it" (liveness) from "stop sending it traffic" (readiness).
  • Your clients live inside other people's limits. A 429 may carry Retry-After, and its value is either seconds or an HTTP-date.
  • An NSO action (2.9.c) is YANG action + tailf:actionpoint + a registered ncs.dp.Action. Its transaction is read-only. Service check-sync never touches the device; deep-check-sync does.
  • Python VM logs (2.9.d): self.log goes to logs/ncs-python-vm-<pkg>.log at level info by default. print() and compile errors go to the shared ncs-python-vm.log.
  • IOS XE scripts (3.1): PATCH never creates, POST fails with 409 on an existing resource, PUT does both. Encode keys with quote(v, safe=""). ncclient targets candidate unless you say otherwise.
  • Modify (1.2): compare first, change the smallest thing, compare again. Keep object identity with moved, and settle drift field by field: accept, reject or co-own.

L1 · What the four units are for

The four units form one loop. 1.1 decides how a solution behaves when something fails or slows down, before any code exists. 3.1 and 2.9 are the two ways this week's solutions touch a device. One is a direct Python client against Cat8000V. The other is NSO with the cisco-ios-cli NED, where you add actions to check what a service did, and logs to see what your own code did. 1.2 covers every day after go-live: a requirement changes, someone edits a box by hand, and you change the solution without breaking what already runs.

Each of those steps needs the difference between "the request was accepted" and "the network is in the intended state". A 204 from RESTCONF, an <ok/> from NETCONF, a green readiness probe and an in-sync service each prove one narrow thing. The review below lines those checks up so you can pick the right one under time pressure.

L3 · Exam detail: the traps worth one more pass

1.1 Design

  • Two-node HA. NSO 6.5 High Availability✅ says Raft needs at least three nodes. Three survives one failure, and five survives two. A two-node system cannot tell a dead peer from its own lost link. Rule-based HA may need occasional manual operator action.
  • Probes. If a startup probe is configured, liveness and readiness wait until it succeeds. The docs' sizing example is 30 × 10 s = 300 s (Configure Liveness, Readiness and Startup Probes✅).
  • Rate limits. Meraki allows 10 requests/s per organization, shared by every application, with 10 extra in the first second, plus 100 requests/s per source IP (Meraki Rate Limit✅). RFC 9110 §10.2.3✅ allows Retry-After as an HTTP-date or delay-seconds. A client that calls float() on it crashes on the date form.

2.9.c-d NSO actions and logs

  • Join key. The tailf:actionpoint name must equal the first argument of register_action(). action needs yang-version 1.1; YANG 1.0 used tailf:action. The trans passed to cb_action is read-only, because configuration belongs in services (Applications in NSO✅).
  • Timeout. /ncs-config/api/action-timeout defaults to PT240S (ncs.conf✅). When it fires, NSO kills the worker sockets for that action and calls cb_abort() without restarting the VMs.
  • Log levels. The default is info. python-vm logging level level-debug raises every VM. vm-levels <pkg> raises one and takes precedence. Files are named ncs-python-vm-<pkg>.log (NSO Python VM✅). The levels match Python's logging levels✅: DEBUG 10, INFO 20.

3.1 Python against IOS XE

  • Verbs. RFC 8040 §4.6✅: if the PATCH target does not exist, the server must not create it. §4.4.1: POST to an existing resource gives 409. §4.5: PUT gives 201 on create and 204 on replace.
  • Encoding. urllib.parse.quote✅ has safe='/', so quote("1/0/1") leaves the slashes. RFC 7951 §6.1✅ sends int64, uint64 and decimal64 as JSON strings.
  • Datastores. ncclient's edit_config defaults to target='candidate' (ncclient manager✅). The 17.5 NETCONF chapter✅ says that with the candidate datastore on, running is not writable through NETCONF. It also gives a 600 s confirmed-commit default and says RESTCONF has no confirmed commit.

1.2 Modify

  • Refactor. Moving to for_each needs a moved block naming the instance key, or Terraform plans destroy-and-create. Removing a moved block later is a breaking change (Refactor modules, v1.13.x✅).
  • Drift gate. -detailed-exitcode returns 0 (no changes), 1 (error) or 2 (changes). Refresh-only mode updates state and root outputs only (terraform plan, v1.13.x✅).
  • Out-of-band policy. Rules match by path and change type, longest path first. If no rule matches, NSO falls back to sync-from-device. On re-deploy, a value accepted with sync-from-device is overwritten by the service value; manage-by-service keeps it (Out-of-band Interoperation✅).

New requirements

  1. Default run is a gap report: print missing, changed (IP or description) and extra against sot.json. Exit 0 if there are no gaps, 2 if there are, 1 on any error, so CI can gate on it.
  2. --apply writes only the gaps and must rerun cleanly (no 409).
  3. Extras are reported but left alone. They are deleted only with --prune.
  4. Every call has a timeout. On 429 or 503, wait Retry-After when it is in seconds, otherwise use capped backoff. Give up after 5 tries. No bare except.
  5. After --apply, read back and exit with the post-change result.
  6. Three-line design note: where this runs (CI job, cron or container), and the two numbers you would alert on.

Solution 
#!/usr/bin/env python3
"""Reconcile Cat8000V loopbacks with sot.json over RESTCONF.
Exit codes: 0 = no gaps, 1 = error, 2 = gaps remain (CI gate)."""
import argparse, json, sys, time
from urllib.parse import quote
import requests

HDRS = {"Accept": "application/yang-data+json",
        "Content-Type": "application/yang-data+json"}

def call(s, method, url, tries=5, **kw):
    for attempt in range(tries):
        r = s.request(method, url, timeout=10, **kw)
        if r.status_code not in (429, 503):
            return r
        ra = r.headers.get("Retry-After", "")
        time.sleep(float(ra) if ra.isdigit() else min(2 ** attempt, 30))
    raise RuntimeError(f"rate limited {tries}x: {method} {url}")

def running(s, base):
    r = call(s, "GET", base + "/Loopback")
    if r.status_code == 404:                       # no Loopback entries
        return {}
    r.raise_for_status()
    rows = r.json().get("Cisco-IOS-XE-native:Loopback", [])
    return {str(lo["name"]): lo for lo in rows}

def ip_of(lo):
    return lo.get("ip", {}).get("address", {}).get("primary", {}).get("address")

def body(lo):
    return {"Cisco-IOS-XE-native:Loopback": [{
        "name": int(lo["id"]),
        "description": lo.get("description", ""),
        "ip": {"address": {"primary": {"address": lo["ip"],
                                       "mask": "255.255.255.255"}}}}]}

def gaps(sot, run):
    want = {str(lo["id"]): lo for lo in sot}
    missing = sorted(want.keys() - run.keys())
    extra = sorted(run.keys() - want.keys())
    changed = sorted(k for k in want.keys() & run.keys()
                     if ip_of(run[k]) != want[k]["ip"]
                     or run[k].get("description", "") != want[k].get("description", ""))
    return want, missing, changed, extra

def main():
    p = argparse.ArgumentParser()
    p.add_argument("base")                 # https://<host>/restconf/data/Cisco-IOS-XE-native:native/interface
    p.add_argument("sot")
    p.add_argument("--apply", action="store_true")
    p.add_argument("--prune", action="store_true")
    p.add_argument("--user", default="admin")
    p.add_argument("--password", default="admin")
    a = p.parse_args()
    sot = json.load(open(a.sot))["loopbacks"]
    with requests.Session() as s:
        s.auth, s.verify = (a.user, a.password), False
        s.headers.update(HDRS)
        try:
            want, missing, changed, extra = gaps(sot, running(s, a.base))
            print(json.dumps({"missing": missing, "changed": changed, "extra": extra}))
            if a.apply:
                for k in missing + changed:
                    url = f"{a.base}/Loopback={quote(k, safe='')}"
                    call(s, "PUT", url, json=body(want[k])).raise_for_status()
                for k in extra if a.prune else []:
                    call(s, "DELETE", f"{a.base}/Loopback={quote(k, safe='')}").raise_for_status()
                want, missing, changed, extra = gaps(sot, running(s, a.base))
                print(json.dumps({"after": {"missing": missing, "changed": changed, "extra": extra}}))
        except (requests.exceptions.RequestException, RuntimeError, KeyError) as e:
            print(f"ERROR {type(e).__name__}: {e}", file=sys.stderr)
            return 1
    return 2 if missing or changed or (a.prune and extra) else 0

if __name__ == "__main__":
    sys.exit(main())

Recall check: 12 questions

1.1 Design

1. A requirement reads "two NSO nodes, automatic failover, no split-brain". What do you push back with?

Answer

HA Raft needs at least three nodes. Three tolerates one failure, and five tolerates two. A two-node system can't tell whether it lost connectivity or its peer died. Rule-based HA works with two nodes but may need occasional manual operator action.

2. A colleague copies the readiness endpoint, which checks the database, into the livenessProbe. The DB blips for 20 s. What happens, and what is the right split?

Answer

Liveness failures make the kubelet restart the container, so every replica restarts at once. Readiness failures only remove the Pod's IP from the matching Services' EndpointSlices. Keep liveness local, put the dependency check in readiness, and add a startupProbe sized to the worst-case boot (the docs use 30 × 10 s = 300 s).

3. A 429 arrives with Retry-After: Fri, 27 Nov 2026 12:00:05 GMT, and the helper does float(value). What breaks, which RFC allows this form, and what are Meraki's two budgets?

Answer

float() raises ValueError. RFC 9110 §10.2.3 allows an HTTP-date or delay-seconds, and RFC 6585 §4 defines 429. Meraki: 10 requests/s per organization, shared across applications (plus 10 extra in the first second), and 100 requests/s per source IP.

2.9.c-d NSO actions and logs

4. The YANG says tailf:actionpoint loop-check; and setup() calls register_action('loop-check-action', Check). What is wrong? What must the module declare to use action, and can cb_action write config through trans?

Answer

The strings differ, so no callback is registered for loop-check. The first argument of register_action() must equal the actionpoint name. The module needs yang-version 1.1; YANG 1.0 used tailf:action. trans is read-only, because configuration changes belong in services.

5. Someone removed a service-created IP directly on r1. loopback L10 check-sync says in-sync. Why, which action shows the problem, and what is the limit of devices device r1 check-sync?

Answer

Service check-sync compares the service code's output with CDB and never contacts the device. deep-check-sync fetches from the device and catches it. Device check-sync compares a config signature, and the NED may answer unsupported; then use compare-config.

6. self.log.debug() and print() output are both missing from logs/ncs-python-vm-loopback.log. Explain both. Then: what is the action timeout default, and what happens when it fires?

Answer

The default level is info, so debug lines are dropped until vm-levels loopback (or the global level) is set to level-debug. print() goes to stdout, which lands in the shared ncs-python-vm.log. /ncs-config/api/action-timeout is PT240S. NSO kills that action's worker sockets and calls cb_abort() without restarting the VMs.

3.1 Python against IOS XE

7. A script POSTs Loopback11 and gets 409 on the rerun. A colleague switches to PATCH on the list-instance URI, and the first run on a fresh router fails. Explain both, and name the verb that is safe on every run.

Answer

POST is create, and an existing resource gives 409 Conflict (RFC 8040 §4.4.1). With PATCH, if the target does not exist the server must not create it (§4.6). PUT on the list-instance URI creates with 201 or replaces with 204 (§4.5).

8. Two bugs: quote("1/0/1") in a URI, and "in-octets": "123456" treated as a number. Explain each and fix it.

Answer

quote() defaults to safe='/', so the slashes stay and become extra path segments; use quote(v, safe="") to get 1%2F0%2F1. RFC 7951 §6.1 encodes int64, uint64 and decimal64 as JSON strings, so convert with int() before comparing or doing maths.

9. m.edit_config(config=cfg) fails on a Cat8000V that has only netconf-yang. After you enable the candidate datastore, target="running" fails instead. Why both, and what does the script do?

Answer

ncclient's edit_config defaults to target='candidate', which the device does not have. With the candidate feature on, the 17.5 guide says running is not writable through NETCONF. Pick the target from ":candidate" in m.server_capabilities, and commit() after candidate edits. If the requirement says "roll back if the box stops answering", use a confirmed commit (default 600 s); RESTCONF has none.

1.2 Modify

10. You move a resource holding two live tenants from count to for_each. What does the plan propose with no extra blocks, what fixes it, and can you delete the fix later?

Answer

Destroy the indexed instances and create keyed ones (on 2026-11-26, offline on 1.13.3: 3 to add, 2 to destroy). Add one moved { from = r[0] to = r["key"] } per index, and Terraform treats each object as if it had been created at the new key. Removing a moved block later is a breaking change for anyone who has not applied yet.

11. After an incident you run terraform apply -refresh-only. What changed, what didn't, and how does CI catch what remains?

Answer

State and root outputs now match the remote objects. Infrastructure and config are unchanged, so the next normal plan proposes reverting the drift ⚠ derived. To accept it, put the value in the SoT. plan -detailed-exitcode returns 2 when changes are pending, which is the CI gate.

12. Operators may edit loopback descriptions and keep them through re-deploy, but IP changes must be reverted. Which NSO 6.5 policy actions do you use, and what happens to a change no rule matches?

Answer

Description: at-value-set manage-by-service. sync-from-device would accept the edit, but a re-deploy would overwrite it with the service value. IP address: sync-to-device for delete and value-set. When no rule matches, NSO falls back to sync-from-device.
