Mental snapshot

  • Dial-out = the router opens the connection to your collector. A configured subscription lives in running-config and survives reload and switchover.
  • IOS XE update-policy periodic counts centiseconds. 6000 is 60 s, not 6 s. Minimum 100 (1 s), no default.
  • On-change on IOS XE: dampening must be 0, row granularity, not hierarchical, single-object XPath. It is a tool for rarely changing state, not a way to avoid thinking about cadence.
  • Receivers cannot be edited. Change one by delete and recreate. Only the first valid receiver is used.
  • "Optimizing frequency" means matching cadence to how fast data changes and what the device and collector can carry: narrow the XPath, pick the right update trigger, stagger paths, limit collectors.
  • Subscription Valid says nothing about the receiver. Check receiver state separately (connecting, connected).
  • NX-OS counts milliseconds in sample-interval; 0 means event-based. Same word "interval", different unit.

Where this fits

Fundamentals to exam depth

L1 Concept. A telemetry subscription is a standing request: send me this slice of the YANG tree, in this encoding, on this trigger. The trigger is either a clock (periodic) or a change (on-change). In dial-out the subscription is device configuration, so the device is the client. It dials the receiver, and if the link drops it keeps retrying. Dial-in is the opposite: your tool opens a session and the subscription dies with it. Dial-out wins behind firewalls and for always-on streams, because only an outbound rule is needed and nothing is lost on a collector restart except the data during the gap.
L2 Mechanics. IOS XE implements RFC 8639/8641 style subscriptions. A configured subscription has an ID, a stream (yang-push), an XPath filter, an encoding, an update policy, an optional source-vrf / source-address, and one or more receivers. Per the 17.5 guide, for gRPC dial-out only yang-push and key-value GPB (encode-kvgpb) are supported (the Cisco support article for YANG Suite states these constraints).

Two state machines matter, and people conflate them. The subscription is Valid, Invalid or Concluded. The receiver is connecting, active, suspended or disconnected in the RFC; the Cisco output prints rcvr-state-connecting and rcvr-state-connected.

Receiver state machine

L3 Exam detail. What you must get right on the CLI, and where the 17.5 guide is specific:
  • Period units. Centiseconds. The guide's own example update-policy periodic 6000 is 60 s. Min 100. No default, so it must be set.
  • On-change. Dampening period must be 0. First update is the full data set (initial sync), then changed rows only. Not hierarchical: a parent XPath will not fire for a child change. Which models support it is read from the device (show platform software ndbman {switch-number|active|standby} models), not from the YANG.
  • Receivers. No modify. Delete the subscription or receiver and recreate. Rewriting a receiver with identical settings forces a reconnect. Multiple receivers allowed, only the first valid one carries data; if it is deleted another connects.
  • Persistence. Configured subscriptions persist across reload only if saved. After a stateful switchover dial-out reconnects on its own; dial-in must be recreated.
  • Restrictions. Subtree filters not supported (the subscription is marked invalid). Union operator over NETCONF only, not gRPC. No QoS for yang-push. 100 subscriptions supported per the guide (platform maxima vary).
  • Deleting. CLI: no telemetry ietf subscription N. The guide says configured subscriptions cannot be deleted by RPC, yet shows a NETCONF delete example. Treat the CLI as the reliable path.

Optimizing frequency: the levers

LeverWhat it doesSource / limit
Narrower XPathFewer objects per update. Capacity depends on how much subtree is subscribed.RFC 8641 s3.6, s3.11.2. IOS XE: no subtree filters; exact keys in on-change.
Longer periodFewer pushes for slow-moving data.IOS XE min 100 cs. The 17.5 guide gives Catalyst 9800 minimum recommended intervals that grow with scale and collector count (e.g. 180 s one collector, 360 s two for one neighbor scenario).
On-changeSilence until something changes.Dampening 0 only; full initial sync on start; models vary.
Fewer collectorsLess duplicate load.IOS XE uses only the first valid receiver per subscription.
gNMI suppress_redundant + heartbeatSAMPLE sends only changed leaves, plus one update per heartbeat.gNMI spec 3.5.1.5.2. Dial-in side; not an IOS XE dial-out knob.
Anchor-timeAligns periodic updates to multiples of the period from a reference time.RFC 8641 only. 17.5 guide does not mention it: do not assume it exists in CLI.

When a publisher cannot carry the load, RFC 8641 expects it to refuse, return hints (acceptable periods, dampening), or suspend (subscription-suspended with reasons such as insufficient-resources and unsupportable-volume). Oversized pushes raise update-too-big; an oversized initial sync raises sync-too-big. In an exam task the practical read is: if data stops or gaps appear after you tighten the period, suspect volume before suspecting the collector.

Anatomy

Configured gRPC dial-out, periodic, as printed in the 17.5 guide:

telemetry ietf subscription 101
  encoding encode-kvgpb
  filter xpath /memory-ios-xe-oper:memory-statistics/memory-statistic
  stream yang-push
  update-policy periodic 6000
  source-vrf Mgmt-intf
  receiver ip address 10.28.35.45 57555 protocol grpc-tcp
  • periodic 6000: 60 s. source-vrf picks the egress VRF. If the collector is not reachable through it, the receiver stays in connecting.
  • Receiver syntax: receiver ip address <ip> <port> protocol <proto> [profile <name>].
  • TLS variant in the guide: ... protocol grpc_tls profile secure_profile. Note the underscore; other text uses the hyphen form. ⚠ unverified — test in lab (it matters again on 3.5.e).

Same subscription over RESTCONF, per the guide: POST to /restconf/data/Cisco-IOS-XE-mdt-cfg:mdt-config-data with "subscription-id": "102" and "period": "6000". The NETCONF form edits the same Cisco-IOS-XE-mdt-cfg module; the on-change form sets the no-sync-on-start leaf to false and dampening to 0. ⚠ unverified — test in lab: exact element nesting, namespace and the leaf spelling (no-synch-on-start in the guide's XML, no-sync-on-start in the support article text).

Verification output, guide style (show telemetry ietf subscription all):

  ID               Type        State       Filter type
  100              Configured  Valid       xpath
  2147483651       Dynamic     Valid       xpath

Receiver link state is a separate view: show telemetry internal connection lists peer, port, VRF, source address, transport and state (Active or Connecting). A device that pushes this via Ansible would use netconf_config (✅): target auto/candidate/running, commit default true, lock default always.

Micro-drill (~10 min)

Target: Cat8000V (IOS XE 17.16 in lab). Collector: Telegraf in the TIG stack on HORNLAB01.

Requirement.

  1. Create configured subscription 301: yang-push, kvGPB, XPath /memory-ios-xe-oper:memory-statistics/memory-statistic, periodic every 30 seconds, receiver on the collector over grpc-tcp, egress via the correct VRF.
  2. Prove the subscription and the receiver are both healthy.
  3. Cut the load: raise the cadence to once per 5 minutes without losing the receiver.
  4. Move the receiver to a different port with no stale state left behind.

Reference fields: subscription ID, stream, encoding, filter xpath, update-policy, source-vrf, receiver ip/port/protocol. Verification: show telemetry ietf subscription all detail, show telemetry internal connection, data visible in Grafana or InfluxDB.

Hint

30 s is not 30. Receiver edits are delete and recreate. Whether period can be edited on a live subscription is ⚠ unverified — test in lab; if it is refused, delete and recreate the whole subscription.

Solution 
telemetry ietf subscription 301
  encoding encode-kvgpb
  filter xpath /memory-ios-xe-oper:memory-statistics/memory-statistic
  stream yang-push
  update-policy periodic 3000
  source-vrf <vrf that reaches collector>
  receiver ip address <collector-ip> <port> protocol grpc-tcp
! 5 minutes = 30000 centiseconds
! change port: no receiver ip address ... then add the new line
! (or no telemetry ietf subscription 301 and rebuild)

Verify: Type Configured, State Valid; connection state Active; points arrive every 30 s, then every 300 s. Note: the exact "no receiver" form is ⚠ unverified — test in lab.

Recall check

Today

  1. The guide's example says update-policy periodic 6000. What is the interval, and what is the smallest legal value?
    Answer60 seconds. Unit is centiseconds; minimum 100 (1 s).
  2. Two receivers are configured on one subscription. The first is unreachable. What does the second one receive?
    AnswerPer the 17.5 guide only the first valid receiver is used, and others are not tried while it is connected or connecting. Do not expect fan-out; create a second subscription for a second collector.
  3. Name three ways to lower telemetry load while keeping the signal, with one IOS XE restriction attached to each.
    AnswerNarrower XPath (no subtree filters, exact keys for on-change); on-change for slow-changing state (dampening 0, row level, model-dependent); longer period on slow data (min 100 cs, and platform scale guidance). Also: fewer collectors.
  4. An N9Kv has sample-interval 10000. How often does it send, and what does 0 mean?
    AnswerEvery 10 seconds (milliseconds). 0 makes the subscription event-based. Minimum at depth 0 is 5 s.
