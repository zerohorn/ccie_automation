Terraform: resource retrieval, provisioning, and state management

Date: Wed 2026-11-11 Blueprint: 2.8.d Resource retrieval · 2.8.e Resource provision · 2.8.f State management of provisioned resources Parent: 2.8 [Build] Use Terraform to statefully manage infrastructure Domain: 2 (weight ⚠ unverified) Tier: 3 (proficiency check) Read time: ~18 min Unit: 27 of 49

Version pins: Terraform 1.13 (workstation lists 1.13.3); provider ciscodevnet/aci v2.17.0 is the only provider on the Candidate Workstation. Target: DevNet Sandbox APIC. Some HashiCorp pages fetched today are the v1.17.x "latest" docs; anything not confirmed on a 1.13 page is labelled.

Mental snapshot

  • Three verbs, one file. Retrieval = data blocks (read-only). Provision = resource blocks driven by plan/apply. State management = editing the mapping between addresses and real objects without touching the objects.
  • State is the join table between a config address like aci_tenant.prod and a real APIC DN like uni/tn-prod. Lose the row and Terraform thinks the object doesn't exist.
  • Data sources are read at plan time unless an argument is unknown or depends_on is set; then the read waits for apply.
  • Prefer config blocks to CLI surgery. import, moved and removed blocks go through plan review; terraform import, state mv, state rm change state immediately.
  • For ACI the import ID is the DN, e.g. uni/tn-X/ctx-Y.
  • Drift handling: normal plan reverts drift; -refresh-only accepts it into state.
  • state rm forgets, it does not delete. The next plan tries to create the object again.

Where this fits

L1 — Concept

Two kinds of block, one engine

Terraform only knows two object kinds. A managed resource (resource) is something Terraform owns: it creates, updates, and destroys it. A data resource (data) is something Terraform only reads. The data sources page says data sources fetch provider data "but do not create or modify resources", and that only read operations happen on them. That is all of 2.8.d. 2.8.e is the normal create/update/delete lifecycle of managed resources through plan and apply.

Why state exists at all

APIC objects have DNs; your config has addresses. Something must record "address aci_tenant.prod is the object at uni/tn-prod". The state purpose page lists four jobs for state: mapping config to real objects, keeping metadata such as the last dependency set (so deletes happen in the right order after a block is removed from config), caching attributes for performance, and giving a team one shared view. Tags weren't enough for this because not every resource supports tags. In network terms state is closer to an adjacency table than a config backup. It's derived, but the control plane can't run without it.

State management = editing the mapping

2.8.f is about changing those rows without touching the real objects. There are four operations:

  • Adopt an object created outside Terraform (import).
  • Re-address an object you renamed or moved in code (moved / state mv).
  • Forget an object without deleting it (removed with destroy = false / state rm).
  • Accept drift into state (refresh-only).

Every one has a CLI form and, except refresh-only, a config-block form. HashiCorp now points people toward the block forms.

L2 — Mechanics

When a data source is read

Per the v1.12.x data sources page:

  • If every argument is a known value, the read happens in the refresh phase before planning.
  • If an argument depends on a managed-resource attribute that changes in this plan, the read is deferred to apply.
  • A depends_on on the data block always defers it until the dependency finishes.

The practical consequence: a data source that depends on something "in flight" returns known after apply. Everything downstream of it then shows as unknown in the plan, which can make plans noisy or force replacements. This is the data-source version of the depends_on cost you saw on 11-02.

Provision flow and what plan actually compares

By default every plan and apply first syncs all resources in state against the real objects (the state purpose page). Plan then diffs config against that refreshed state. The terraform plan reference (v1.13.x) gives three mutually exclusive modes:

  • Normal: make reality match config.
  • Destroy (-destroy): plan to remove everything.
  • Refresh-only (-refresh-only): only update state and root outputs to match out-of-band changes.

Useful options:

  • -refresh=false skips the sync. It's faster but blind to drift, and you can't combine it with refresh-only.
  • -replace=ADDRESS forces a destroy/create of one instance. It replaces the old taint workflow.
  • -target is documented as "exceptional circumstances only".
  • -out saves a plan, which may contain secrets in cleartext.
  • -detailed-exitcode returns 0 for no changes, 1 for an error, and 2 for changes present. That's the hook for a CI drift check.

Steps 1 and 8: the backends page says the default local backend keeps state in a local JSON file and locks with system APIs. Step 5's parallelism of 10 is from the graph page verified on 11-02 and the import CLI page today.

The refactor page calls state mv a legacy command. It recommends the blocks for new migrations because they go through normal plan review and leave a record in the code. removed and import blocks need Terraform 1.7 or newer, which the 1.13 pin covers. The state rm page (v1.13.x) suggests removed blocks for the same reason. Every state-modifying subcommand writes a backup that you can't disable. Read-only ones like list don't.

L3 — Exam detail

ACI specifics with provider v2.17.0

  • Import ID is the DN. BRKDCN-2607 shows an import block with id = "uni/tn-…/ctx-…" targeting aci_vrf. Its CLI form takes the "full path to Dn". The same deck notes that CLI import doesn't generate configuration and runs once per object.
  • Generating config. Write only the import block and run terraform plan -generate-config-out=FILE.tf. Then review the file, because generated HCL often carries every attribute, including defaults.
  • aci_rest_managed is the escape hatch when no dedicated resource exists. It takes dn, class_name and a content map. The deck says it can reconcile state. The releases page shows import fixes in 2.14.0 and 2.15.0 (DNs with semicolons and brackets) and child-object import in 2.13.0 and 2.18.0. The 2.18.0 JSON-string child import is newer than the lab's 2.17.0, so don't rely on it.
  • 2.17.0 moved aci_vrf (plus aci_any and aci_taboo_contract) to the Plugin Framework. Attribute names on those resources may differ from older examples, so read the schema rather than memorising blog HCL.
  • import block identity: the v1.17 import block page offers identity as an alternative to id. Whether 1.13 plus aci 2.17.0 support it is ⚠ unverified, so use id with the DN.

Task shapes consistent with "statefully manage"

  • "Bring the existing tenant under Terraform without disruption." Import, match the config until the plan shows no changes, then apply.
  • "Rename resource labels / convert to for_each without destroying anything." Use moved blocks per instance key.
  • "Stop managing object X but leave it in the fabric." Use removed with destroy = false.
  • "Someone changed a description in the GUI; keep the GUI value." Either refresh-only and update the config, or just update the config so plan shows no changes.
  • "Use the DN of an object you don't own." Use a data block, or just a literal DN.

Traps

  • Import doesn't make config correct. The import block page requires to to match an existing resource block. If your block's arguments differ from the APIC object, the same apply that imports will also update it, because import plus diff happen together. Read the plan line by line.
  • The import ID must be known at plan. The block page says so explicitly, so don't feed it from a resource attribute that's created in the same run.
  • state rm followed by plan wants to create the object again. On APIC a POST to an existing DN often just merges, so you may see "success" and silently re-own the object (⚠ APIC behaviour unverified — test in lab).
  • Moved without the block: the state mv page reminds you that a renamed address defaults to delete plus create. On ACI, deleting a tenant cascades to every child object.
  • Quoting instance keys. On Linux, wrap 'aci_tenant.t["prod"]' in single quotes (state mv/rm pages).
  • State contains secrets, as does a -out plan file. Don't commit terraform.tfstate to the Git repo your CI uses.

Anatomy

Terraform 1.13 syntax per the block references; ACI argument names other than aci_rest_managed's are ⚠ unverified — check with the schema command in Speed notes.

# --- 2.8.d retrieval: read, don't own ---
data "aci_tenant" "common" {        # ⚠ argument name "name" unverified for v2.17.0
  name = "common"
}
# reference: data.aci_tenant.common.id   (id = DN on this provider ⚠)

# --- 2.8.e provision: own it ---
resource "aci_rest_managed" "tn" {  # dn / class_name / content per BRKDCN-2607
  dn         = "uni/tn-REST"
  class_name = "fvTenant"
  content = {
    name  = "REST"
    descr = "managed by terraform"
  }
}

# --- 2.8.f state: adopt, re-address, forget ---
import {
  to = aci_rest_managed.legacy       # must match an existing resource block
  id = "uni/tn-LEGACY"               # DN; must be known at plan time
}

moved {
  from = aci_rest_managed.tn         # old label
  to   = aci_rest_managed.rest       # new label: no destroy/create
}

removed {
  from = aci_rest_managed.old
  lifecycle {
    destroy = false                  # forget, leave object on APIC
  }
}
# CLI equivalents (immediate, no plan review)
terraform import aci_rest_managed.legacy uni/tn-LEGACY
terraform state mv aci_rest_managed.tn aci_rest_managed.rest
terraform state rm -dry-run 'aci_rest_managed.t["old"]'   # list matches first
terraform plan -refresh-only                              # accept drift
terraform plan -detailed-exitcode                         # 0 none · 1 error · 2 changes

Micro-drill (~10 min)

Target: DevNet Sandbox APIC · Terraform 1.13 · ciscodevnet/aci v2.17.0 · local backend.

Requirement:

  1. In the APIC GUI, create tenant TF-ADOPT with description gui. Terraform must not create it.
  2. Bring it under Terraform as aci_rest_managed.adopt using a config block, not the CLI. The final plan must show no changes, with the description still gui.
  3. Rename the address to aci_rest_managed.tenant with no destroy.
  4. Stop managing it while leaving it on the APIC.

Reference fields: dn, class_name (fvTenant), content.name, content.descr; DN form uni/tn-NAME.

Verify:

  • terraform state list after each step.
  • terraform plan -detailed-exitcode returns 0 after step 2 and step 3.
  • After step 4, the tenant still appears in the GUI and state list is empty.
Hint

Write the import block first and let -generate-config-out produce the resource. Then trim it down to the four fields. For steps 3 and 4, delete the old block in the same edit you add moved or removed.

Solution 
# step 2 (main.tf)
import {
  to = aci_rest_managed.adopt
  id = "uni/tn-TF-ADOPT"
}
resource "aci_rest_managed" "adopt" {
  dn         = "uni/tn-TF-ADOPT"
  class_name = "fvTenant"
  content = { name = "TF-ADOPT", descr = "gui" }
}
# terraform plan   -> 1 to import, 0 to change ; terraform apply

# step 3: rename label in the resource block to "tenant", add:
moved {
  from = aci_rest_managed.adopt
  to   = aci_rest_managed.tenant
}
# terraform plan -> move, no destroy ; apply ; plan -detailed-exitcode = 0

# step 4: delete the resource block (and moved/import blocks), add:
removed {
  from = aci_rest_managed.tenant
  lifecycle { destroy = false }
}
# terraform plan -> forget, no destroy ; apply

Recall check

  1. When is a data source read at plan time, and what two things push it to apply?
    Answer

    At plan (refresh phase) when all arguments are known. It's deferred when an argument depends on a managed-resource value that changes in this plan, or when the data block has depends_on.

  2. You run terraform state rm aci_tenant.prod. What happens to the tenant, and what does the next plan propose?
    Answer

    The tenant stays on APIC, unmanaged. The next plan proposes creating it again, which may fail or conflict. The block alternative is removed { … destroy = false }, which is reviewed in plan.

  3. Give the import block's two required pieces for an ACI VRF, the ID format, and the constraint on the ID.
    Answer

    to (an address matching an existing resource block) and id as the full DN, e.g. uni/tn-T/ctx-V. The ID must be known during plan. The alternative is identity on newer docs (⚠ for 1.13 / aci 2.17).

  4. What are the three plan modes, what are the -detailed-exitcode values, and which mode accepts GUI drift?
    Answer

    Normal, destroy, refresh-only. Exit codes: 0 no changes, 1 error, 2 changes. Refresh-only updates state and outputs to match out-of-band changes.

  5. (from 2026-11-03) What alias does device.connect() give with no arguments in pyATS, and how do you open a second session on the vty path as vty_1?
    Answer

    default; device.connect(alias='vty_1', via='vty').

  6. (from 2026-11-05) A RESTCONF PATCH succeeds but your Python CLI raises JSONDecodeError. Why, and what order do you check?
    Answer

    RESTCONF returns 204 with no body. Check the status code first, then whether a body is present, then decode.
