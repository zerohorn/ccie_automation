Mental snapshot

  • Two vantage points. AppDynamics sits inside the application (agents on tiers and nodes). ThousandEyes sits outside it (synthetic probes from agents, with path visibility).
  • The task is localization. User, network path, web tier, app tier, backend. Name the failing segment and hand it off with evidence.
  • AppDynamics unit of work is the business transaction. Each one is classed normal, slow, very slow, stall or error against thresholds; flow-map colors depend on baselines.
  • ThousandEyes HTTP response time is time to first byte, starting before DNS. Split it into DNS, connect, SSL, wait, receive to find the phase that grew.
  • Path Visualization gives the verdict on loss. Red ring mid-path means the network between agent and target. Red ring on the destination node means the target itself.
  • The products talk to each other. Browser RUM can ingest ThousandEyes loss, latency and jitter; ThousandEyes can take AppDynamics services and recommend tests.

Where this fits

Fundamentals to exam depth

L1: concept

"Slow" has three possible owners: the network, the application, or what the application calls. You have spent 20 years separating the first from the rest with ping, traceroute and packet captures. These two products do that at the application layer and keep history.

AppDynamics instruments the running application. You see tiers, nodes, message queues and databases on a flow map, with the business transactions that cross them (Flow Map Overview ✅). A business transaction is the request type being measured end to end. It answers "which request, in which tier, calling which backend, got slow".

ThousandEyes does not look inside the application. Agents run tests from chosen locations: Tests ✅ lists agent-to-server (network), HTTP server and page load and transaction (web), BGP (routing) and DNS. It answers "does the path to the app look healthy from where the user is, and which phase of the request got slow".

L2: mechanics

AppDynamics classification. Thresholds are boundaries of normal performance, defaults apply to every business transaction, and each one lands in normal, slow, very slow, stall or error (Transaction Thresholds ✅). Baselines are computed from hourly data, with daily, weekly or monthly seasonality. A deviation is counted in standard deviations; the page's example warns at 2 and goes critical at 4 (Dynamic Baselines ✅). Baselines are not instant: hours with no seasonality, days for daily, weeks for weekly, and by default no baseline for a metric under 20 calls per minute.

AppDynamics workflow. The docs give a six-step slow-response procedure (Slow Response Times ✅). Start at Troubleshoot > Slow Response Times and the Slow Transactions tab (Step 1 ✅). Snapshots present means drill in for root cause; none means go check slow backends.

Fetches of steps 2, 3 and 5 failed twice this run; only their titles (from the parent page) are used. Read them yourself.

Flow map reading. Solid lines are synchronous calls, dashed lines asynchronous. The numbers on a line are calls per minute and average round-trip time. Line color (green, yellow, red) compares to baseline, but the default view does not compare against a baseline and new installs need time to build one. That is why a flow map can look healthy while users complain.

ThousandEyes phases. HTTP response time starts before DNS and ends at the first byte. Wait time is request-sent to first byte. Receive is first to last byte, and availability is 100% for a 2xx or 3xx and 0% otherwise (ThousandEyes Metrics: What Do Your Results Mean? ✅). The test breaks failures down by phase: DNS, connect, SSL, send, receive, validation (HTTP Server Tests ✅).

Path Visualization. The page explains the verdict on loss: a red ring mid-path points to the network between agent and target, a red ring on the destination points to the target (an application, firewall or load balancer). Set loss and delay thresholds with Highlight so suspect hops stand out (Path Visualization ✅).

Integration 1: ThousandEyes into AppDynamics. Browser RUM ingests packet loss, latency and jitter from agent-to-server, HTTP server, page load and transaction tests. Requirements: SaaS Controller 23.4.0 or later, a browser application, an active Network and App Synthetics subscription, and a ThousandEyes OAuth bearer token. You paste the token in AppDynamics and click Sync with ThousandEyes; data shows in the Network Insights widget on the Browser App Dashboard. Ingestion is capped at 9 million network metrics per RUM Peak Edition unit (ThousandEyes Network Metrics in Browser RUM ✅). The stated use is separating network cause from app cause per domain, location and time window (Use Cases ✅).

Integration 2: AppDynamics into ThousandEyes. In ThousandEyes: Manage > Integrations > New integration > AppDynamics, Basic or OAuth client credentials, tick "Activate test recommendations", Test, Save. You then pick applications and dependent services, and ThousandEyes proposes tests. Prerequisites include an AppDynamics End User Monitoring license and cSaaS build 23.4.x. The page does not say whether this is GA or supported (AppDynamics for Test Recommendations ✅).

Task shapes consistent with the blueprint verb "diagnose". Given dashboards, metrics or a flow map, identify the failing segment; choose the next screen or test; explain why two views disagree (flow map green, users unhappy: baseline not built); or wire the integration between the two products. These are inferred, not known exam content.

Speed notes

  • No CLI discovery exists for either product. Speed is navigation memory: Troubleshoot > Slow Response Times (AppD); Test Settings, Views, Path Visualization (TE).
  • Memorize the order: ThousandEyes first (is the path clean, which phase), then AppDynamics (which BT, snapshot, backend).
  • Know the three numbers: 20 calls/min (no baseline), 2 and 4 SD (example thresholds), 9 million metrics per unit (RUM cap).
  • Whether product docs are reachable offline on the Candidate Workstation is ⚠ unverified; do not count on it.

Micro-drill (~10 min, paper only)

Target device: none. Neither product is in your CML lab (Cat8000V, IOSv, N9Kv). All numbers below are invented for the drill.

Requirement: Frankfurt users report checkout is slow since 14:00. Name the failing segment and the team you hand off to, citing three data points.

SourceObservation
TE HTTP server test, Frankfurt Cloud Agentavailability 100%; response time 3.1 s; DNS 20 ms; connect 35 ms; SSL 60 ms; wait 2.8 s; receive 40 ms
TE network layer, same agentloss 0%; latency 22 ms; jitter 2 ms
AppDynamicsCheckout BT 4 SD over baseline; other BTs green; all nodes in OrderSvc tier slow; slow snapshots spend most time in an exit call to one database backend

Reference fields: TE: response time, wait, connect, loss, latency, jitter. AppD: BT health, deviation from baseline, tier nodes, backend call.

Verify: your answer must explain why it is not the network and why it is not one node.

HintCompare wait time to the rest of response time, then look at which AppD step covers "all nodes in the tier".
SolutionSegment: the database backend behind the OrderSvc tier. Wait is 2.8 s of 3.1 s; DNS, connect and SSL are small; loss, latency and jitter are clean, so not the path. All OrderSvc nodes slow and snapshots point to one backend call, so not a single node. Handoff: database owner. Variation: if connect were 900 ms with 6% loss on a mid-path hop, the answer flips to the transit network.

Recall check

Today

1. A BT is slow but Step 1 finds no slow snapshots. Where next?Step 3: check for slow database or remote-service calls on the backend.
2. In an HTTP server test, which metric is time to first byte, what is wait time, and what does availability 0% mean?Response time is time to first byte, starting before DNS. Wait is request sent to first byte. Availability is 0% when the status code is not 2xx or 3xx.
3. Path Viz shows a red ring mid-path versus on the destination node. What does each mean?Mid-path: loss in the network between agent and target. On the destination: loss at the target itself (app, firewall, load balancer).
4. A new deployment's flow map is green but users complain. Give two reasons.The default view does not compare to a baseline, and baselines take hours to weeks to build. Also, a metric under 20 calls per minute gets no baseline by default.
