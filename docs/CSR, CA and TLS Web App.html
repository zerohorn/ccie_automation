CSR, CA and a TLS web app

2026-10-29 (Thu) · Blueprint 5.2 — Create a CSR via OpenSSL, send it to a CA, secure a web app with the certificate · Domain 5 Security (15% per tracker) · Tier 2 · Read ≈ 18 min · Unit 20 of 49

Mental snapshot

  • A CSR is a signed request: subject + public key + optional attributes (e.g. requested extensions). The signature, made with the matching private key, proves the requester holds that key. It carries no issuer, validity or serial; the CA adds those.
  • The private key never leaves the server. Only the CSR goes to the CA. If a key ever travels, you did something wrong.
  • The CA decides what lands in the certificate. By default openssl x509 -req ignores extensions in the CSR, so a SAN you put in the CSR can silently vanish.
  • Clients match the hostname against SAN entries (DNS or IP). Common Name is no longer valid for identifying a service (RFC 9525).
  • Server presents leaf + intermediates; the client already holds the root in its trust store. Missing intermediate = chain failure.
  • Serving: either the app loads cert + key itself (Python ssl) or a TLS termination proxy does and the app speaks plain HTTP behind it.
  • Exam shape: generate key + CSR with correct subject/SAN, get it signed, install, then prove it with openssl verify and openssl s_client.

Fundamentals → exam depth

L1 — concept

Public-key identity needs a third party. You make a key pair, wrap the public key and your name into a CSR (PKCS#10, RFC 2986✅), and sign it with your own private key. That self-signature prevents someone from requesting a certificate for another party's public key (RFC 2986 §3, note 2). The CA checks you, then signs a certificate binding your name to your key. A client that trusts the CA can trust the binding.

L2 — mechanics

What the CA controls matters more than what you ask for. With openssl x509 -req, the page says request extensions are ignored unless -copy_extensions is copy/copyall, and extensions you want come from -extfile/-extensions (openssl-x509 3.2✅). With openssl ca, a policy section decides which subject fields are required, optional or must match the CA, and fields the policy does not mention are silently deleted (openssl-ca 3.0✅).

L3 — exam detail

  • SAN is the identity. RFC 9525 §2: the Common Name RDN must not identify a service. DNS names match label by label, case-insensitive; a wildcard is only allowed as the whole left-most label; IP entries match exactly (§6.4) (RFC 9525✅). RFC 6125, which allowed CN fallback, is obsolete. If the exam says "reach it by IP", you need an IP: SAN entry.
  • Extension set for a server cert: basicConstraints=CA:FALSE, keyUsage (digitalSignature, keyEncipherment), extendedKeyUsage=serverAuth, subjectAltName. A CA cert needs CA:TRUE (x509v3_config, 1.1.1✅ — older version; syntax is stable but check your install).
  • Key and CSR flags: -newkey rsa:2048 (default RSA 2048), -noenc to leave the key unencrypted (-nodes deprecated since 3.0), -keyout, -subj "/C=US/O=Lab/CN=app.lab.local", repeatable -addext "key=value". -days applies only with -x509 (openssl-req 3.6✅).
  • Chain building starts at the target, finds an issuer by name, uses the trust store first, then -untrusted intermediates, and does not backtrack. OpenSSL ships no default trust anchors; distros configure one. -verify_hostname checks SAN DNS (or CN), -verify_ip checks SAN IP only (verification options (master)✅).
  • File order: Python's load_cert_chain wants one PEM file with the certificate plus any CA certificates needed to establish its authenticity; the key can be separate; a key/cert mismatch raises SSLError (ssl, Python 3.15 docs✅). Leaf first, then intermediates is the convention ⚠ ordering not stated on that page.
  • Proxy vs app termination: FastAPI's HTTPS page says TLS is normally terminated by a separate proxy (Traefik, Caddy, Nginx, HAProxy) that forwards plain HTTP, and that certificates are obtained from a third party, not generated (About HTTPS✅). The page gives no uvicorn/Flask flags.

Anatomy

Pinned to OpenSSL as documented above (3.0–3.6 pages; workstation build ⚠ unverified — run openssl version).

# key + CSR in one command (req page: -newkey, -noenc, -keyout, -subj, -addext)
openssl req -new -newkey rsa:2048 -noenc -keyout app.key -out app.csr \
  -subj "/O=Lab/CN=app.lab.local" \
  -addext "subjectAltName=DNS:app.lab.local,IP:10.10.10.20"

# inspect what you are about to send
openssl req -in app.csr -noout -text -verify
# extension file the CA side controls (x509v3_config syntax)
[server_ext]
basicConstraints=CA:FALSE
keyUsage=digitalSignature,keyEncipherment
extendedKeyUsage=serverAuth
subjectAltName=DNS:app.lab.local,IP:10.10.10.20
# client-side proof
openssl verify -CAfile ca.crt -verify_hostname app.lab.local app.crt
openssl s_client -connect 10.10.10.20:8443 -servername app.lab.local \
  -CAfile ca.crt -verify_return_error -brief

s_client: without -verify_return_error the handshake continues after certificate errors, so you see all problems (openssl-s_client 3.0✅). ⚠ unverified — test in lab: DNS: form inside -addext, -verify exit behavior on 3.0 (the 3.6 page says exit 1 since 3.3), -verify_hostname combined with -verify flags on your build.

Verify: (1) cert text shows both SAN entries and CA:FALSE; (2) openssl verify -CAfile ca.crt app.crt prints OK; (3) s_client … -verify_return_error completes; (4) repeat with -servername other.lab.local logic via openssl verify -verify_hostname other.lab.local and confirm it fails.
Hint

Make the CA with openssl req -x509 -newkey rsa:2048 -noenc -keyout ca.key -out ca.crt -subj "/CN=Lab CA" -addext "basicConstraints=critical,CA:TRUE" -days 365 (x509 flags per req page). The server's extension file must contain the SAN; a SAN only in the CSR will not survive.

Solution
openssl req -new -newkey rsa:2048 -noenc -keyout app.key -out app.csr -subj "/CN=app.lab.local"
cat > ext.cnf <<'X'
basicConstraints=CA:FALSE
keyUsage=digitalSignature,keyEncipherment
extendedKeyUsage=serverAuth
subjectAltName=DNS:app.lab.local,IP:127.0.0.1
X
openssl x509 -req -in app.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 90 -extfile ext.cnf -out app.crt
openssl verify -CAfile ca.crt app.crt
python3 - <<'P'
import ssl, http.server
ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
ctx.load_cert_chain("app.crt", "app.key")
s = http.server.HTTPServer(("127.0.0.1", 8443), http.server.SimpleHTTPRequestHandler)
s.socket = ctx.wrap_socket(s.socket, server_side=True)
s.serve_forever()
P
# other shell
openssl s_client -connect 127.0.0.1:8443 -servername app.lab.local -CAfile ca.crt -verify_return_error -brief

Recall check

  1. What is in a CSR, what is not, and what does its signature prove?
    AnswerVersion 0, subject, subject public key info, optional attributes (e.g. requested extensions), signed by the subject's private key. No issuer, validity or serial. The signature stops someone requesting a cert for another party's public key (RFC 2986 §3, §4).
  2. The CSR carried a SAN; the issued cert has none. Why, and name two fixes.
    Answerx509 ignores request extensions by default. Use -extfile/-extensions, or -copy_extensions copy (for ca, the config option).
  3. Name the three CA-section artifacts openssl ca insists on and one surprise about the policy section.
    AnswerDatabase file (index.txt, may be empty), serial file with a valid hex serial, and CA cert/key; policy silently drops DN fields it does not list unless -preserveDN.
  4. A browser reaches the app by IP and rejects the cert, whose CN is the IP. Why?
    AnswerCN is not used to identify a service (RFC 9525 §2); the cert needs an IP: SAN, matched octet-for-octet.
  5. (from 2026-10-22) Your openssl-signed device key will not import into IOS XE. Likely cause?
    AnswerThe 17.5 gNMI guide says the device key must be des3-encrypted before crypto pki import … pem terminal with a password (stored in the 10-22 notes).
  6. (from 2026-10-26) A Pod's readiness probe fails: is it restarted, and what happens to Service traffic?
    AnswerNot restarted; its IP is removed from the Service's EndpointSlices.
