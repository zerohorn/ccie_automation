Mental snapshot

  • 1.1 is the only blueprint item with the verb Design. Expect task shapes like "pick and justify a deployment" or "change this Compose/K8s/client config to meet requirement X", not a blank-page architecture.
  • Four lenses, one per sub-item: where it runs (container, VM, orchestrator), what happens when it fails, how it behaves under load, and how you know.
  • Reliability for stateful automation (NSO, Vault, GitLab) is a consensus problem. NSO HA Raft needs at least three nodes. Two-node HA can't tell a dead peer from a broken link.
  • Rate limiting is half the performance story for network automation. You consume other people's limits (Meraki: 10 req/s per org) more often than you set your own. Handle 429 + Retry-After correctly.
  • Kubernetes splits health into three probes: startup (is it booted?), liveness (restart it?), readiness (send it traffic?). Compose has one healthcheck plus depends_on conditions.
  • Observability has three signals: metrics, logs, traces. On this exam, metrics usually means Prometheus-style counters and gauges in Grafana, plus device telemetry from 3.4/3.5.

Where this fits

1.1 is a hub. Each lens is examined hands-on in a later domain, so this page builds the decision framework those units plug into.

L1 · Concept: four lenses on one solution

Take a typical exam-scale solution: a small Python REST service (2.1) that reads a source of truth, pushes config to devices through RESTCONF or a controller API, and exposes status. "Designing" it means answering four questions in order, because each answer constrains the next.

Where does it run? (1.1.a)

The blueprint lists containers, VMs, orchestration, automation, components and infra requirements. In practice the choice is a ladder. A VM suits a vendor appliance or a stateful platform shipped as an OVA. A container under Compose suits a few cooperating services on one host. An orchestrator (Kubernetes) suits services that need replicas, rolling updates, autoscaling or scheduling across nodes. Maintainability and modularity come from splitting by responsibility (API, worker, DB, collector) so each part can be rebuilt and replaced independently. Compose describes a service the same way: something that "can be scaled or replaced independently".

What happens when it breaks? (1.1.b)

Availability means a replacement is ready. Resiliency means the system recovers on its own. Stateless tiers get availability from replicas behind a Service or load balancer. Stateful tiers need replication with a clear rule for who is primary. That rule is where two-node designs fail.

How does it behave under load? (1.1.c)

Scalability is about adding capacity: horizontal (more replicas) or vertical (bigger instances). Latency is the per-request cost, and each hop, poll interval and serial loop adds to it. Rate limiting is the contract between client and server. In network automation the controller usually enforces the limit, and your design has to live within it.

How do you know? (1.1.d)

Monitoring answers known questions with predefined checks ("is it up?"). Observability lets you ask new questions from the signals the system already emits. You need metrics for trends and alerting, logs for events, and traces for following one request across services. On this exam that means device telemetry (3.4/3.5), application metrics in Grafana, and the AppDynamics/ThousandEyes view from 1.5.

L2 · Mechanics

Reliability mechanics: restart, probe, replicate, elect

There are four layers. Each one covers failures the layer below it can't.

  1. Restart. Compose restart values are no (the default), always, on-failure[:max-retries] and unless-stopped. In Kubernetes a crashing container is restarted with exponential backoff. Repeated crashes show as CrashLoopBackOff.
  2. Probe. When a liveness probe fails, the kubelet kills and restarts the container. When a readiness probe fails, the Pod's IP is removed from the EndpointSlices of every matching Service. The container keeps running, but it stops getting traffic. A startup probe holds off the other two until failureThreshold × periodSeconds has elapsed. The docs' example is 30 × 10 = 300 s.
  3. Replicate. A Deployment keeps N Pods. Stateless tiers can survive losing a node when replicas are spread across nodes.
  4. Elect. Stateful tiers need consensus. NSO 6.5 offers three HA modes, and only one can run at a time. HA Raft is consensus-based and hands-off. Rule-based HA (since 5.4) lets you influence primary selection but may need manual operator action. External HA gives data replication only. Raft needs at least three nodes. Three tolerates one failure, and five tolerates two. An even node count adds no fault tolerance.
Startup gates the other two probes. Liveness restarts the container. Readiness only stops traffic to it. Mixing up the last two causes most probe-related outages.

Performance mechanics: autoscale and back off

Horizontal Pod Autoscaler. The controller loop runs every 15 s by default and computes desiredReplicas = ceil(currentReplicas × currentMetric / desiredMetric). If the ratio is within the tolerance (0.1 by default), it skips scaling. For scale-down it takes the highest recommendation within a stabilization window, 5 minutes by default, so replicas drop gradually. Resource metrics come from metrics.k8s.io, normally served by metrics-server. Without it, a CPU-based HPA has nothing to act on.

Being a polite client. RFC 6585 §4 defines 429 Too Many Requests and says the response MAY carry Retry-After. RFC 9110 §10.2.3 allows that value to be an HTTP-date or delay-seconds, so a robust client handles both forms. Meraki's published budget: 10 requests/s per organization, shared by every application using that org, with a burst of 10 extra in the first second (30 in 2 s). There is a separate cap of 100 requests/s per source IP. Meraki implements this as a token bucket. Its remedies are design changes, not just retries: batch writes with action batches, use org-wide calls instead of per-device loops, and replace polling with webhooks (Push API) where the topic supports it.

The server tells you how long to wait. Use exponential backoff only when Retry-After is absent, and always cap the number of retries.

Observability mechanics: metric types and the pull model

Grafana's Prometheus primer describes a counter as a number that only increases (total bytes written, total requests). You chart it through a rate function, for example the increase over 5-minute windows. A gauge can go up or down (RAM in use, queue depth). Prometheus scrapes targets on an interval, and the Prometheus data source comes preinstalled in Grafana, queried with PromQL. Grafana exposes its own /metrics endpoint once internal metrics are enabled. Device telemetry from 3.4/3.5 fills the same role for the network: periodic subscriptions behave like gauges sampled on a cadence, and on-change subscriptions behave like events.

Hybrid and cloud placement. The blueprint names on-prem, hybrid and public cloud. The practical rules: state stays close to its consumers, controllers stay reachable from the devices they manage, and anything that crosses a boundary needs TLS (5.2) and secret handling (5.4). Dial-out telemetry (3.4) is the network version of the same idea. The device initiates the connection, so the collector can sit behind a firewall or in a cloud VPC.

Trap: two-node HA. Any requirement that says "two NSO nodes, automatic failover" conflicts with the NSO docs. Raft needs three because two nodes can't tell a dead peer from a partition. Rule-based HA with two nodes works, but expect manual intervention. Put that trade-off in your design note.

Trap: readiness used as liveness. If a readiness endpoint checks a downstream dependency and someone copies it into a liveness probe, a database blip restarts every API replica at once. Keep liveness local. Readiness can include dependencies.

Version note. Kubernetes docs fetched are the main branch (newer than the 1.33 pin). The HPA default values used here (15 s, 0.1, 5 min) are long-standing, but confirm them on a 1.33 cluster. Docker docs are current, not pinned to 28. Grafana docs are "latest", against the 12.2 pin.

# Compose: health-gated start + restart policy (shape from docs.docker.com startup-order example)
services:
  api:
    build: .
    restart: unless-stopped          # no | always | on-failure[:N] | unless-stopped
    depends_on:
      db:
        condition: service_healthy   # or service_started / service_completed_successfully
        restart: true                # restart api if db is restarted by a Compose operation
  db:
    image: postgres:18
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 10s
      retries: 5
      start_period: 30s
      timeout: 10s
# Kubernetes container probes (field names from the probes task page)
livenessProbe:
  httpGet: {path: /healthz, port: liveness-port}
  failureThreshold: 1
  periodSeconds: 10
startupProbe:                        # 30 x 10 s = 300 s to finish booting
  httpGet: {path: /healthz, port: liveness-port}
  failureThreshold: 30
  periodSeconds: 10
# Python 3.13 client: honour Retry-After (RFC 9110: seconds OR HTTP-date), cap retries
import time, random, requests
from email.utils import parsedate_to_datetime      # ⚠ unverified — test in lab
from datetime import datetime, timezone

def retry_after_seconds(value: str | None, attempt: int) -> float:
    if value is None:
        return min(2 ** attempt, 30) + random.random()   # fallback backoff + jitter
    if value.isdigit():
        return float(value)                               # delay-seconds form
    when = parsedate_to_datetime(value)                   # HTTP-date form
    return max(0.0, (when - datetime.now(timezone.utc)).total_seconds())

def get(session: requests.Session, url: str, max_tries: int = 5):
    for attempt in range(max_tries):
        r = session.get(url, timeout=10)
        if r.status_code != 429:
            r.raise_for_status()
            return r.json()
        time.sleep(retry_after_seconds(r.headers.get("Retry-After"), attempt))
    raise RuntimeError(f"rate limited after {max_tries} tries: {url}")

The Python fragment matches the RFC and Meraki behaviour described above, but it has not been run. ⚠ unverified — test in lab.

Micro-drill (~10 min)

Requirement. Containerise the 2.1 FastAPI "devices" service (or any small HTTP app) with a Postgres or Redis backend. It must:

  1. not start until the backend reports healthy,
  2. restart on crash but stay down after docker compose stop,
  3. expose a /healthz that checks only the local process,
  4. in its outbound client, honour 429 + Retry-After with at most 5 tries.

Then write three lines of design justification: why Compose rather than Kubernetes here, what would change for 3 replicas, and what you would monitor.

Reference fields. services.<n>.restart, depends_on.<svc>.condition, healthcheck.test / interval / retries / start_period / timeout.

Verification. docker compose up -d, then docker compose ps shows db healthy before api starts. docker kill the api container and it returns. docker compose stop api and it stays down. Point the client at a stub that returns 429 with Retry-After: 2: you should see roughly 2 s gaps and a clean failure after 5 tries.

Target. Candidate Workstation (Docker 28 + Compose). No network device needed.

Hint

unless-stopped is the only restart value that both restarts after a crash and respects an explicit stop. For the 429 stub, a FastAPI route can return Response(status_code=429, headers={"Retry-After": "2"}) ⚠.

Solution 
services:
  api:
    build: .
    ports: ["8000:8000"]
    restart: unless-stopped
    depends_on:
      db:
        condition: service_healthy
    healthcheck:

      interval: 10s
      retries: 3

    image: postgres:18
    environment: {POSTGRES_USER: app, POSTGRES_PASSWORD: example, POSTGRES_DB: app}

Recall check

1. A requirement says "two NSO nodes with automatic failover and no split-brain." What do you push back with?

NSO HA Raft needs at least three nodes. Three tolerates one failure, five tolerates two. A two-node system can't distinguish a failed peer from a lost link. Rule-based HA works with two nodes but may need manual operator action.

2. Liveness vs readiness failure: what does Kubernetes do in each case?

Liveness: the kubelet kills and restarts the container, with backoff that can lead to CrashLoopBackOff. Readiness: the Pod's IP is removed from matching Services' EndpointSlices and the container keeps running.

3. Meraki returns 429. Give the budget numbers, two forms Retry-After can take, and two design changes beyond retrying.

10 req/s per org shared across apps (+10 burst in the first second, 30 in 2 s), 100 req/s per source IP. Retry-After is delay-seconds or an HTTP-date (RFC 9110 §10.2.3). Design changes: action batches, org-wide endpoints instead of per-device loops, Push API webhooks instead of polling, configuration templates.

4. HPA: give the replica formula, default loop interval, default tolerance and default scale-down stabilization window.

desired = ceil(current × currentMetric / desiredMetric). 15 s sync period, 0.1 tolerance, 5-minute downscale stabilization. Needs metrics.k8s.io (metrics-server) for resource metrics.

5. (from 2026-11-17, 2.9.b) A leaf with when and a leaf with must both evaluate false. What does the operator see in each case?

when: the node is not configurable / removed, with no error. must: the commit is rejected with the error-message. (Restated from the 2026-11-17 page.)

6. (from 2026-11-16, 5.5) Why must a JWT verifier pass algorithms=[...] instead of trusting the token header, and which two attacks does that stop?

The alg header is attacker-controlled. Pinning algorithms stops "alg: none" and RS256→HS256 key confusion (RFC 8725). (Restated from the 2026-11-16 page.)
