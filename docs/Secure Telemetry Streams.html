Secure telemetry streams (TLS / mTLS)

Thu 2026-10-22 · Blueprint 3.5.e · Domain 3 (Network Programmability and Automation Tools) · Tier 1 (gap) · ~18 min read · Unit 16 of 49
Exam is v1.1. Pins: IOS XE 17.5 (lab runs 17.16), NX-OS 9.3(8).

Mental snapshot

  • Every telemetry transport has a "who is the TLS server" answer. Dial-in (gNMI): the router is the server. Dial-out (gRPC): the collector is the server and the router is the TLS client.
  • Default is server-auth only: the TLS client checks the server's cert chain and name. mTLS adds a client certificate that the server validates.
  • IOS XE keeps all of this in a PKI trustpoint. Dial-in uses gnxi secure-trustpoint; dial-out references a profile on the receiver line.
  • NETCONF dial-in telemetry rides SSH, not TLS: security is SSH keys/AAA. NX-OS dial-out uses a certificate <file> <hostname> line.
  • Most failures are boring: name/SAN mismatch, missing CA in the trustpoint, wrong port, clock skew, or an expired cert.
  • Cisco's 17.5 MDT guide lists TLS auth as unsupported in its gRPC restrictions list yet also says it works from 17.1.1. Know both statements exist.

Where this fits

Fundamentals to exam depth

L1: concept

TLS gives a channel confidentiality and peer identity. Identity is an X.509 certificate signed by a CA the other side trusts. The client checks (a) the chain leads to a trusted CA, (b) the name or IP it dialed matches the cert's SAN, (c) validity dates. That is server-auth TLS. In mTLS the server also sends a CertificateRequest and validates the client's cert. TLS 1.3 handshake: RFC 8446 sec. 2 (overview), 4.3.2 (CertificateRequest), 4.4.3 (CertificateVerify). The gNMI spec (sec. 3.1) requires TLS, says implementations should support TLS 1.2 or later, and describes new connections as mutually authenticated.

Telemetry adds a twist: you must decide which end is the server for each transport.

L3: exam detail

  • IOS XE gNMI secure mode (17.5 guide): commands gnxi, gnxi secure-trustpoint, gnxi secure-server, optional gnxi secure-client-auth (mTLS), optional gnxi secure-port. Secure default port 9339, insecure 50052. Insecure and secure can run together; the guide's Day Zero flow starts insecure then switches. Verify with show gnxi state.
  • Key encryption: the guide says IOS needs the device private key encrypted (it uses openssl rsa -des3) and imports with crypto pki import <tp> pem terminal password <pw>, pasting CA cert, key, device cert. Then revocation-check none in the trustpoint.
  • gNOI cert management: cert.Install (new cert; ID becomes the trustpoint name), cert.Rotate (renew; controller tests a new connection and sends Finalize), GetCertificates, RevokeCertificates, CanGenerateCSR. Bootstrapping via gnxi secure-init starts with a self-signed cert the client does not verify. gnmi-yang secure-peer-verify-trustpoint enables mutual auth; without it the device checks the client against all trustpoints and the trustpool.
  • Dial-out TLS (IOS XE): feature table says TLS for gRPC dial-out arrived in 17.1.1. The 17.5 chapter shows receiver ip address <ip> <port> protocol grpc_tls profile secure_profile in one example (underscore) while Cisco's YANG Suite page uses grpc-tls (hyphen). Try ? on the box.
  • Receivers can't be edited in place (from 3.5.d): changing profile means delete and recreate the subscription.
  • NX-OS 9.3: certificate is set under the destination with certificate /bootflash/server.key localhost style syntax (hostname argument = CN); "gRPC client sends the wrong certificate" counts toward the 20-error limit that disables the connection. HTTPS works only if a certificate is configured.
  • Name matching: openssl -verify_ip checks the SAN IP only; -verify_hostname checks SAN DNS or CN. If you dial a bare IP, put an IP SAN in the cert.
  • Auth beyond TLS: gNMI also lets the client pass username/password (and optional AAA metadata) in RPC metadata; failure maps to Unauthenticated (16). TLS and RPC credentials are separate layers.

# Collector-side cert with IP SAN (YANG Suite page)
openssl genrsa -out myca.key 2048
openssl genrsa -out server.key 2048
openssl req -x509 -new -nodes -key myca.key -sha256 -days 365 -out myca.cert

Micro-drill (~10 min)

Target: Cat8000V (IOS XE 17.16). Requirement: enable secure gNMI with server-auth TLS, then require client certs, and prove each state from the workstation.

  1. Create a root CA, a device cert (CN or SAN = device mgmt IP) and a client cert with openssl.
  2. Import device cert chain into a trustpoint (key encrypted).
  3. Enable gnxi secure-server on a non-default port.
  4. Verify with show gnxi state and openssl s_client (expect chain verifies, no client cert needed).
  5. Add gnxi secure-client-auth; show that connecting without -cert/-key fails and with them succeeds.

Reference: gnxi secure-trustpoint, secure-port, crypto pki import ... pem terminal password.

HintKey must be des3-encrypted before import. If s_client says verify error, check SAN against the IP you used in -connect and use -verify_ip.

Recall check

Today

1. Dial-in vs dial-out: which end is the TLS server in each, and where does the certificate that proves the server's identity live?Dial-in: router (trustpoint named by gnxi secure-trustpoint). Dial-out: collector holds server cert+key; router trustpoint holds the signing CA.
2. What does gnxi secure-client-auth add, and what are the secure and insecure default ports?Authenticates the client certificate against the root cert (mTLS). Secure 9339, insecure 50052.
3. Your openssl-signed device key won't import into IOS XE. What is the likely cause and fix?Key not encrypted; encrypt with openssl rsa -des3 and re-import with the password.
4. A collector is reached by IP 10.1.1.3 but its cert only has a DNS name. What fails, and which openssl option reproduces the check?Name verification fails (no IP SAN). -verify_ip checks SAN IP only. Reissue with IP SAN.
