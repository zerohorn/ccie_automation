Mental snapshot

  • 5.5 is the server side of what 5.3 (OAuth token) and 5.4 (Vault) did from the client side: your API now has to reject bad callers, not just be a good caller.
  • Three nouns in the blueprint verb map to three jobs: secrets are what the server keeps (signing key, key hashes), tokens are what callers present, and headers are how tokens travel and how the server answers (WWW-Authenticate, security headers).
  • Status codes follow a strict split: 401 = "who are you?" (credentials missing or bad); 403 = "I know who you are, and no."
  • Credentials go in headers, never in the URL, because URLs land in logs.
  • Compare secrets in constant time (secrets.compare_digest), not with ==.
  • For a JWT, pin the algorithm list and validate exp, aud, iss. Never let the token header pick the algorithm.
  • The signing key and API keys come from the environment or Vault at startup, never from source code.

Where this fits

L1 — Concept: what "securing" means for an API

A REST API has no login page and no session cookie by default. Every request arrives cold, so it must carry its own proof of identity, and the server must check that proof on every request. The OWASP REST Security Cheat Sheet states the baseline: HTTPS only, access checks at every endpoint, and an API key on every request to a protected endpoint. REST Security Cheat Sheet✅

Think of it in networking terms. TLS is your IPsec tunnel: it protects the bytes in transit, but anything inside the tunnel is trusted only as far as you authenticate it. The token in the Authorization header is like the AAA credential on the far end. The server still has to decide what that identity may do, and that decision is authorization, the equivalent of command authorization on a TACACS+ server.

The three nouns in the blueprint line map onto those layers:

  • Secrets live at L0: the JWT signing key, the API key list (or its hashes), and the webhook HMAC secret. FastAPI's settings guide loads them from environment variables through pydantic-settings. Settings and Environment Variables✅
  • Tokens are what the caller presents at L2. They can be opaque (a random string you look up) or self-contained (a JWT you verify mathematically).
  • Headers carry tokens in (Authorization, X-API-Key, a signature header) and carry policy out (WWW-Authenticate, Cache-Control, X-Content-Type-Options).

Bearer syntax and the challenge header

RFC 6750 §2.1 defines Authorization: Bearer <b64token> and requires resource servers to support it. §2.3 allows an access_token query parameter, but says clients SHOULD NOT use it, because URLs get logged. §3 says a resource server MUST send WWW-Authenticate when the request lacks valid credentials. §3.1 defines the error codes: invalid_request → 400, invalid_token → 401, insufficient_scope → 403. RFC 6750✅

The request path inside FastAPI

FastAPI expresses each check as a dependency. The classes in fastapi.security (APIKeyHeader, HTTPBearer, HTTPBasic) only extract the credential. They raise 401 if it is missing, and they never validate it. Validation is your code. Security Tools✅

L3 — Exam detail: the traps

1. 401 versus 403 changed in FastAPI 0.122.0

Before FastAPI 0.122.0, a missing credential made the built-in security classes return 403. From 0.122.0 on, they return 401 with a WWW-Authenticate header (APIKey, Bearer or Basic). FastAPI documents how to restore the old behavior: subclass the class and override make_not_authenticated_error. Use Old 403 Authentication Error Status Codes✅. If a task's grader expects a specific code, check fastapi.__version__ before you argue with it. ⚠ The FastAPI version on the exam workstation is unverified.

APIKeyHeader sends WWW-Authenticate: APIKey. That challenge isn't standardized. FastAPI sends it because a 401 requires some challenge, per the Security Tools page.

2. Constant-time comparison

== stops at the first differing byte, which leaks timing. secrets.compare_digest is the same function as hmac.compare_digest. It takes about the same time wherever the mismatch is, but it accepts only bytes or ASCII-only str. FastAPI's Basic-auth example encodes values to UTF-8 bytes first for that reason. HTTP Basic Auth✅ · secrets✅ (3.15 doc; module unchanged since 3.6). Unequal lengths can still leak the length, but not the value (hmac docs).

3. JWT validation discipline

RFC 8725 is the checklist. The attacks it describes are alg: none, RS256→HS256 confusion (the RSA public key used as an HMAC secret), and brute-forcing a weak HS256 key. The defenses: §3.1 verify against an allowlist of algorithms, §3.5 use high-entropy keys (never a human password), §3.8 validate issuer and subject, and §3.9 validate audience. RFC 8725✅. In PyJWT, that becomes algorithms=[...], audience=, issuer=, and options={"require": [...]}. exp is checked automatically and raises ExpiredSignatureError, and leeway absorbs clock skew. Usage Examples — PyJWT✅ (2.15.1). The claim names come from RFC 7519 §4.1.1–4.1.7: iss sub aud exp nbf iat jti. RFC 7519✅

The FastAPI tutorial generates the HS256 key with openssl rand -hex 32, sets a 30-minute token, puts the username in sub, and turns any InvalidTokenError into a 401 with WWW-Authenticate: Bearer. OAuth2 with Password (and hashing), Bearer with JWT tokens✅. The tutorial does not set or check aud/iss. RFC 8725 says to check them when one issuer serves several APIs.

4. HMAC over raw bytes

Webex computes the signature over the raw request bytes, before any JSON parsing. If you parse and re-serialize first, whitespace and key order change and the digest won't match. X-Webex-Signature can carry several alg=digest pairs separated by commas, and you verify each pair on its own. In FastAPI, read the raw body with await request.body(). ⚠ That call isn't on any page fetched today, so test it in the lab. hmac.new requires digestmod (since 3.8). hmac✅ (3.15 doc)

5. Response headers and hygiene

For API responses, OWASP lists Cache-Control: no-store, Content-Security-Policy: frame-ancestors 'none', a correct Content-Type, HSTS, X-Content-Type-Options: nosniff and X-Frame-Options: DENY. It also says to return 405 for methods you don't allow, 415 for unsupported request types, and 429 for rate limits, and to keep error messages generic. In FastAPI, the clean place to add these headers is one @app.middleware("http") function. Middleware✅

6. Secrets supply

BaseSettings maps environment variables to fields case-insensitively, can read .env (needs python-dotenv), and is cached with @lru_cache, which tests can override through app.dependency_overrides. If the task says the key lives in Vault, read it once at startup: GET /v1/<mount>/data/<path> with X-Vault-Token, and the value is under data.data. KV secrets engine - version 2 (API)✅ (latest; pin 1.20). ⚠ The /v1/ prefix isn't in today's summary. It is standard Vault, but verify it with vault kv get -output-curl-string.

Anatomy (annotated, not the drill solution)

A. API key header with constant-time match

from typing import Annotated
import secrets
from fastapi import Depends, FastAPI, HTTPException, status
from fastapi.security import APIKeyHeader

api_key_hdr = APIKeyHeader(name="X-API-Key")        # missing → 401, WWW-Authenticate: APIKey (≥0.122.0)

def require_key(key: Annotated[str, Depends(api_key_hdr)]) -> str:
    expected = get_settings().api_key.encode()      # from env/.env, never literal
    if not secrets.compare_digest(key.encode(), expected):
        raise HTTPException(status.HTTP_401_UNAUTHORIZED, "Invalid API key",
                            headers={"WWW-Authenticate": "APIKey"})
    return key

The pieces are documented separately (APIKeyHeader on Security Tools, compare_digest on HTTP Basic Auth). Combining them like this is ⚠ unverified, so test it in the lab.

B. JWT verify with audience, issuer, required claims (PyJWT)

import jwt
claims = jwt.decode(
    token, SIGNING_KEY,
    algorithms=["HS256"],                      # allowlist; header 'alg' is not trusted
    audience="netops-api", issuer="lab-idp",   # InvalidAudienceError / InvalidIssuerError
    options={"require": ["exp", "iss", "sub"]},# MissingRequiredClaimError
    leeway=10,                                 # seconds of clock skew on exp/nbf
)
if "admin" not in claims.get("scope", "").split():
    raise HTTPException(403, "insufficient_scope")   # authenticated, not authorized

The scope claim layout is your own convention (⚠). Space-separated scopes follow OAuth practice from 5.3.

C. Webhook HMAC verify (Webex X-Webex-Signature shape)

raw = await request.body()                     # ⚠ unverified call; raw bytes, not request.json()
hdr = request.headers.get("x-webex-signature", "")   # look up case-insensitively
for pair in (p.strip() for p in hdr.split(",")):
    alg, _, digest = pair.partition("=")
    if alg == "sha256":
        mine = hmac.new(SECRET, raw, digestmod="sha256").hexdigest()  # lowercase hex
        if hmac.compare_digest(mine, digest):
            break
else:
    raise HTTPException(401, "bad signature")

Pair format alg=digest and lowercase hex come from the Webex guide. The exact algorithm label strings are ⚠ unverified.

D. Security headers middleware

@app.middleware("http")
async def sec_headers(request: Request, call_next):
    response = await call_next(request)
    response.headers["Cache-Control"] = "no-store"
    response.headers["X-Content-Type-Options"] = "nosniff"
    response.headers["Content-Security-Policy"] = "frame-ancestors 'none'"
    return response

Speed notes (offline on the workstation)

  • python -m pydoc fastapi.security.APIKeyHeader shows the constructor args (name, scheme_name, description, auto_error). Use pydoc jwt.decode for PyJWT options.
  • python -c "import fastapi,jwt;print(fastapi.__version__,jwt.__version__)" settles the 401/403 question in five seconds.
  • Generate keys with python -c "import secrets;print(secrets.token_urlsafe(32))" or openssl rand -hex 32. The secrets docs call 32 bytes sufficient (2015 baseline).
  • Swagger at /docs shows a padlock per protected route. That's a quick way to check every route got its dependency.
  • curl -i shows status and WWW-Authenticate together. Use -H 'X-API-Key: …' and -H 'Authorization: Bearer …'.
  • vault kv get -output-curl-string secret/app prints the exact HTTP call your app should make (from 5.4).

Micro-drill (~10 min)

Requirement. Build a FastAPI app netops_api with three routes:

  • GET /health is open.
  • GET /devices needs header X-API-Key matching env var NETOPS_API_KEY. Return a static list such as ["cat8kv","iosv"].
  • POST /admin/reload needs Authorization: Bearer <JWT>, HS256, aud="netops-api", and scope containing admin.

Missing or invalid credentials → 401 with WWW-Authenticate. Valid JWT without admin scope → 403. Every response carries Cache-Control: no-store.

Reference fields. fastapi.security.APIKeyHeader(name=...), HTTPBearer() → .credentials, jwt.decode(..., algorithms=, audience=), secrets.compare_digest, env NETOPS_API_KEY, NETOPS_JWT_KEY.

Verification.

  1. curl -i :8000/devices → 401 plus WWW-Authenticate.
  2. Same request with the right key → 200 plus cache-control: no-store.
  3. Mint two tokens with jwt.encode, one with scope:"read" and one with "admin". Expect 403, then 200.
  4. A token with aud="other" → 401.

Target. Candidate Workstation (local uvicorn). No network device needed.

Hint

Write two dependency functions. require_key wraps APIKeyHeader. require_admin wraps HTTPBearer, decodes the token, and raises 401 for jwt.InvalidTokenError and 403 for a missing scope. Attach the headers in one middleware. Read both secrets through a cached settings object.

Solution sketch 
from functools import lru_cache
from typing import Annotated
import secrets, jwt
from fastapi import Depends, FastAPI, HTTPException, Request
from fastapi.security import APIKeyHeader, HTTPBearer, HTTPAuthorizationCredentials
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    netops_api_key: str
    netops_jwt_key: str

@lru_cache
def get_settings(): return Settings()

app = FastAPI()
key_hdr, bearer = APIKeyHeader(name="X-API-Key"), HTTPBearer()

@app.middleware("http")
async def no_store(request: Request, call_next):
    r = await call_next(request); r.headers["Cache-Control"] = "no-store"; return r

def require_key(k: Annotated[str, Depends(key_hdr)]):
    if not secrets.compare_digest(k.encode(), get_settings().netops_api_key.encode()):
        raise HTTPException(401, "Invalid API key", headers={"WWW-Authenticate": "APIKey"})

def require_admin(c: Annotated[HTTPAuthorizationCredentials, Depends(bearer)]):
    try:
        claims = jwt.decode(c.credentials, get_settings().netops_jwt_key,
                            algorithms=["HS256"], audience="netops-api",
                            options={"require": ["exp", "sub"]})
    except jwt.InvalidTokenError:
        raise HTTPException(401, "Invalid token", headers={"WWW-Authenticate": "Bearer"})
    if "admin" not in claims.get("scope", "").split():
        raise HTTPException(403, "insufficient_scope")
    return claims

@app.get("/health")
def health(): return {"ok": True}

@app.get("/devices", dependencies=[Depends(require_key)])
def devices(): return ["cat8kv", "iosv"]

@app.post("/admin/reload")
def reload(claims: Annotated[dict, Depends(require_admin)]): return {"by": claims["sub"]}

⚠ Whole solution untested. Check that InvalidAudienceError is a subclass of InvalidTokenError in your PyJWT version, and that fastapi[standard]/pydantic-settings are installed.

Recall check

  1. A request has a well-formed, unexpired JWT whose scope lacks the needed value. Which status code and which RFC 6750 error code apply?
  2. Why must a JWT verifier pass algorithms=[...] instead of trusting the token header, and which two attacks does that stop?
  3. Your Webex webhook receiver rejects every event although the secret is right. Give the most likely cause and the fix.
  4. On FastAPI ≥ 0.122.0, what does APIKeyHeader return when the header is missing, and how do you get the old behavior?
  5. (from 2026-11-09) A genie diff shows hundreds of changed counter lines. Where do the default exclusions come from, and which two flags change them?
  6. (from 2026-11-10) An app reads secret/app fine via CLI but its token gets 403 over HTTP. What path error is likely, and how do you find the right path quickly?
Answers
  1. 403 with insufficient_scope (RFC 6750 §3.1). The caller is authenticated but lacks privilege.
  2. The alg header is attacker-controlled. An allowlist blocks alg: none and the RS256→HS256 key-confusion attack (RFC 8725 §2.1, §3.1).
  3. The HMAC is computed over parsed or re-serialized JSON instead of the raw bytes, or with the wrong algorithm for the header. Compute it over the raw body and pick the algorithm from the header pair (SHA-1 for X-Spark-Signature).
  4. 401, detail "Not authenticated", WWW-Authenticate: APIKey. To get 403 back, subclass the class and override make_not_authenticated_error.
  5. verification_datafile.yaml for learn snapshots and pts_datafile.yaml for parse snapshots. --exclude adds exclusions, and --no-default-exclusion removes the defaults.
  6. For KV v2, the API and policy path is secret/data/app, and listing uses metadata/. Use -output-curl-string or -output-policy to see the real path.
