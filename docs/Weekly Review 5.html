1. Where the week fits

All four topics sit on one request path. A client reaches an API over TLS, the API answers with the right status, the platform decides whether the instance is fit to receive traffic, and telemetry tells you whether any of it is working. Each layer has its own "looks healthy" signal that can be wrong. That is the review theme: a green indicator at one layer proves nothing about the layer above it.

Receiver states you must read correctly

RFC 8639 defines four receiver states. IOS XE prints its own strings (rcvr-state-connecting, rcvr-state-connected in the 17.5 guide), and the separate show telemetry internal connection shows Active or Connecting per transport connection. These are different views of one pipeline. Do not compare them literally.

Triage order

When a service "doesn't work", walk outside-in and stop at the first failure. This beats starting at the layer you know best.

Anatomy: two details that decide the answer

The 2.1 and 5.2 items look unrelated until you read the exact lines. The first shows the pattern the FastAPI "Handling Errors" tutorial uses for a 404. The second shows why openssl x509 -req does not carry a CSR's SAN unless you tell it to: the x509 manual says extensions in the request are not copied by default, and -copy_extensions copy changes that.

raise HTTPException(status_code=404, detail="Item not found")   # body: {"detail": "Item not found"}

openssl x509 -req -in srv.csr -CA ca.pem -CAkey ca.key -CAcreateserial \
    -copy_extensions copy -out srv.pem                          # keeps the CSR's SAN

Target: Candidate Workstation (Ubuntu 24.04, uv). Optional last step on Cat8000V (17.16). No cluster needed: the readiness check is a shell exit code.

Requirement.

  1. Build a lab CA and a server certificate whose SAN contains the workstation IP, signed by that CA.
  2. Write a FastAPI app with GET /healthz returning {"status":"ok"} and GET /items/{name} that returns 404 with a detail body for an unknown name.
  3. Serve it over TLS on port 8443. Prove the cert verifies by IP with s_client, then show the 200 and the 404 with curl -i --cacert.
  4. Write a one-line readiness check from curl that exits 0 when healthy and non-zero when not. Stop the server and show the exit code change.
  5. Optional: if the TIG dial-out is configured, show the receiver connection as Active on Cat8000V and name the command you used.

Reference fields: openssl req -new -newkey -noenc -keyout -subj -addext · openssl x509 -req -CA -CAkey -CAcreateserial -copy_extensions · HTTPException(status_code, detail) · s_client -connect -verify_ip -CAfile.

Verify: verification reports success for the IP; /items/nope returns 404 with {"detail": ...}; /openapi.json lists both paths; the readiness command flips exit status when you stop uvicorn.

Hint

Put the IP SAN in the CSR with -addext, then make the signing step keep it. Without that second part the issued cert has no SAN and step 3 fails. For the readiness line, curl has an option that turns HTTP errors into a failing exit code ⚠ confirm in curl --help all.

Solution (⚠ unverified — test in lab) 
openssl req -x509 -new -newkey rsa:2048 -noenc -keyout ca.key -subj "/CN=lab-ca" -days 30 -out ca.pem
openssl req -new -newkey rsa:2048 -noenc -keyout srv.key -subj "/CN=ws" \
    -addext "subjectAltName=IP:10.0.0.5" -out srv.csr
openssl x509 -req -in srv.csr -CA ca.pem -CAkey ca.key -CAcreateserial \
    -copy_extensions copy -days 30 -out srv.pem

6. Recall check

Three per topic. Answer aloud before opening.

4.3.b-d Pods, probes, kubectl

1. A Pod shows CrashLoopBackOff and RESTARTS keeps rising. Which command shows the crashed instance's output, and what are the restart-delay timing facts?

Answer

kubectl logs POD --previous. The delay starts at 10 s, doubles, caps at 300 s, and resets after 10 minutes of clean running. ⚠ Numbers verified 2026-10-26 from page source; the rendered page body was not readable today.

2. An app takes 4 minutes to boot and a liveness probe (period 10, threshold 3) keeps killing it. What do you add?

Answer

A startup probe on the same endpoint with period 10 and a failure threshold of at least 24 (for example 30), so the liveness probe only starts after startup succeeds. ⚠ Same caveat as above.

3. Readiness fails on one Pod. Is it restarted, and what happens to Service traffic?

Answer

No restart. Its IP is removed from the Service's endpoints, so it stops receiving traffic. The Probes page summary states that Kubernetes can stop sending traffic to containers that are not ready.

2.1 Python REST API

4. A POST handler is declared with item: Item and q: str. Where does each value come from?

Answer

item is parsed from the JSON body (a Pydantic model); q is a query-string parameter. ⚠ From the 2026-10-27 page, not re-fetched today.

5. A lookup returns 200 with nothing for a missing id. What is the fix and what shows in the body?

Answer

Raise HTTPException(status_code=404, detail="Item not found"). Body: {"detail": "Item not found"}. The detail value can be any JSON-convertible value, not only a string.

6. Name the three built-in URLs FastAPI serves and what each is.

Answer

/docs (Swagger UI), /redoc (ReDoc), /openapi.json (the generated OpenAPI schema that feeds both).

3.5.f-g Confirm and triage telemetry

7. Subscription is Valid but show telemetry internal connection says Connecting. Name the checks.

Answer

Ping the receiver from the device, test the receiver port (the Cisco example shows a refused connection), check for a firewall and for the right port number, and on VRF devices set the source VRF or source address. Healthy shows Active.

8. Where do you find why a subscription is Invalid, and what was the cause in the Cisco example?

Answer

The Notes field of show telemetry ietf subscription <id> detail. The XPath had an extra slash after the module prefix colon (/memory-ios-xe-oper:/memory-statistics/... instead of ...oper:memory-statistics/...).

9. How many receiver states does RFC 8639 define, and what does a timeout do?

Answer

Four: connecting, active, suspended, disconnected. Timeout is the transition from connecting to disconnected when the publisher cannot reach the receiver. With multiple receivers on one configured subscription, the 17.5 guide says only the first valid receiver is used.

5.2 CSR, CA, TLS web app

10. The CSR carried a SAN but the issued cert has none. Why, and name two fixes.

Answer

openssl x509 -req ignores request extensions unless told otherwise. Use -copy_extensions copy (or copyall), or supply the extension via -extfile.

11. A browser reaches the app by IP and rejects a cert whose CN is that IP. Why, and how do you reproduce the check with openssl?

Answer

RFC 9525 says the Common Name must not be used to identify a service. An IP identity must match an iPAddress entry in subjectAltName. Reproduce with -verify_ip, which checks only SAN IP entries; -verify_hostname checks DNS SAN and falls back to CN.

12. What do -CA and -CAcreateserial do on openssl x509?

Answer

-CA makes the command act as a micro CA and sets the issuer to the CA cert's subject. -CAcreateserial creates the serial-number file if missing and writes a random serial for the new cert.
