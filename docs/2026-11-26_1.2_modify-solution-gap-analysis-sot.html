Modify Automation Solutions

Date Thu 2026-11-26 Blueprint 1.2 Modify an existing network automation solution based on business and technical requirements (includes gap analysis, source of truth) Domain 1.0 Software Design, Development, and Deployment (20%) Tier 3 Read ~18 min Unit 36 of 49 Docs Terraform v1.13.x · ciscodevnet/aci 2.17.0 schema · ansible-core 2.19.3 + ansible.utils 6.0.1 (run offline) · NSO 6.5 · RFC 8342

This is the last unit of the week; tomorrow is weekly review 9. Today's verb is Modify. You get code that already works and a list of new requirements. The job is to find what is missing and change only that, without breaking what runs today. The drill uses Terraform against the DevNet ACI sandbox, because Terraform with ciscodevnet/aci is what the workstation ships.

Mental snapshot

  • "Modify" means you start from working code and a requirement delta. Make the smallest change that closes the delta. Nothing that works today should be destroyed, recreated or reconfigured.
  • Gap analysis has two halves. The requirement gap is what the solution cannot do yet. The state gap is where the network differs from the source of truth (SoT). List both before you edit anything.
  • The SoT is the data your automation renders from. It is the authority for the fields it owns. When network and SoT disagree, decide per field: push the SoT value (remediate), or pull the network value into the SoT (accept).
  • Every tool has a read-only compare: terraform plan, ansible-playbook --check --diff, NSO compare-config, genie diff. Run it before the change to get a clean baseline, and again after it to prove you get zero.
  • Change the data model first (schema and SoT entries), then the code, then the checks. Validate the SoT before it touches a device.
  • Refactors must keep object identity. In Terraform, moved blocks keep a count→for_each change from destroying anything, and import blocks adopt hand-made objects. In NSO, re-deploy reconcile takes ownership of existing config.
  • Merge-style compares see "missing" and "changed", never "extra". To find objects on the network that the SoT does not list, diff both ways.

Where this fits

Unit 1.1 asked you to design a solution from scratch. Unit 1.2 hands you one that exists and asks you to change it. The mechanics come from units already covered: rendering from a SoT (2.6), Terraform state (2.8.f), NSO sync (2.9) and Genie diff (3.3.b). This unit is the judgment that sits on top of them: what to change, in what order, and how to prove nothing else moved.

L1: Two gaps and one authority

A requirement arrives as prose. "Operations wants tenants defined in a YAML file with descriptions." "The lab tenant someone built by hand must come under automation." Some of that is a business requirement: who uses the tool, and what outcome they need. Some is technical: platforms, interfaces, constraints. The gap analysis turns that prose into a list of concrete differences you can test.

The SoT is the answer to "what should be there?" It can be a YAML file in Git, a database, or NSO's CDB. The NSO 6.5 guide lists "act as a network source of truth" among the reasons to make every change through NSO. NetBox does not appear on the v1.1 Equipment and Software List. So expect files in the Git repo, NSO, or an API the task gives you. ⚠ inference from the list

RFC 8342 (NMDA) gives this the standard vocabulary. <intended> is the configuration the system tries to apply. <operational> holds what is actually in use, plus state. They can differ for honest reasons. A resource may be missing, for example config for an interface that is not present. Remnant config may linger while resources are released. The device may add system or default configuration. A good gap report keeps those apart from real drift.

L2: The modify loop

Step 2 is the one people skip. Run the read-only compare before you touch the code. If it already shows changes, the network has drifted, or someone left work half-done. Your change and that old drift would then show up mixed in one plan, and you could not tell them apart. Record the drift as a gap and decide its authority (step 4). Only then start changing things.

Step 4 is per field, not per system. Some values belong to the SoT and must be enforced, such as IP addresses or a tenant's existence. Others can be owned by operators, such as an MTU tweak or a description. NSO 6.5 makes this explicit with out-of-band policies (L3). In Terraform you express it with lifecycle { ignore_changes = [...] } or by moving the field out of the config. ⚠ ignore_changes not re-read today

Step 5 before step 6. Change the schema and the SoT entries first. Then the template or resource only reads fields that already exist and are validated. Data errors then fail fast with a JSON path, not deep in a device error.

The last column is the classic trap. Terraform deletes what leaves the SoT because state remembers it. Ansible forgets it, because there is no state. If the requirement says "remove anything not in the SoT," a playbook needs an explicit list of extras and a delete task for each.

L3: Exam-depth detail

Terraform: refactor without churn, and drift

  • Changing a resource from count to for_each changes every address, from t[0] to t["prod"]. By default Terraform reads a new address as destroy-old, create-new. On 1.13.3 offline, two live instances refactored without help planned 3 to add, 2 to destroy. With one moved { from = t[0] to = t["prod"] } per index, the same plan showed "has moved to" for each, and 1 to add, 0 to destroy. The v1.13.x refactoring page shows the index-to-key form.
  • If moved blocks live in a module other people consume, keep them. The same page warns that removing them is a breaking change for anyone who has not applied yet.
  • -refresh-only plans or applies only state updates for changes made outside Terraform. The refresh-only tutorial notes it replaces the deprecated terraform refresh, which overwrote state without review. It changes state, not config. Normal mode then still drives remote objects to match the config, so the next plan proposes undoing the drift. To accept the change, also change the SoT. ⚠ derived from the two mode definitions
  • -detailed-exitcode returns 0 for no changes, 1 for an error and 2 for changes, per the v1.13.x plan reference. That is your CI drift gate. Confirmed offline: 2 with a pending change.
  • Adopting a hand-made ACI object uses an import block with the full DN as ID. Cisco Live BRKDCN-2607 imports aci_tenant with id = "uni/tn-tf_test_import". The 2.17.0 provider schema also has a provider argument allow_existing_on_create, described as letting existing objects be managed. Its default is not in the schema. ⚠ default and behavior untested

Ansible: what check and diff cannot see

  • Per the check-mode guide, modules without check-mode support report nothing and do nothing under --check. A silent run is not proof that there is no gap. In the pinned collections, cisco.aci.aci_tenant (2.12.0) and ansible.netcommon.restconf_config/netconf_config (8.4.0) all declare supports_check_mode=True in their source.
  • restconf_config 8.4.0 GETs the path, then computes dict_diff(running, candidate) and sends only that diff. That helper only returns keys that are in the candidate, so config on the device but absent from the SoT never shows up. It also puts the candidate under before and running under after in --diff output, the reverse of what you expect. read from 8.4.0 source
  • Validate SoT data before render with ansible.utils.validate. The default engine is ansible.utils.jsonschema, which needs the jsonschema Python library on the controller. ⚠ library on CWS unconfirmed
  • For a two-way list compare, use the builtin difference filter in both directions. Its ansible-doc says the output order is arbitrary, so sort before you compare or print.

NSO 6.5: sync verbs and out-of-band policy

  • Device actions in Lifecycle Operations: check-sync compares a signature. It is cheap, but it may report unsupported. compare-config fetches the config and diffs it. sync-from pulls the device config into CDB and commits it at once. sync-to pushes a minimal diff. Both take dry-run.
  • After a sync-from, services may be out of sync; the guide says to run check-sync and re-deploy. Service check-sync does not contact the device. Only deep-check-sync catches an edit made out of band.
  • Brownfield adoption: re-deploy reconcile makes the service own config that existed before it. Manual config further down the tree is kept unless you add discard-non-service-config.
  • New in 6.5 (Out-of-band Interoperation): confirm-network-state, set per commit or per device. Each rule in a service out-of-band policy picks an action by path and change type (at-create, at-delete, at-value-set). sync-from-device accepts the change into CDB. sync-to-device reverts the device. manage-by-service keeps the value through re-deploy and deletes it with the service. If no rule matches, NSO uses sync-from-device.

Task shapes consistent with the verb

  • Starting code plus a requirements paragraph. You add a field, a platform or a resource. Then show that existing objects did not change (plan: 0 to destroy, check: changed=0).
  • A drift report: name what differs, say which side wins and why, and close it in the right direction.
  • A design-style question: given business constraints (who calls it, what they need, mixed old and new devices), choose which part of the existing solution to extend. The BRKDEV-2014 worked example favours NSO over a per-device REST collection, because it gives one consistent northbound API across old and new devices.

Anatomy

Each snippet was run or validated offline this run, at the versions noted. None of them is the drill solution.

A. Two-way gap report in plain Python (3.13.18, stdlib, executed)

def gap(intended: dict, actual: dict) -> dict:
    want, have = set(intended), set(actual)        # set(dict) = its keys
    return {
        "missing": sorted(want - have),            # in SoT, not on device
        "extra":   sorted(have - want),            # on device, not in SoT
        "changed": sorted(k for k in want & have   # on both...
                          if intended[k] != actual[k]),   # ...values differ
    }

sot = {"Loopback10": "10.10.10.1/32", "Loopback20": "10.20.20.1/32"}
dev = {"Loopback10": "10.10.10.9/32", "Loopback99": "10.99.99.1/32"}
# -> {"missing": ["Loopback20"], "extra": ["Loopback99"], "changed": ["Loopback10"]}

Three set operations make up the whole gap report. - is difference and & is intersection. Sorting makes the output stable for diffs and tests. Fill actual from a RESTCONF GET (unit 3.1.iosxe) or from an APIC class query.

B. Validate the SoT, then diff both ways (ansible-core 2.19.3, ansible.utils 6.0.1, executed on localhost)

- name: Validate SoT before touching anything
  ansible.utils.validate:
    data: "{{ {'tenants': tenants} }}"
    criteria: "{{ lookup('ansible.builtin.file', 'tenant_schema.json') | from_json }}"
    engine: ansible.utils.jsonschema           # default; needs python jsonschema

- name: Compute gaps                           # actual_names from a query task
  ansible.builtin.set_fact:
    missing: "{{ tenants | map(attribute='name') | difference(actual_names) }}"
    extra:   "{{ actual_names | difference(tenants | map(attribute='name')) }}"

- name: Human-readable diff (shows with --diff, reports changed when different)
  ansible.utils.fact_diff:
    before: "{{ actual_names | sort }}"
    after:  "{{ tenants | map(attribute='name') | sort }}"

On a bad entry, validate fails with a message like Additional properties are not allowed ('desc' was unexpected) and json_path $.tenants[2]. fact_diff returns diff_text and diff_lines.

C. CI drift gate (Terraform 1.13.3)

terraform plan -input=false -detailed-exitcode -out=tfplan
case $? in
  0) echo "network matches SoT" ;;
  2) echo "diff present: review tfplan before apply"; exit 1 ;;
  *) echo "plan error"; exit 1 ;;
esac

Target: DevNet ACI Simulator Always-On sandbox APIC (credentials from the sandbox page), from the workstation with Terraform 1.13.3 and ciscodevnet/aci 2.17.0. Replace cw with your initials, because the sandbox is shared.

  count = length(var.tenants)

  4. The incident description on cw-dev is accepted as the new standard.

HintWrite the data first: the YAML with three entries, using the incident text for cw-dev. Map each old index to its new key with moved. A tenant that already exists gets an import block, not just a new map entry. Accepting drift here means changing the SoT, not running refresh-only.
Solution 
# sot.yaml
tenants:
  cw-prod: { descr: "Production" }
  cw-dev:  { descr: "Dev (incident 4711)" }   # accepted drift lives in the SoT
  cw-lab:  { descr: "Lab - adopted" }

# main.tf
locals {
  sot = yamldecode(file("${path.module}/sot.yaml"))
}

resource "aci_tenant" "t" {
  for_each    = local.sot.tenants
  name        = each.key
  description = each.value.descr
}

moved {
  from = aci_tenant.t[0]
  to   = aci_tenant.t["cw-prod"]
}
moved {
  from = aci_tenant.t[1]
  to   = aci_tenant.t["cw-dev"]
}

import {
  to = aci_tenant.t["cw-lab"]
  id = "uni/tn-cw-lab"
}

# CI: terraform plan -input=false -detailed-exitcode  (exit 2 = APIC and SoT differ)

Recall check

Today

  1. You change count to for_each on a resource that holds two live tenants. What does the plan propose with no extra blocks, and what fixes it?
    AnswerIt plans to destroy [0] and [1] and create keyed instances (offline: 3 to add, 2 to destroy). Fix: one moved { from = r[0] to = r["key"] } per index. The plan then shows "has moved to" and 0 to destroy.
  2. A colleague edits a tenant description in the GUI during an incident. You run terraform apply -refresh-only. What changed, what didn't, and what does the next normal plan show?
    AnswerState (and outputs) now hold the GUI value. Nothing changed on the APIC, and the config still has the old value. So the next normal plan proposes reverting the description. To accept the change, put it in the SoT.
  3. Why can a restconf_config run, or its --check, report no change while the Cat8000V has extra loopbacks that the SoT doesn't list?
    AnswerIn 8.4.0 it computes dict_diff(running, candidate), which only returns keys present in the candidate. Device-only config is never reported or removed. Diff both ways, and delete the extras explicitly.
  4. NSO 6.5: name the three out-of-band policy actions and what each does with an outside change to service-managed config. Which applies when no rule matches?
    Answersync-from-device copies the device value into CDB (accept). sync-to-device reverts the device to CDB (reject). manage-by-service accepts the value and stores it with the service instance, so it survives re-deploy and is removed with the service. The fallback is sync-from-device.

From history

  1. (from 2026-11-18) Which tag goes on <device> in an NSO service template, why, and what does replace do differently from merge for children?
    Answertags="nocreate": the template must never create a device entry, only add config under one that exists. merge and nocreate are inherited by child nodes; replace and create are not. replace replaces the node's content instead of merging into it. (Restated from the 2026-11-18 page.)
  2. (from 2026-11-23) A requirement says "two NSO nodes with automatic failover and no split-brain." What do you push back with?
    AnswerHA Raft needs at least 3 nodes: 3 tolerate one failure and 5 tolerate two. Two nodes cannot tell a dead peer from a lost link. Rule-based HA may need manual action to recover. (Restated from the 2026-11-23 page.)
