Kubernetes core objects: Deployments, Services, Ingress, Secrets, Volumes, Namespaces

Date Tue 2026-10-20 Blueprint 4.3.a Domain 4 (weight not on tracker; unverified) Tier 2 Read ~18 min Unit 14 of 49 Pin kubectl/Kubernetes 1.33

Mental snapshot

  • You write desired state as YAML; controllers loop until reality matches. Everything below is a different kind of "desired state" object.
  • Deployment owns ReplicaSets, which own Pods. A Deployment is the thing you edit; ReplicaSets are the thing that gets replaced during a rollout.
  • Service is a stable name and virtual IP in front of whichever Pods match a label selector. No label match, no backends.
  • Ingress maps HTTP(S) host and path to Services, and does nothing unless an Ingress controller is installed.
  • Secret is base64 in an API object, not encryption. Consume it as env vars (fixed at start) or as a volume (files that update eventually).
  • Volumes are Pod-scoped; PV/PVC are how data outlives a Pod. Namespaces scope names, and Service DNS embeds the namespace.

Where this fits

Fundamentals to exam depth

L1: concept

Kubernetes is a declarative API. You submit objects; controllers compare spec to status and act. For an architect, treat it like an intent-based controller: the manifest is the intent, kubectl apply is the northbound call, and the kubelet on each node is the southbound agent. Two things are easy to get wrong coming from network gear: there is no running-config you edit in place (you re-apply a file, and the API rejects some changes), and labels are the glue, not names or IPs.

L2: mechanics

Deployment and ReplicaSet. The Deployment's .spec.selector must match the Pod template labels or the API rejects it, and the selector is immutable after creation. Only a change to the Pod template (image, labels, env) starts a rollout; scale does not. Each rollout creates a new ReplicaSet ✅ named <deployment>-<hash>, with a pod-template-hash label you must not edit. The default strategy is RollingUpdate with maxSurge and maxUnavailable both 25% (surge rounds up, unavailable rounds down); neither can be 0 if the other is 0. Recreate kills all old Pods first. Defaults worth memorizing: revisionHistoryLimit 10, progressDeadlineSeconds 600, minReadySeconds 0.

Service. A Service selects Pods by label; a controller maintains the matching EndpointSlices as Pods come and go. port is what the Service listens on, targetPort is the Pod's port (defaults to port, can be a named port), nodePort is the port opened on every node (default range 30000-32767). A Service without a selector needs its EndpointSlice created by hand. clusterIP: None makes it headless: DNS returns Pod addresses and there is no virtual IP. Inside the cluster a Service resolves as <svc> in its own namespace, <svc>.<ns> from elsewhere, full form <svc>.<ns>.svc.cluster.local. The details are on the Service page ✅.

Ingress. It exposes HTTP and HTTPS routes only; it is not a generic port forwarder. An Ingress ✅ needs a controller to fulfil it. ingressClassName names the IngressClass (and so the controller); if omitted, a default class should exist. Every path needs pathType: Exact, Prefix or ImplementationSpecific; the longest match wins and exact beats prefix at equal length. A tls block references a Secret with tls.crt and tls.key; TLS ends at the Ingress and traffic to Pods is plaintext. The TLS hosts must match rule hosts explicitly. The page states the API is GA but frozen and recommends Gateway API for new work; the exam topic list still says ingress, so know the object.

Secrets. A Secret ✅ is stored unencrypted in etcd by default; base64 is encoding only. data takes base64, stringData takes plain text and is merged into data on write (stringData wins on a clash). Cap is 1 MiB. Types: Opaque (default), kubernetes.io/tls (requires tls.crt and tls.key, contents not validated), kubernetes.io/dockerconfigjson (requires .dockerconfigjson), plus basic-auth, ssh-auth, service-account-token. immutable: true cannot be reverted; delete and recreate to change.

L3: exam detail

Volumes and persistence. A volume ✅ is declared under spec.volumes and mounted per container under volumeMounts (name, mountPath, readOnly, subPath). Data survives container restarts in every type; only some survive the Pod.

TypeLifetimeUseGotcha
emptyDirPod on that nodeScratch, sharing between containersmedium: Memory counts against container memory limit
hostPathNode filesystemNode agentsSecurity risk; differs per node
configMap / secretFollows source objectConfig files, credentialsAlways read-only; subPath = no updates
persistentVolumeClaimOutlives PodDurable dataClaim must be in the Pod's namespace

For durability: a PersistentVolume ✅ is cluster storage, a PVC is the request (size, access mode, class). Binding is one-to-one. Dynamic provisioning needs a PVC that names a StorageClass (an empty class name opts out). Access modes: RWO (one node), ROX, RWX, RWOP (one Pod, CSI only); they are matching constraints, not write protection. Reclaim policy Retain keeps data and leaves the PV Released; Delete removes PV and storage and is the default for dynamically provisioned volumes. PV phases: Available, Bound, Released, Failed.

Namespaces. Namespaces ✅ scope names, not networks. Defaults: default, kube-system, kube-public, kube-node-lease. They cannot nest; Nodes, PersistentVolumes and StorageClasses are cluster-scoped. Pick a namespace per command with -n/--namespace or set it for the context with kubectl config set-context --current --namespace=NAME. Cross-namespace Service access requires the qualified name. Forgetting the namespace is the most common reason "I applied it but can't see it".

ReplicaSet and scaling. Scaling changes spec.replicas; it does not create a revision. On scale-down the controller removes pending Pods first, then lower deletion-cost, then Pods on busier nodes, then newer Pods. A bare Pod whose labels match a ReplicaSet selector gets adopted, and extras are terminated, so keep labels distinct. Use a Deployment unless you have a reason not to.

Rollout commands. kubectl set image deployment/NAME CONTAINER=IMAGE starts a rollout; rollout status exits non-zero if the progress deadline is exceeded; rollout history (--revision=N) lists revisions; rollout undo (--to-revision=N) rolls back; pause/resume batch edits into one rollout, and you cannot roll back while paused. After progressDeadlineSeconds the Deployment gets a Progressing=False condition with reason ProgressDeadlineExceeded; Kubernetes takes no other action, so a stuck rollout stays stuck until you undo or fix it.

Anatomy

Deployment from the docs' own example (apps/v1), annotated:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx              # label on the Deployment itself; does NOT default from template in apps/v1
spec:
  replicas: 3               # scale changes this, no new revision
  selector:
    matchLabels:
      app: nginx            # immutable; must match template labels below
  template:                 # changing anything under here = new rollout
    metadata:
      labels:
        app: nginx          # this is what a Service selector targets
    spec:
      containers:
      - name: nginx
        image: nginx:1.14.2
        ports:
        - containerPort: 80

Ingress with TLS, from the docs' example (networking.k8s.io/v1); note the Secret is referenced by name and must be in the same namespace (⚠ same-namespace rule for Ingress TLS Secrets not on the fetched text; test in lab):

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: tls-example-ingress
spec:
  tls:
  - hosts:
      - https-example.foo.com   # must also appear in a rule host
    secretName: testsecret-tls  # type kubernetes.io/tls: tls.crt + tls.key
  rules:
  - host: https-example.foo.com
    http:
      paths:
      - path: /
        pathType: Prefix        # required per path
        backend:
          service:
            name: service1
            port:
              number: 80

Speed notes

  • Never type YAML from scratch. kubectl run nginx --image=nginx --dry-run=client -o yaml > pod.yaml is on the kubectl Quick Reference ✅; the same pattern with create deployment is the likely quick start (⚠ create deployment ... --dry-run=client -o yaml combination not on the fetched text).
  • Field names offline: kubectl explain pods is listed on the quick reference; drill deeper with dotted paths such as kubectl explain deployment.spec.strategy (⚠ dotted-path form and --recursive not verified here).
  • Namespaced or not: kubectl api-resources --namespaced=true / =false.
  • Preview a change: kubectl diff -f ./my-manifest.yaml before kubectl apply -f.
  • Pull a single field: kubectl get configmap NAME -o jsonpath='{.data.ca\.crt}' style (jsonpath form on the quick reference; the same shape works for Secret data, which you then base64-decode, ⚠ test).
  • Set the namespace once: kubectl config set-context --current --namespace=NAME.
  • Labels: every Service problem starts with kubectl get pods --show-labels (⚠ flag not on fetched text).
  • Whether kubectl and a cluster are available on the Candidate Workstation is not confirmed. Check the exam-day instructions.

Requirement: in a new namespace lab, run an app with 3 replicas, expose it inside the cluster, route HTTPS for one host to it, supply the TLS cert as a Secret, and give it a scratch volume.

  • Namespace lab; all objects live in it.
  • Deployment web: 3 replicas, label app: web, image nginx:1.14.2 (from the docs example; an old tag, substitute if the registry is unreachable), container port 80, an emptyDir mounted at /cache.
  • Service web: ClusterIP, port 80 to containerPort 80, selected by app: web.
  • Secret web-tls of type kubernetes.io/tls with tls.crt and tls.key (use any PEM pair you have, e.g. from the 5.2 drill).
  • Ingress web: ingressClassName of your controller, host web.lab.example (a name you choose, not a real one), pathType: Prefix at /, TLS secret web-tls.

Reference fields: spec.replicas, spec.selector.matchLabels, spec.template.spec.volumes[].emptyDir, spec.template.spec.containers[].volumeMounts[], spec.ports[].port/targetPort, spec.tls[].secretName, spec.rules[].http.paths[].pathType.

Verify:

  • kubectl -n lab get deploy,rs,pods: 3 Pods Ready, one ReplicaSet named web-<hash>.
  • kubectl -n lab get endpointslices: three Pod addresses behind Service web.
  • Change the image tag, then kubectl -n lab rollout status deployment/web and rollout history shows 2 revisions; rollout undo returns to 1.
  • kubectl -n lab scale deployment/web --replicas=5 adds no revision.
  • kubectl get pods without -n lab shows nothing: confirms namespace scoping.
HintWrite the Deployment first with kubectl create deployment web --image=nginx:1.14.2 --replicas=3 --dry-run=client -o yaml (⚠ flags unverified) and edit in the volume. The Service selector must equal the template label, not the Deployment's name.
Solution 
apiVersion: v1
kind: Namespace
metadata: {name: lab}
---
apiVersion: apps/v1
kind: Deployment
metadata: {name: web, namespace: lab, labels: {app: web}}
spec:
  replicas: 3
  selector: {matchLabels: {app: web}}
  template:
    metadata: {labels: {app: web}}
    spec:
      containers:
      - name: web
        image: nginx:1.14.2
        ports: [{containerPort: 80}]
        volumeMounts: [{name: cache, mountPath: /cache}]
      volumes: [{name: cache, emptyDir: {}}]
---
apiVersion: v1
kind: Service
metadata: {name: web, namespace: lab}
spec:
  selector: {app: web}
  ports: [{port: 80, targetPort: 80}]
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: {name: web, namespace: lab}
spec:
  ingressClassName: nginx-example      # replace with your IngressClass
  tls: [{hosts: [web.lab.example], secretName: web-tls}]
  rules:
  - host: web.lab.example
    http:
      paths:
      - {path: /, pathType: Prefix, backend: {service: {name: web, port: {number: 80}}}}

Create the TLS Secret separately (⚠ unverified): kubectl -n lab create secret tls web-tls --cert=tls.crt --key=tls.key, or a manifest with type: kubernetes.io/tls and base64 data.

Recall check

Today

1. You edit a Deployment's selector to add a label and apply it. What happens, and what are two ways forward?The selector is immutable after creation, so the update is rejected. Revert the edit, or delete and recreate the Deployment (--cascade=orphan on delete keeps the Pods running). It must also still match the Pod template labels.
2. A Service's targetPort is a number that does not match the container's listening port. What do you see, and how do you confirm the Service still has endpoints?Endpoints exist (they depend on the label selector, not the port), but connections fail or are refused. Check EndpointSlices to see Pod IPs, then test the port directly against a Pod IP. targetPort defaults to port and can be a named port.
3. Name three differences between mounting a Secret as env vars versus as a volume.Volume: each key becomes a file, tmpfs-backed, read-only, updates arrive eventually (not with subPath). Env: mapped per key with secretKeyRef; keys with invalid names are skipped but the Pod starts. Both block container start if the Secret is missing and not optional.
4. PVC is Pending and the Pod will not start. Give two causes and the reclaim-policy default for dynamic volumes.No PV satisfies size, access mode and class, or no StorageClass/dynamic provisioner is available (an empty class name opts out of dynamic provisioning); the PVC must also be in the Pod's namespace. Dynamically provisioned volumes default to Delete.
