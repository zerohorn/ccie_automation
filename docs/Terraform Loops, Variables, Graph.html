Terraform loops, variables and the resource graph

Mon 2026-11-02Blueprint 2.8.a-c · Loop control, variables, resource graphsDomain 2 (weight unverified)Tier 3~18 minUnit 21 of 49

Mental snapshot

  • count = N copies addressed by integer index; for_each = one copy per map key or set member, addressed by key. They never coexist in one block.
  • Key rule: for_each keys and count must be known at plan time. Anything the API generates at apply time (IDs) cannot drive either.
  • Variables are typed inputs. Precedence is a stack: default lowest, -var/-var-file highest. Maps are replaced, not merged.
  • The graph is built from references (implicit) plus depends_on (explicit). File order is irrelevant. Independent nodes run in parallel, default 10 at once.
  • depends_on is a last resort: it makes plans conservative ("known after apply" spreads).
  • Exam shape for 2.8.a-c (blueprint verbs: loop control, variables, resource graphs): write or fix a config that creates N ACI objects from a variable, and explain or print the dependency order.
  • Lab: only ciscodevnet/aci v2.17.0 is installed on the workstation; no IOS XE provider. Everything runs against APIC.

Where this fits

Fundamentals to exam depth

L1: concept

Terraform is declarative: you describe objects, it computes the difference from state and applies it. Three things make a config scale beyond copy-paste: loops (many objects from one block), variables (inputs that change per environment), and the graph (Terraform works out order itself).

L2: mechanics

Loops. count takes an integer, exposes count.index, and instances are type.name[0], [1]. for_each takes a map or a set of strings, exposes each.key/each.value (equal for a set), and instances are type.name["key"]. A list must go through toset(); that drops order and duplicates. dynamic blocks loop over nested blocks inside one resource, not over resources.

Why keys beat indexes. Remove the first item of a list driving count and every later index shifts, so Terraform sees changes to every following instance. With for_each keys, removing one key affects only that instance. (The fetched count page does not discuss index shifting; this is standard behavior of index-addressed instances, treat as ⚠ unverified against the doc.)

Variables. A variable block takes type, default, description, validation, sensitive, nullable, and (1.10+) ephemeral. Type constructors: list, set, map, object, tuple. sensitive hides CLI output only; the value is still in state in cleartext.

Graph. Terraform adds a node per resource instance, edges from every reference and from depends_on, a root node, and splits destroy and create nodes where a replacement happens. It validates no cycles, then walks the graph: a node runs when its dependencies finish, up to 10 concurrently (-parallelism). Destroy runs in reverse dependency order.

Anatomy

Snippets show the shapes only; resource arguments for the ACI provider are ⚠ unverified (registry docs were not fetched) so check with terraform providers schema -json on the workstation.

# variables.tf
variable "vrfs" {
  type = map(object({
    description = optional(string, "")
  }))
  validation {
    condition     = length(var.vrfs) > 0
    error_message = "At least one VRF is required."
  }
}
variable "tenant_name" { type = string }

# main.tf  (ACI argument names: check schema)
resource "aci_vrf" "v" {
  for_each  = var.vrfs
  tenant_dn = aci_tenant.t.id        # implicit edge
  name      = each.key
}
# count form and a toggle
resource "aci_tenant" "t" {
  count = var.create_tenant ? 1 : 0
  name  = var.tenant_name
}
# reference with index:  aci_tenant.t[0].id

# dynamic block shape (nested blocks inside one resource)
dynamic "rule" {
  for_each = var.rules
  content { name = rule.value.name }
}

⚠ unverified: optional(string, "") default syntax needs Terraform ≥1.3 (not on a fetched page); tenant_dn/name argument names for aci_vrf at v2.17.0; aci_tenant.t[0].id output attribute.

Target: DevNet Sandbox APIC (tracker: local APIC deferred). Provider: ciscodevnet/aci 2.17.0, the only installed provider.

Requirement:

  • Variable vrfs: map of objects with an optional description. Validate that at least one entry exists.
  • Create one tenant and one VRF per map key, using for_each.
  • Add a second tenant toggle with count that creates nothing when false.
  • Run terraform graph and name the edge order. Remove one VRF key and show only that instance is destroyed.

Reference fields: look up the argument names in terraform providers schema -json for aci_tenant and aci_vrf. Provider block needs the APIC URL and credentials; check the provider schema for names (⚠ unverified).

Verification: (1) terraform plan shows aci_vrf.v["prod"] style addresses; (2) after apply, delete one key and plan: exactly one destroy; (3) terraform state list shows keyed addresses.

Hint

The tenant reference in each VRF is what orders creation. If the plan shows VRFs with no dependency on the tenant, you typed the tenant name instead of referencing the resource.

variables.tf as in Anatomy; one aci_tenant, one aci_vrf with for_each = var.vrfs and each.key as name, a second tenant with count = var.extra ? 1 : 0. Run init, validate, plan -var-file. Attribute names are yours to confirm from the schema; I did not verify them.

Recall check

Today

1. A config drives count from a list and you delete the first list item. What happens and what is the safer pattern?

Later indexes shift, so Terraform plans changes for every following instance (index-addressed). Use for_each over a map keyed by stable names. ⚠ index shifting is not on the fetched count page.

2. for_each = var.names where names is a list(string) fails. Give the error cause and two ways to fix.

Only maps or sets of strings are accepted. Wrap in toset() (drops order and duplicates) or convert to a map.

3. Name the order of variable sources from lowest to highest, and say what happens when a map is set in two sources.

default, env TF_VAR_, terraform.tfvars, terraform.tfvars.json, *.auto.tfvars, then -var/-var-file. Maps and objects are overridden whole, not merged.

4. How many nodes does Terraform apply in parallel by default, what changes the setting, and what does depends_on cost you?

10; -parallelism. depends_on can make plans more conservative: more replacements and more "(known after apply)" values. Use references where possible.
