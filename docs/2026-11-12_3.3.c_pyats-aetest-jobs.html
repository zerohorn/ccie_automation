3.3.c pyATS: develop and execute test jobs and scripts with AEtest

Date Thu 2026-11-12 Blueprint 3.3.c (parent 3.3 Modify/troubleshoot an automated test using pyATS) Domain 3 · weight ⚠ unverified Tier 1 (gap) Read time ~18 min Unit 28 of 49

Mental snapshot

  • A testscript is a Python module with up to three kinds of container: one optional CommonSetup, any number of Testcase classes, one optional CommonCleanup. Decorated methods inside them are the sections.
  • Order is definition order. Setup runs first, tests run in script order, cleanup runs last, at every level.
  • Results come from exceptions: AssertionError gives Failed, any other uncaught exception gives Errored. self.failed() and friends end a section immediately.
  • Results roll up. Ranking from strongest: Aborted, Errored, Failed, Blocked, Passx, Passed, Skipped.
  • Steps split one section into reported sub-checks. By default the first non-passing step ends the section; continue_=True keeps going.
  • Parameters are injected by argument name and shadow outward-in: section, then testcase, then script. Job or CLI arguments overwrite script defaults.
  • Two ways to run: standalone (aetest.main(), no archive) and Easypy (pyats run job, archive, reports, testbed injected).

Where this fits

3.3.a gave you the testbed. 3.3.b gave you structured data from parse and learn. 3.3.c is the harness that turns those into pass/fail verdicts a pipeline can act on. The blueprint verb on the parent is modify/troubleshoot, so expect task shapes like "this script reports Blocked; make it pass" or "add a check to an existing job" rather than writing a framework from nothing.

L1: Concept

AEtest is a test harness in the same family as unittest or pytest, built for network test plans where order matters and where a failed prerequisite should stop dependent work. You do not write a main loop that calls checks. You declare classes and decorated methods; the engine imports the module, discovers sections, instantiates them and runs them in a fixed order. The AEtest docs hub ✅ describes this as import, inspect, run.

For a network engineer the useful analogy is a change-window MOP. Common setup is "connect, confirm pre-checks". Each testcase is a numbered verification block with its own prep and rollback. Common cleanup is "disconnect, restore". The harness enforces that if prep fails, the verification is not attempted, and it reports why.

The second idea is the job. A testscript says what to check. A job file (Easypy) says which scripts to run, against which testbed, with which arguments, and it packages logs and results into an archive. Standalone execution is for writing and debugging; the job is what you hand to CI.

L2: Mechanics

Containers and sections

Per the Script Structure ✅ page:

Two rules from that page carry most troubleshooting tasks. First, a failing testcase setup blocks that testcase's test sections. Second, test sections and subsections run regardless of earlier siblings' results; deciding to stop is your job, through results with goto, must_pass, or steps.

How a section gets its result

From Section Results ✅: every section starts as Passed. An AssertionError makes it Failed. Any other uncaught exception (a KeyError on a parsed dict is the classic) makes it Errored. You can also call self.passed(), self.failed(), self.errored(), self.skipped(), self.blocked(), self.aborted() or self.passx(). Each takes optional reason, goto, from_exception and data, ends the section on the spot like return, and can be called once.

The page also says not to catch BaseException, since that swallows Ctrl-C and exit requests. Catch the specific exception you expect.

Parameters

Test Parameters ✅ work like Python scoping. The script has a parameters dict; a testcase can have its own; a section sees the merged view, nearest scope winning. Sections receive parameters as function arguments by name, so def check(self, testbed, interfaces): gets both if they exist. A default in the signature applies only when the parameter is undefined. Reserved names are testscript, section, reporter and steps, and they win over normal parameters with the same name. Job-file arguments (Easypy) or CLI arguments (standalone) overwrite matching script defaults. Writing to self.parameters inside a section stays local to that section.

L3: Exam detail

Rollup: which result wins

The Results Rollups ✅ page gives a full pairwise table. It reduces to one ladder:

Consequences worth memorising: Skipped never drags a Passed parent down (Passed + Skipped = Passed). Blocked loses to Failed, so a testcase with a failed setup and blocked tests reports Failed. Errored beats Failed, so one KeyError in a section of otherwise failed asserts reports Errored. Passx sits above Passed: one Passx child makes the parent Passx.

Steps in detail

Per Section Steps ✅: ask for steps as an argument, then open each step with with steps.start('name') as step:. An assert inside a step fails only that step; other exceptions make it Errored. If a step ends in anything other than Passed, Passx or Skipped, the engine skips the remaining steps and closes the section, unless that step was started with continue_=True. Steps nest with step.start() and are numbered 1, 1.2, 1.2.1. Step results roll up into the section with the same ladder.

This is the main design decision in a verification test. Use steps with continue_=True when you want "check all 12 interfaces and report each", and the default when step 2 is meaningless if step 1 failed (no connection, no parse).

All from Flow Control ✅. One gap: the fetched pages do not state what happens to testcases when CommonSetup fails. ⚠ unverified — test in lab. Do not rely on an implicit block; if connection failure must stop the run, say so with self.failed(..., goto=['common_cleanup']).

Looping, datafiles, processors

Looping Sections ✅: only subsection, Testcase and test can loop. @aetest.test.loop(intf=['Gi1','Gi2']) creates one section per value; without uids the ids are built from name and parameters (test[intf=Gi1]). With uids, the uid count sets the iteration count. aetest.loop.mark(target, ...) marks a loop at runtime, for values you only know after connecting.

Datafile Inputs ✅: a YAML file applied after import. parameters merge with dict.update(); testcases are keyed by class name, not uid; datafiles cannot add or remove looping. Pass with -datafile=, aetest.main(datafile=...) or run(..., datafile=...).

Section Processors ✅: pre, post and exception hooks. A pre-processor that returns False marks the section Skipped and its post-processors do not run.

Anatomy

Annotated snippets for pyATS as documented on pubhub (docs undated). Device calls follow the 3.3.a and 3.3.b pages.

# verify_lab.py  — testscript (module)
from pyats import aetest

parameters = {'interfaces': ['Loopback0']}     # script defaults; job args overwrite

class CommonSetup(aetest.CommonSetup):
    @aetest.subsection                        # CommonSetup must use subsections
    def connect(self, testbed):               # 'testbed' injected by Easypy
        testbed.connect()                     # ⚠ connect-all form: see 3.3.a page
        # store for later sections; ⚠ verify persistence on your pyATS version
        self.parent.parameters['dev'] = testbed.devices['cat8kv']

class InterfacesUp(aetest.Testcase):
    must_pass = False                         # True = stop the run on failure

    @aetest.setup
    def collect(self, dev):
        self.brief = dev.parse('show ip interface brief')   # 3.3.b

    @aetest.test
    def check(self, steps, interfaces):       # 'steps' is reserved
        for intf in interfaces:
            with steps.start(f'{intf} up', continue_=True):
                assert intf in self.brief['interface'] # ⚠ parser keys

# job.py  — Easypy job file
from pyats.easypy import run

def main(runtime):
    run(testscript='verify_lab.py', runtime=runtime,
        interfaces=['GigabitEthernet1', 'Loopback0'])  # extra kwargs → script args

# launch, then inspect
pyats run job job.py --testbed-file testbed.yaml
pyats logs view --latest            # opens newest archive in a browser
pyats run job job.py -t testbed.yaml --no-archive --html-logs ./out

# standalone tail for fast iteration (Running TestScripts page)
if __name__ == '__main__':

    result = aetest.main(testbed=loader.load('testbed.yaml'))
    aetest.exit_cli_code(result)         # makes $? reflect the result

Speed notes (offline on the workstation)

  • pyats run job --help lists job, testbed, archive and logging flags (arguments vary with installed plugins).
  • pyats logs list and pyats logs view --latest; add --no-browser --host 0.0.0.0 if the browser is on another box. Archives live under ~/.pyats/archive or the venv's users/<you>/archive.

Micro-drill (~10 min)

Requirement. On Cat8000V, write verify_lab.py and job.py. The job passes a list of interfaces. One testcase checks each interface's status is up, reporting one step per interface and continuing past failures. If the device cannot be reached, the run must jump straight to common cleanup. Common cleanup disconnects. Include one deliberately bogus interface name to prove the step continues and the testcase reports Failed.

Reference fields. Script argument interfaces (list). Device name from your 3.3.a testbed (example: cat8kv). Parser: show ip interface brief → ['interface'][name]['status'] ⚠ unverified key path; confirm with genie parse.

Verification. (1) pyats run job job.py -t testbed.yaml ends with common_setup Passed, testcase Failed, common_cleanup Passed. (2) pyats logs view --latest shows one step per interface, the bogus one Failed and the next one still executed. (3) Shut the mgmt path or point the testbed at a wrong IP: testcase shows Blocked or Skipped (not Errored) and cleanup still runs.

Target. Cat8000V 17.16 over SSH; repeat against N9Kv with os: nxos if time allows.

Hint

Put the connection in a try/except in a CommonSetup subsection and call self.failed(reason, goto=['common_cleanup']). Pass the interface list as an extra keyword argument to run(); it arrives as a parameter named interfaces. Use continue_=True on each step.

Solution 
from pyats import aetest

class CommonSetup(aetest.CommonSetup):
    @aetest.subsection
    def connect(self, testbed):
        dev = testbed.devices['cat8kv']
        try:
            dev.connect(log_stdout=False)              # ⚠ kwarg: see 3.3.a page
        except Exception as e:                         # connection errors vary by plugin
            self.failed(f'connect failed: {e}', goto=['common_cleanup'])
        self.parent.parameters['dev'] = dev            # ⚠ verify in lab

class InterfacesUp(aetest.Testcase):
    @aetest.setup
    def collect(self, dev):
        self.brief = dev.parse('show ip interface brief')

    @aetest.test
    def status_up(self, steps, interfaces):
        for intf in interfaces:
            with steps.start(f'{intf} status', continue_=True):
                entry = self.brief['interface'].get(intf)
                assert entry is not None, f'{intf} not present'
                assert entry['status'] == 'up', f"{intf} is {entry['status']}"

class CommonCleanup(aetest.CommonCleanup):
    @aetest.subsection
    def disconnect(self, testbed):
        testbed.devices['cat8kv'].disconnect()       # ⚠ guard if never connected

# job.py
from pyats.easypy import run
def main(runtime):
    run(testscript='verify_lab.py', runtime=runtime,
        interfaces=['GigabitEthernet1', 'Loopback0', 'Loopback999'])

Why .get() plus assert: a direct index on a missing key would raise KeyError and report Errored instead of Failed.

Recall check

1. A testcase's @aetest.setup raises AssertionError. What happens to its tests, and what does the testcase report?

Its test sections are Blocked. Rollup: Failed (setup) + Blocked = Failed. Cleanup still has its own slot at the end.

2. Rank the seven results. What do Errored + Failed and Passed + Skipped roll up to?

Aborted, Errored, Failed, Blocked, Passx, Passed, Skipped. Errored + Failed = Errored. Passed + Skipped = Passed.

3. A test has three steps; step 2 fails; none use continue_. What runs, and what is the change?

Step 3 is skipped and the section ends Failed. Start step 2 with continue_=True (the flag on the failing step decides).

4. How does the testbed reach a script in standalone mode versus an Easypy job, and which mode writes an archive?

Standalone: you load it and pass aetest.main(testbed=...) (custom argparse if you want a flag). Easypy: --testbed-file/-t injects the testbed parameter, None without it. Only Easypy produces TaskLog, reports and an archive.

5. (from 2026-11-04, 5.3) Expired token versus a token lacking scope: HTTP status and challenge error for each?

401 with invalid_token versus 403 with insufficient_scope (RFC 6750 s3.1).

6. (from 2026-11-05, 2.2) A request hangs against a powered-off router. What is the Requests default, and what do you pass?

No timeout by default. Pass timeout=(connect, read).
