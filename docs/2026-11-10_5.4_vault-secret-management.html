Mental snapshot

  • Vault is a policy-gated API in front of secrets. Everything is path + capability. Learn the path rules and you have most of the troubleshooting.
  • Two separate questions: how does the app prove who it is (auth method, issues a token) and what may that token do (policies attached to the token).
  • KV v2 inserts data/ and metadata/ into API paths and policies. The CLI hides it; policies and curl do not.
  • AppRole = role_id (username-like, not secret) + secret_id (password-like, short-lived, ideally single-use and response-wrapped), delivered by different channels.
  • Apps should not carry Vault logic. Vault Agent can authenticate, renew, and render secrets to a file or inject env vars into a child process.
  • Tokens expire. A 403 after an hour of working is usually TTL, not policy.
  • Network analogy: policy = ACL with most-specific match and an explicit deny that beats everything; token = session with a lease timer.

Where this fits

Fundamentals → exam depth

L1 Concept

The problem: credentials hard-coded in repos, playbooks and env files. Vault centralizes them, authenticates the caller, authorizes by path, audits every access, and hands out short-lived tokens. The app gets a token, the token carries policies, and policies decide which paths and operations are allowed. Policy is deny-by-default; an empty policy grants nothing.

L2 Mechanics

Flow follows the CI/CD pattern on the AppRole best-practices page. The app already holds role_id; the broker never needs it.

L3 Exam detail

  • Policy matching. * is a prefix glob valid only as the last character; + matches exactly one segment. Most specific path wins; deny beats everything including sudo.
  • Verb mapping. Capabilities follow HTTP verbs: GET→read, POST/PUT→create/update, DELETE→delete, LIST→list. Generating dynamic creds is a GET, so it needs read.
  • KV v2 policy needs two paths when the app reads and lists: data/ for values, metadata/ for list. allowed_parameters-style constraints are not supported on KV v2.
  • AppRole role knobs. token_policies (old policies deprecated), bind_secret_id default true, secret_id_ttl, secret_id_num_uses (0 = unlimited), secret_id_bound_cidrs, token_ttl, token_max_ttl. A per-secret-id ttl/num_uses cannot exceed the role's.
  • Hardening. secret_id_num_uses=1, bound CIDRs, short token TTLs, wrap the secret_id, alert when an unwrap is refused because the token was already used.
  • Agent. Auto-auth with AppRole reads role_id_file_path and secret_id_file_path; the secret_id file is removed after reading by default. Templates render KV v2 under .Data.data; static secrets re-render every 5 min by default (static_secret_render_interval).
  • Never use the root token for an application. It exists for initial setup and emergencies.

Anatomy

Pinned to Vault docs as fetched (labelled "latest"; lab is Vault 1.20). Not the drill solution.

# enable KV v2 and write a secret (CLI inserts data/ for you)
vault secrets enable -path=external-apis kv-v2
vault kv put external-apis/weather/california api_key=...

# AppRole role, then credentials
vault auth enable approle
vault write auth/approle/role/my-role token_type=batch secret_id_ttl=10m token_ttl=20m token_max_ttl=30m secret_id_num_uses=40
vault read auth/approle/role/my-role/role-id
vault write -wrap-ttl=120s -f auth/approle/role/my-role/secret-id
# policy: path is the API path, not the CLI path
path "external-apis/data/weather/california" {
  capabilities = ["read"]
}
# HTTP API: KV v2 read; token is returned at auth.client_token on login
GET  /v1/external-apis/data/weather/california        # header X-Vault-Token
POST /v1/auth/approle/login   {"role_id":"...","secret_id":"..."}
POST /v1/external-apis/data/weather/california  {"options":{"cas":0},"data":{"api_key":"..."}}
# Vault Agent: auto-auth + env injection
auto_auth {
  method { type = "approle"
    config = { role_id_file_path = "/etc/vault/roleid"
               secret_id_file_path = "/etc/vault/secretid"
               remove_secret_id_file_after_reading = true } }
  sink { type = "file" config = { path = "/etc/vault/token" } }
}
env_template "DB_USER" {
  contents = "{{ with secret \"secret/data/db\" }}{{ .Data.data.user }}{{ end }}"
  error_on_missing_key = true
}
exec { command = ["./server"] }
# GitLab CI (Premium/Ultimate): secret path is <path>/<field>@<mount>
job:
  id_tokens: { VAULT_ID_TOKEN: { aud: https://vault.lab.local:8200 } }
  secrets:
    DATABASE_PASSWORD: { vault: production/db/password@ops, token: $VAULT_ID_TOKEN }

GitLab docs fetched are current (pin 18.4). Needs VAULT_SERVER_URL; the value lands in a temp file by default (file: false for the raw value). Vault-side JWT auth config is not covered here.

Speed notes (offline on the workstation)

  • -output-curl-string turns a CLI call into the exact HTTP request, so you see the real path. -output-policy emits the minimal policy a command needs. Both are on the CLI usage page.
  • vault kv get -mount=secret -field=passcode creds prints a bare value for piping.
  • vault agent -h for flags; vault policy write NAME file.hcl, then vault policy read NAME.
  • Env vars: VAULT_ADDR, VAULT_TOKEN, VAULT_FORMAT=json, VAULT_CACERT. VAULT_SKIP_VERIFY exists; don't use it as a fix.
  • vault path-help <path> for field lists on the live server ⚠ unverified — test in lab.
  • Vault binary on the workstation image: ⚠ unverified. curl + jq against HORNLAB01 is the fallback.

Micro-drill (~10 min)

Requirement. An app named cml-poller must read the Cat8000V RESTCONF credentials from Vault and nothing else.

  • KV v2 mount netauto; secret cat8000v/restconf with username, password.
  • Policy poller-ro: read that one secret only.
  • AppRole cml-poller: batch tokens, token TTL 20m, secret_id single use, TTL 10m.
  • Deliver the secret_id wrapped (120 s). Unwrap it, log in, read the secret with curl, extract the password with jq.
  • Verify. (a) a second unwrap of the same token fails; (b) a second login with the same secret_id fails; (c) reading netauto/data/other returns 403; (d) token lookup shows TTL ≤ 20m and policies poller-ro + default.
  • Target. Vault on HORNLAB01 with a non-root token (never reuse a token from the upstream reference repo). Optional: GET the hostname from Cat8000V RESTCONF with the retrieved credentials ⚠ unverified — test in lab.
  • Reference fields. auth/approle/role/:name: token_type, token_ttl, secret_id_ttl, secret_id_num_uses, token_policies. Login response: auth.client_token. KV read: data.data.password.
Hint

Policy path is netauto/data/cat8000v/restconf. The wrapping token comes back from the secret-id call; unwrap with vault unwrap or POST sys/wrapping/unwrap using it as the token. ⚠ unverified: response field name

Solution 
vault secrets enable -path=netauto kv-v2
vault kv put -mount=netauto cat8000v/restconf username=admin password='...'
cat > poller-ro.hcl <<'HCL'
path "netauto/data/cat8000v/restconf" { capabilities = ["read"] }
HCL
vault policy write poller-ro poller-ro.hcl
vault auth enable approle
vault write auth/approle/role/cml-poller token_type=batch token_policies=poller-ro \
  token_ttl=20m secret_id_ttl=10m secret_id_num_uses=1
ROLE=$(vault read -field=role_id auth/approle/role/cml-poller/role-id)
WRAP=$(vault write -wrap-ttl=120s -f -field=wrapping_token auth/approle/role/cml-poller/secret-id)
SID=$(VAULT_TOKEN=$WRAP vault unwrap -field=secret_id)
TOK=$(curl -s -d "{\"role_id\":\"$ROLE\",\"secret_id\":\"$SID\"}" $VAULT_ADDR/v1/auth/approle/login | jq -r .auth.client_token)
curl -s -H "X-Vault-Token: $TOK" $VAULT_ADDR/v1/netauto/data/cat8000v/restconf | jq -r .data.data.password

⚠ unverified — test in lab: -field=wrapping_token, vault unwrap flags, batch token with token_policies on 1.20.

Recall check

Today

  1. An app reads secret/app fine via CLI as admin but its token gets 403. What is the likely path error and how do you find the right path fast?
    AnswerKV v2 API/policy path is secret/data/app (list uses metadata/). Use -output-curl-string or -output-policy.
  2. Which AppRole value is not secret, which is, and how should the secret one reach the app?
    Answerrole_id is username-like; secret_id is password-like. Deliver separately through a trusted broker, response-wrapped, ideally single-use.
  3. A wrapped secret_id unwrap is refused. What does that tell you and what do you do?
    AnswerThe single-use token was already unwrapped or expired: possible interception. Alert, check audit logs, revoke and reissue.
  4. Service vs batch token, and which does the AppRole page recommend?
    AnswerService tokens are persisted, renewable, revocable, can have children. Batch tokens are not persisted, not renewable, no children. Batch is recommended.
