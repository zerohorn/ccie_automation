NSO: service template from a provided device config

Date 2026-11-18 (Wed) Blueprint 2.9.a Domain 2 — Network Programmability & Automation (weight ⚠ not verified this run) Tier 1 (gap) Read ~18 min Unit 31 of 49

Pins: NSO 6.5 docs, cisco-ios-cli NED. Lab status: NSO is still unbuilt per tracker, so this page is reading plus paper drill. Prereq was yesterday's 2.9.b (service YANG).

Mental snapshot

  • An NSO service template is the device config you already know, captured as XML in NSO's device-model schema, with the per-instance values replaced by {...} XPath expressions.
  • You don't hand-write the XML. Put the config into NSO (or sync it from a device), then pipe it through | display xml-template and save it into the package's templates/ directory.
  • The servicepoint attribute on <config-template> must match the ncs:servicepoint in the service YANG. That one string ties the YANG list to the template.
  • {/leaf} reads the service instance. {$VAR} reads a variable set in Python. {.} is the current node inside a <?foreach?>.
  • FASTMAP means you only write create logic. NSO works out modify and delete itself, so the template must give the same output for the same inputs every time.
  • Verify with commit dry-run outformat native before you commit. Debug with commit dry-run | debug template.
  • Once deployed, use check-sync, re-deploy, and display service-meta-data (refcount/backpointer) to prove the service owns what it should.

Where this fits

L1 — Concept

An NSO service has three parts that ship together in one package: a YANG service model (the inputs and their validation), a mapping from those inputs to device configuration, and optional code. For 2.9 the blueprint wants a python-and-template package on the cisco-ios-cli NED, and 2.9.a is the mapping part. In NSO, the mapping is usually an XML template.

The key idea is that the template does not contain CLI. It contains data that follows the YANG schema under /devices/device/config, which is the NED's model of the device. The NED turns that data into native commands when the transaction is pushed. So the template has the shape of a NETCONF payload that uses NSO's device tree: devices → device → name → config → (NED namespace) → …. You already did RESTCONF/NETCONF payloads in 2.4. This is the same skill, except the schema is the NED's and the values are XPath expressions.

The blueprint verb is "from a provided device config". The task shape that fits this verb: you are given working IOS config (on a device, in a file, or in the task text), and you have to turn it into a reusable template driven by the service model's leaves. The work is mostly mechanical. Most of the risk is in small mismatches: the servicepoint name, namespaces, leaf names, and the context node.

L2 — Mechanics

The capture-and-parameterize pipeline

Step 1–3. "Develop a Simple Service" (NSO 6.5) captures the config and writes the file in one CLI line: show running-config devices device ex1 config sys dns | display xml-template | save packages/dns-config/templates/dns-config-tpl.xml. The page says any .xml file in templates/ is loaded as a template. Its name is the filename without .xml, and that is the name Python passes to Template.apply(). If you are typing config into NSO instead of syncing it, the Templates page shows show configuration | display xml-template in config mode, before you commit. That captures only your uncommitted change, which is often exactly the fragment you want.

Step 4. Find every literal that changes between instances. In the 6.5 example, the device name becomes {/device} and the DNS address becomes {$DNS_IP}, a variable that Python sets with ncs.template.Variables(). Expressions start at the service instance, so /device means "the device leaf of this service instance", not a path from the root of CDB. Literal text and expressions can be mixed in one value, and the result is a string concatenation. This is how you build Loopback{/id}-style names or descriptions.

Step 5. Add servicepoint="…" to the root element. The template-only skeleton generates this. In a python-and-template package, Python applies the template by name, and in the 6.5 example the root carries no servicepoint because the Python callback owns that registration. Know both patterns, and know which one you are in.

Step 6. Compile the YANG (make -C <pkg>/src), then run packages package <pkg> redeploy to reload one package, or packages reload to reload all of them. Package Management says the result is true when the package is up.

L3 — Exam depth

FASTMAP: why "create only" works

The Services page says that at run time NSO "renders the minimum resulting change" for any change to an instance. The Implementing Services page adds the condition: the create logic must give the same device changes for the same inputs. In practice this means no now()-style timestamps, no random values, and no reading of device state that changes between runs. If you break this, every re-deploy shows drift.

Exam-grade details

  • Empty means skipped, not an error. The Templates page says an empty node-set or an empty string means the statement is ignored. A mistyped leaf name like {/devcie} gives no error and simply leaves that part of the config out. Always check with dry-run.
  • Strings, not numbers. {$x > $y} with x='9', y='11' is true, because both are strings. Use number().
  • Context switching. When a key leaf takes its value from a node-set, NSO moves the context to the matching list entry. Inside that subtree, /leaf still resolves from the root node (the service), but relative paths now resolve from the new context. ⚠ unverified — test in lab: exact root vs context behaviour for relative paths after an implicit loop.
  • Multi-device in one instance. If device is a leaf-list, <name>{/device}</name> loops over every value (implicit loop). <?foreach {/device}?>…{.}…<?end?> is the explicit form. Every <?if?> and <?foreach?> needs its own <?end?>.
  • Multi-NED. Only the namespaces the target device advertises are applied. You can also gate blocks with <?if-ned-id …?>. That matters if the task mixes IOS and IOS XR, which is not the tracker's case.
  • One template per servicepoint and callback type. A second template that claims the same servicepoint is a load conflict.
  • Brownfield. If the config already exists on the device, a new service does not own it. re-deploy reconcile (Lifecycle Operations) makes the service take ownership of data that was there before it. commit no-overwrite refuses to overwrite data NSO did not create.

Anatomy

Annotated, not a drill solution. Structure from the NSO 6.5 Templates and Implementing Services pages. The IOS NED inner element names are ⚠ unverified — test in lab. Get them from your own display xml-template output, not from memory.

<!-- templates/loopback-template.xml -->
<config-template xmlns="http://tail-f.com/ns/config/1.0"
                 servicepoint="loopback">        <!-- = ncs:servicepoint in YANG -->
  <devices xmlns="http://tail-f.com/ns/ncs">
    <device tags="nocreate">                     <!-- never create a device -->
      <name>{/device}</name>                     <!-- leaf-list? implicit loop -->
      <config tags="merge">
        <interface xmlns="urn:ios">              <!-- cisco-ios-cli NED ns -->
          <Loopback>                            <!-- ⚠ names from YOUR capture -->
            <name>{/loopback-id}</name>
            <description>svc {/name}</description>   <!-- literal + XPath concat -->
            <ip><address><primary>
              <address>{/ip}</address>
              <mask>{$NETMASK}</mask>             <!-- set in Python cb_create -->
            </primary></address></ip>
          </Loopback>
        </interface>
      </config>
    </device>
  </devices>
</config-template>
# python/<pkg>/main.py (python-and-template) — pattern from "Develop a Simple Service"

vars.add('NETMASK', '255.255.255.255')       # computed value goes here

template.apply('loopback-template', vars)   # file name, no .xml

Speed notes (offline, on the workstation)

  • Don't type XML. Configure once by hand in NSO config mode, run show configuration | display xml-template, and copy. It's faster and the namespaces are correct.
  • | display xpath on show running-config devices device r1 config … gives the exact instance path. Use it to check names before you write expressions.
  • NSO CLI ? and tab completion under devices device r1 config show the NED's real element names, for example whether Loopback's key is name.
  • ncs-make-package --help (⚠ unverified flag) or the man page: --service-skeleton template|python-and-template, --no-test, --build, --dest.
  • packages package X redeploy beats packages reload when you're iterating on one package.
  • Keep commit dry-run outformat native next to the provided config. If the two differ, read them line by line.

Micro-drill (~10 min, paper or netsim)

Requirement. You are given this working config from router r1:

interface Loopback200
 description MGMT-ANCHOR
 ip address 10.200.0.1 255.255.255.255

Build a template-only service lo-anchor with YANG inputs name (key), device (leaf-list, leafref to /ncs:devices/ncs:device/ncs:name), id (uint16), and ip (inet:ipv4-address). The mask is fixed at /32. The description must read MGMT-ANCHOR-<name>. One instance must be able to target two routers.

Reference names/paths. Template root ns http://tail-f.com/ns/config/1.0. Device tree ns http://tail-f.com/ns/ncs. IOS NED ns urn:ios. Skeleton: ncs-make-package --build --no-test --service-skeleton template lo-anchor.

Verify. (1) show packages package lo-anchor oper-status shows up. (2) Instance with device [ r1 r2 ]: commit dry-run outformat native shows the three lines on both devices. (3) After commit, lo-anchor X check-sync returns in-sync true. (4) Delete the instance, dry-run, and confirm only Loopback200 is removed.

Target. NSO 6.5 with netsim cisco-ios-cli devices (not built yet). Until it is, write it on paper and check your work against the Implementing Services examples.

Hint

Capture first: show running-config devices device r1 config interface Loopback 200 | display xml-template. With a leaf-list, <name>{/device}</name> already loops. Concatenate the description as literal text plus {/name}. A fixed mask can stay a literal. Template-only means no $VARS from Python.

Solution (structure; NED element names ⚠ unverified) 
<config-template xmlns="http://tail-f.com/ns/config/1.0" servicepoint="lo-anchor">
  <devices xmlns="http://tail-f.com/ns/ncs">
    <device tags="nocreate">
      <name>{/device}</name>
      <config tags="merge">
        <interface xmlns="urn:ios">
          <Loopback>
            <name>{/id}</name>
            <description>MGMT-ANCHOR-{/name}</description>
            <ip><address><primary>
              <address>{/ip}</address>
              <mask>255.255.255.255</mask>
            </primary></address></ip>
          </Loopback>
        </interface>
      </config>
    </device>
  </devices>
</config-template>

YANG: list lo-anchor { key name; uses ncs:service-data; ncs:servicepoint lo-anchor; … }. This is the 2.9.b pattern. The servicepoint string must be identical in both files.

Recall check

1. Where does a template's servicepoint have to match, and what do you see when it doesn't?

It must match ncs:servicepoint in the service YANG list. On a mismatch the package fails to load: oper-status file-load-error, with error-info giving file:line "Unknown servicepoint: …".

2. Give the one-liner that captures r1's DNS config as a template straight into a package, and the name Python uses to apply it.

show running-config devices device r1 config … | display xml-template | save packages/<pkg>/templates/<name>.xml. Python calls Template(service).apply('<name>', vars) with no .xml.

3. A template uses {/devcie} by mistake. What happens at commit, and how do you find it?

No error. The empty result is ignored, so that statement is skipped and the config is missing. commit dry-run | debug template shows the XPath result.

4. Which tag goes on <device>, why, and what does replace do differently from merge for children?

nocreate, so the service never creates a device entry. merge and nocreate are inherited by children. replace (and create) apply only to the node they are on, and replace replaces that node.

5. (from 2026-11-11) Give the import block's two required pieces for an ACI VRF, the ID format, and the constraint on the ID.

to = an address that matches an existing resource block. id = the full DN, uni/tn-T/ctx-V. The ID must be known at plan time.

6. (from 2026-11-12) Rank the seven AEtest results. What do Errored + Failed and Passed + Skipped roll up to?

Aborted > Errored > Failed > Blocked > Passx > Passed > Skipped. Errored + Failed = Errored. Passed + Skipped = Passed.
