Genie Parse, Learn, Diff

Date Mon 2026-11-09 Blueprint 3.3.b: gather config/operational state via Genie parsers/models Domain 3 (weight not checked) Tier 1 (gap) Read ~18 min Unit 25 of 49

Mental snapshot

  • Genie turns show output into Python dicts. A parser handles one command. An Ops model (learn) runs several commands and merges them into one OS-neutral structure in .info.
  • Same two operations exist in Python (device.parse(), device.learn()) and as CLI (genie parse, genie learn), both driven by the testbed from 3.3.a.
  • genie diff compares two saved snapshots (files or directories) and is the pre/post-change check. It skips volatile keys (counters, timers) by default.
  • Which parser class loads depends on the device's os in the testbed. Wrong os means "could not find parser" or wrong schema.
  • Parsers wrap CLI. They do not make an IOSv speak RESTCONF. Lab split: IOSv/IOSvL2 = CLI parsers only; Cat8000V = CLI parsers too (RESTCONF stays for 2.x tasks); N9Kv = NX-OS parsers.
  • The blueprint verb is gather state. Expect "get this value out of that device and prove it changed", not "write a new parser".

Where this fits

Fundamentals to exam depth

L1: concept

You already read CLI as text. Genie does what TextFSM or regex scripts do, but the parsers are maintained per OS and per command, and each one returns a dict that conforms to a declared schema. Because the schema is fixed, output['platform']['software']['system_version'] works the same way every run, which is what makes a test assert on it. Genie is the library layer on top of pyATS (the framework), and it contains parsers, Ops (operational state), Conf (configure by object), and a harness of triggers and verifications; the introduction ✅ lays these out. Blueprint 3.3.b only needs parsers and Ops.

L2: mechanics

Parse takes one command and returns one dict. Learn takes a feature name, runs the several commands that feature needs, parses each, and merges the results into one structure that the docs describe as the same across operating systems. The Ops page says the learned data lives in .info, a nested dict keyed by item (for example interface name) then property (oper_status, duplex_mode, counters); see the Ops cookbook ✅.

The right parser is chosen by abstraction: libraries are grouped under named tokens such as nxos or iosxe, the lookup tries longer token combinations first and raises LookupError if nothing matches (abstraction concept ✅). The page does not say how the testbed os feeds this; that link is practical knowledge, so treat it as ⚠ unverified: confirm in lab with device.os printed from genie shell.

  • Diff default excludes: parse snapshots use each OS's verification_datafile.yaml, learn snapshots use pts_datafile.yaml. --exclude adds keys; --no-default-exclusion removes the default list and makes the diff noisy.
  • Directory diff matches files by name (for example bgp_nxos_nxos-osv-1_ops.txt), so pre and post must be produced the same way.
  • Python parse extras: parse('all') runs every available parser; fuzzy=True matches several commands with limited regex; raw_data=True exposes raw output via out.raw_output (needs pyATS 22.5+).
  • Limiting learn: Ops accepts a command list or attribute list to cut execution time (Ops cookbook).
  • Learn failures come back as exception objects in learn('all') results, and the CLI reports "Feature not yet developed for this os" for missing models.

Anatomy

Docs are undated and unversioned; the lab pyATS version is unknown. Device names below are placeholders (⚠ unverified: use your testbed names).

# Python: one command -> dict
from pyats.topology import loader
tb  = loader.load('testbed.yaml')
dev = tb.devices['c8kv-1']
dev.connect()
out = dev.parse('show version')          # dict
print(out.keys())                        # discover top-level keys first

# Python: whole feature -> Ops object
snap = dev.learn('ospf')                 # example feature from the docs
print(snap.info)                         # nested dict

# CLI: same via the testbed
genie parse "show version" --testbed-file testbed.yaml --devices c8kv-1 --output pre
genie learn ospf interface --testbed-file testbed.yaml --output pre
# ...change something...
genie learn ospf interface --testbed-file testbed.yaml --output post
genie diff pre post --output diff_out

The docs' only concrete parse key path is NX-OS show version: ['platform']['software']['system_version']. Key paths for IOS and IOS XE commands are ⚠ unverified: print them in lab. genie shell --testbed-file tb.yaml preloads testbed (genie shell ✅), which is the fastest place to explore.

Speed notes

  • The feature browser listing parsers and models is a JavaScript app (Search: Genie feature browser, Available Parsers). Plan for no browser access: use the offline route below.
  • genie --help, then genie parse --help, genie learn --help, genie diff --help list the flags. The top-level help names create, diff, dnac, learn, parse, run, shell.
  • genie shell --testbed-file tb.yaml, then testbed.devices, dev.connect(), help(dev.parse).
  • Find a parser offline: python -c "import genie.libs.parser as p; print(p.__path__)", then grep -rn "show ip interface brief" <path>/ios ⚠ unverified: test in lab. Parser source also shows the schema, so you get key paths without running anything.
  • Print before you assert: import json; print(json.dumps(out, indent=2)).

Recall check

Today

  1. What is the difference in what parse and learn return, and how many commands each runs?
    AnswerParse: one command, one dict. Learn: a feature, several commands, one Ops object with data in .info.
  2. A genie diff shows hundreds of changed lines, mostly counters. Where do the default exclusions come from for parse vs learn snapshots, and which two flags change them?
    AnswerParse: each OS's verification_datafile.yaml. Learn: pts_datafile.yaml. --exclude adds keys; --no-default-exclusion turns the list off (the likely cause of the noise).
  3. genie parse "show interfaces" prints JSON on screen. What do you add to keep files, and which flag stores unparsed output?
    Answer--output DIR writes _parsed.txt and _console.txt. --raw stores device output without parsing.
  4. genie learn says "Feature not yet developed for this os". What does that mean and what is your fallback?
    AnswerNo Ops model for that feature on that OS. Parse the individual show commands instead (or learn a feature that exists); check _exception.txt.

From history

  1. (from 2026-11-03) A connection has no credentials, the device has none, and the testbed has only default. The task enters enable mode. Which credential does the lookup use, and in what order does it search?
    AnswerConnection, then device, then testbed; a missing named credential falls back to default.
  2. (from 2026-11-05) Running your CLI with no arguments crashes with AttributeError on args.func. Why, and what is the fix?
    AnswerIn argparse, subparsers are not required by default. Set required=True on add_subparsers so it prints usage and exits 2.
