NSO 2.9.b — Basic YANG module for a service

Tue 2026-11-17 Blueprint 2.9.b: Basic YANG module (lists, leaf-lists, data types, leafrefs, single-arg when/must) Domain 2 · Infrastructure as Code / programmability (weight ⚠ unverified) Tier 1 gap ~18 min read Unit 30 of 49 Pins: NSO 6.5 · YANG 1.1

Lab status: the tracker still lists NSO as "fully unbuilt". This page is reading plus pen-and-paper modelling until an NSO 6.5 instance exists. 2.9.a (service template) comes next and builds on this module.

Mental snapshot

  • In NSO, the service YANG is the service's API. It defines the inputs the operator types and the rules that reject bad input before any device is touched.
  • Two statements turn an ordinary list into a service: uses ncs:service-data; and ncs:servicepoint "<name>";. The servicepoint name is the glue to the template or Python code.
  • You cannot load raw .yang into NSO. make runs ncsc -c to compile it to .fxs, and then packages reload loads it.
  • Leafref = foreign key. The skeleton's device leaf-list points at /ncs:devices/ncs:device/ncs:name, so only devices NSO already knows are accepted.
  • when makes a node exist only while a condition holds. If the condition goes false, the node is removed. must rejects the commit and shows your error-message.
  • NSO 6.5 supports YANG 1.1 with a few exceptions. For example, a leafref inside a union is not validated, and deref() is a Tail-f extension that --strict-yang flags.

Where this fits

L1 — Concept: you are now the model author

Every YANG page so far (2.4, 2.5, 2.6, 3.5) had you reading someone else's model: you found a path in Cisco-IOS-XE-native and built a payload for it. In 2.9 the roles flip. You write the model, and NSO builds the CLI, NETCONF, RESTCONF and Python access to it for you. The NSO "Implementing Services" guide says the service YANG specifies the inputs the service takes and the validation rules that make sure client values fit what the service expects.

That gives the module two jobs. The first is shape: which inputs exist, how they nest, and which ones identify an instance. The second is guardrails: types, ranges, references and conditions that reject nonsense at commit. If a bad value is blocked in YANG, the template and Python never have to handle it. On the exam, that is the cheapest place to stop errors.

Where the data lives: NSO's CDB is a tree whose schema comes from compiled YANG. A service instance is just another list entry in that tree, next to /devices/device. That is why a leafref from your service to /ncs:devices/ncs:device/ncs:name works. Both nodes are in the same database.

Types you will actually reach for

The NSO YANG chapter uses string, int32, uint16, boolean, empty, enumeration, union and the ietf-inet-types family (inet:ipv4-address, inet:port-number). Restrict them inline with range (numbers) or pattern (strings). The "Implementing Services" example puts a pattern on a target-device leaf. Two NSO-specific notes from the chapter:

  • Union order matters. Put the widest type (usually string) last. Otherwise a value that should match int32 or an enum can match the string branch first.
  • Imports cost a load path. If you use inet: types, the compiled module depends on the inet-types namespace, so its .fxs must be loaded. The chapter suggests --addloadpath ${NCS_DIR}/etc/ncs. With ncs-make-package the generated Makefile normally handles this ⚠ unverified — test in lab.

L3 — Exam detail and NSO-specific traps

"Single-arg when/must"

The blueprint limits 2.9.b to single-arg when/must. A reasonable reading is one condition that tests one other node, for example when "../use-vrf = 'true'"; or must "../mtu <= 9000";. It probably does not mean chained and/or logic across several lists. That reading is an interpretation and not stated anywhere ⚠. Task shapes consistent with the verb "create" include: add a leaf that only appears under a condition, add a constraint with a custom message, and turn a free-text device field into a leafref.

XPath context: where does .. start?

In the NSO chapter's when example, leaf b carries when "../a = 'true'", and a is its sibling. So the path starts at the node that owns the when, and .. steps up to the parent. In the must example, the constraint sits on container interface and names ifType and ifMTU directly, which are its children. Rule of thumb: the context node is the node that carries the statement. RFC 7950 s6.4.1 says the context node depends on where the statement is defined. The per-statement rules (s7.5.3, s7.21.5) could not be read in this run's fetch ⚠ re-read before relying on edge cases, e.g. when on augment/uses.

The most common mistake: putting must "mtu < 9000" on the leaf mtu. From the leaf, mtu looks for a child named mtu, finds nothing, and the empty node-set compares false. Write must ". < 9000" on the leaf, or must "mtu < 9000" on the parent ⚠ behaviour inferred from XPath rules — test in lab.

NSO's YANG 1.1 exceptions (ncsc man page, 6.5)

  • The empty type is not supported in leaf-lists.
  • anydata is not supported.
  • A leafref inside a union is not validated and is treated as a string. Bad references get through silently, so don't use this pattern when you need a guardrail.
  • Submodule scoping follows the older rules: a submodule must include other submodules to see their definitions.

Defaults, mandatory, config false

  • A leaf with a default can be left out, so it is effectively not mandatory. Don't put both mandatory true and a default on one leaf. NSO also has tailf:default-ref for a dynamic default copied from another leaf.
  • config false marks state data. It is returned by get, not get-config, and cannot be written. Service inputs are always config. Operational leaves become relevant with actions in 2.9.c.

Reload behaviour after you change the model

Changing a .fxs triggers a CDB data-model upgrade on packages reload. The 6.5 Package Management guide offers a dry-run option to test the upgrade, and packages reload force to proceed past warnings you have reviewed. In an exam, a typical cause of a failed reload is a model change that conflicts with existing data, such as making a leaf mandatory when instances already exist without it ⚠ example scenario, not from the doc.

Anatomy (pinned to NSO 6.5)

// src/yang/l3-edge.yang  — illustrative, not the drill answer
module l3-edge {
  yang-version 1.1;                         // ⚠ skeleton default not verified
  namespace "http://example.com/l3-edge";   // never change across revisions
  prefix l3e;

  import ietf-inet-types { prefix inet; }   // needs inet-types .fxs on load path
  import tailf-ncs       { prefix ncs; }    // ⚠ import lines as in skeleton: unverified
  import tailf-common    { prefix tailf; }

  typedef vlan-id { type uint16 { range "1..4094"; } }   // reusable guardrail

  list l3-edge {
    key name;                     // instance identity → "l3-edge NAME" in CLI
    uses ncs:service-data;        // makes it a service (with servicepoint)
    ncs:servicepoint l3-edge-servicepoint;   // template must use same name

    leaf name { type string; }

    leaf-list device {            // skeleton pattern
      type leafref { path "/ncs:devices/ncs:device/ncs:name"; }
    }

    leaf vlan { type vlan-id; mandatory true; }
    leaf ipv4 { type inet:ipv4-address; }

    leaf use-vrf  { type boolean; default false; }
    leaf vrf-name {
      when "../use-vrf = 'true'";  // single-arg when, context = vrf-name
      type string;
    }

    leaf mtu {
      type uint16;
      default 1500;
      must ". >= 576" {             // context = the leaf itself
        error-message "mtu must be at least 576";
      }
    }
  }
}

Speed notes (offline on the workstation)

  • ncs-make-package --help ⚠: the skeleton values per the 6.5 man page are java, java-and-template, python, python-and-template and template. Add --no-test to skip the test dir, --dest to pick a directory, and --build to build right after creating.
  • ncsc --list-errors lists all warning/error codes. ncsc --get-info x.fxs shows what a compiled file contains. --strict-yang catches deref().
  • show ncs-state loaded-data-models data-model <name> confirms that NSO loaded your model (CDB and YANG guide).
  • NSO CLI ? and TAB on your own service path prove the model rendered the way you meant: keys, leaf-lists and when-hidden leaves.
  • The skeleton YANG generated by ncs-make-package is the fastest reference for the ncs import and the servicepoint syntax. Copy it instead of writing from memory.
  • pyang -f tree (RFC 8340 notation) still works for a structural sanity check if pyang is installed and tailf-ncs is on its path ⚠ unverified on workstation.

Micro-drill (~10 min, paper or NSO when built)

Requirement. Write loopback-svc.yang for a service list loopback-svc keyed by name, with these leaves:

  • device: a single leaf (not a leaf-list) that must reference a managed device.
  • loopback-id: 0–2147483647, mandatory.
  • ipv4: an IPv4 address.
  • dns-server: a leaf-list of IPv4 addresses.
  • advertise: boolean, default false.
  • ospf-area: uint32. It must only exist when advertise is true.
  • A must check, with error message "loopback 0 is reserved", that rejects loopback-id 0.

Reference names/paths. uses ncs:service-data; · ncs:servicepoint loopback-svc-servicepoint; · /ncs:devices/ncs:device/ncs:name · inet:ipv4-address

Verify. (1) make -C loopback-svc/src compiles cleanly. (2) packages reload returns true. (3) loopback-svc t1 device nope is rejected. (4) ospf-area is not offered by ? until advertise true. (5) loopback-id 0 plus commit dry-run shows your message.

Target. NSO 6.5 (not yet built; netsim or cisco-ios-cli NED to Cat8000V in 2.9.a). Until then, write it on paper and run pyang if available.

Hint

advertise and loopback-id are siblings of the nodes that check them. Put the must on the leaf itself and use . to refer to it. Use ../advertise in the when on ospf-area. A default plus mandatory on one leaf is a contradiction, so don't give loopback-id a default.

Solution (⚠ not compiled — no NSO in lab yet) 
module loopback-svc {
  yang-version 1.1;
  namespace "http://example.com/loopback-svc";
  prefix lbs;
  import ietf-inet-types { prefix inet; }
  import tailf-ncs { prefix ncs; }

  list loopback-svc {
    key name;
    uses ncs:service-data;
    ncs:servicepoint loopback-svc-servicepoint;

    leaf name { type string; }
    leaf device {
      type leafref { path "/ncs:devices/ncs:device/ncs:name"; }
      mandatory true;
    }
    leaf loopback-id {
      type uint32 { range "0..2147483647"; }
      mandatory true;
      must ". != 0" { error-message "loopback 0 is reserved"; }
    }
    leaf ipv4 { type inet:ipv4-address; }
    leaf-list dns-server { type inet:ipv4-address; }
    leaf advertise { type boolean; default false; }
    leaf ospf-area {
      when "../advertise = 'true'";
      type uint32;
    }
  }
}

Alternative for the loopback check: range "1..2147483647" blocks 0 with a generic error. The requirement asks for a custom message, which only must + error-message gives you.

Recall check

  1. Which two statements turn an ordinary YANG list into an NSO service, and what breaks if the template uses a different name for one of them?
    Answeruses ncs:service-data; and ncs:servicepoint "NAME";. If the names don't match, the package fails to load: show packages package NAME oper-status shows file-load-error with error-info "… Unknown servicepoint …".
  2. A leaf with when and a leaf with must both evaluate false. What does the operator see in each case?
    Answerwhen: the node is removed or not available (no error). must: the commit is rejected with the error-message text.
  3. Write the leafref path that picks an IP from the server list of the host chosen in sibling leaf server-host, without deref(). Why avoid deref()?
    Answer/host[name=current()/../server-host]/server/ip. deref() is a Tail-f extension that third-party tools may not understand, and ncsc --strict-yang flags it.
  4. Name two YANG 1.1 features NSO 6.5 does not support, and one that is accepted but not enforced.
    Answerempty type in leaf-lists, and anydata. A leafref inside a union is accepted but not validated (treated as a string).
  5. (from 2026-11-11) You run terraform state rm aci_tenant.prod. What happens to the tenant, and what does the next plan propose?
    AnswerThe tenant stays on the APIC, unmanaged. The next plan proposes creating it again (unless the resource block is removed, or you use the removed { destroy = false } block). Restated from the 11-11 page.
  6. (from 2026-11-12) A testcase's @aetest.setup raises AssertionError. What happens to its tests, and what does the testcase report?
    AnswerIts tests are Blocked. Failed + Blocked rolls up to Failed. Restated from the 11-12 page.
