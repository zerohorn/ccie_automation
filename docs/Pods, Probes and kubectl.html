Pod lifecycle, health checks and kubectl

4.3.b Pod lifecycle (scale up/down, status, logs) · 4.3.c Monitor pods via health checks · 4.3.d Use kubectl. Pins: Kubernetes/kubectl 1.33. The docs fetched today are the main branch (newer than 1.33); version-specific differences are flagged. Domain 4 exam weight: ⚠ unverified.

Mental snapshot

  • A Pod has one phase (Pending, Running, Succeeded, Failed, Unknown) and each container has one state (Waiting, Running, Terminated). CrashLoopBackOff and Terminating are display strings from kubectl, not phases.
  • The kubelet owns restarts. restartPolicy defaults to Always, and Deployments require it.
  • Three probes, three different consequences: startup gates the other two, liveness failure restarts the container, readiness failure only pulls the Pod out of Service endpoints.
  • Scaling is a change to a controller's replica count, not to a Pod. kubectl scale edits the Deployment; the ReplicaSet creates or deletes Pods.
  • Delete is a process: grace period (30 s default), preStop, SIGTERM to PID 1, SIGKILL. Endpoint removal runs in parallel with it.
  • Triage order that works for almost every task: get → describe (events) → logs (and --previous) → exec/debug.

Where this fits

Layer 1: concept

L1 · What a Pod is doing, and who decides

A Pod is a unit the scheduler places on one node. After that, the kubelet on that node does the work: pulls images, starts containers, runs probes, restarts failures. Controllers such as Deployments and ReplicaSets sit above and keep the count right. If you think of the kubelet as a local supervisor (similar to systemd with health checks) and the Deployment as the thing that keeps N supervisors' worth of Pods alive across the cluster, most behavior follows.

Two vocabularies matter. Phase is a coarse Pod summary. Container state is per container. What kubectl get pods shows in the STATUS column is a third thing: a display string that can say CrashLoopBackOff, ImagePullBackOff or Terminating, which do not exist as phases. Read describe for the real state and reason.

Layer 2: mechanics

L2 · Restarts, termination, scaling

Restart policy. Values are Always (default), OnFailure and Never. With Always a container restarts on any exit, including 0. OnFailure restarts only on non-zero exit. Never never restarts. Deployments require Always; Jobs normally use OnFailure or Never. Repeated crashes get an exponential delay of 10 s, 20 s, 40 s and so on, capped at 300 s, and the delay resets after the container has run cleanly for 10 minutes. Some alpha feature gates change those numbers; they are newer than the 1.33 pin and are not exam material.

Termination. On delete the API records a grace period (terminationGracePeriodSeconds, default 30 s). The kubelet runs preStop if defined, then sends SIGTERM to PID 1 of each container, then SIGKILL when time runs out. If preStop is still running at expiry the kubelet grants one 2 s extension. The control plane removes the Pod from EndpointSlices at the same time, so a well-behaved app stops accepting work on SIGTERM and finishes in-flight requests. kubectl delete pod X --grace-period=0 --force deletes the API object immediately and the process may keep running; avoid it unless a task demands it.

Scaling. kubectl scale deployment/NAME --replicas=N changes spec.replicas. The ReplicaSet then creates Pods (which pass through Pending → Running) or picks Pods to delete (which go through the termination sequence above). Autoscaling is a separate object: kubectl autoscale deployment/NAME --min=2 --max=10 creates a HorizontalPodAutoscaler, which needs a working metrics source. Whether the exam cluster has one is ⚠ unverified. If you scale a RollingUpdate Deployment mid-rollout, the extra replicas are shared across the old and new ReplicaSets in proportion to their sizes.

L2 · The three probes

The kubelet runs each probe on its own timer. A probe uses one of four mechanisms: exec (exit 0 is healthy), httpGet (status 200 to 399 is healthy), tcpSocket (connect succeeds) or grpc (standard gRPC health protocol, stable since 1.27). Named ports work for HTTP and TCP probes but not for gRPC.

Probe comparison
ProbeRunsOn failureUse it for
startupOnly at startup, until first successContainer killed, restartPolicy appliesSlow boot; raise its failureThreshold instead of loosening liveness
livenessWhole life, after startup passesKubelet restarts the containerStuck process that will not recover on its own

Layer 3: exam detail

probe-level terminationGracePeriodSecondsPod value (30 s)1Not allowed on readiness probes
  • Pod conditions the kubelet maintains include PodScheduled, Initialized, ContainersReady and Ready. A Pod is Ready only when all containers are ready (and any readiness gates are true).
  • Do not put external dependencies in the liveness check. A database outage then restarts every app Pod and adds load. Put dependency checks in readiness; keep liveness to the app itself.
  • kubectl rollout status deployment/NAME exits 0 on completion and 1 when the progress deadline (default 600 s) is exceeded. Failed shows as Progressing=False with reason ProgressDeadlineExceeded. Kubernetes does not roll back by itself.
  • minReadySeconds (default 0) is how long a new Pod must stay ready before it counts as available. A rollout that never completes often means readiness never passes.
  • Version note: container-level restart rules and in-place restart actions in the lifecycle page are feature-gated and newer than 1.33. Ignore them for this exam.

# Triage chain (commands from the kubectl quick reference)
kubectl get pods                       # STATUS, READY x/y, RESTARTS
kubectl describe pod POD               # State, Last State, Reason, Exit Code, Events
kubectl logs POD [-c CTR] [--previous] # --previous = the crashed instance
kubectl exec -it POD -- sh             # shell, if the image has one
kubectl debug -it POD --image=busybox:1.28 --target=CTR   # ephemeral container

  • kubectl create deployment NAME --image=IMG --dry-run=client -o yaml (the dry-run=client -o yaml form is on the quick reference; the create deployment combination with it is ⚠) gives a manifest skeleton to add probes to.

  • Sorting helps spot crash loops: kubectl get pods --sort-by='.status.containerStatuses[0].restartCount'. Fields and filters: -o jsonpath=..., -o custom-columns=..., --field-selector=status.phase=Running, -l label=value (all on the quick reference).
  • kubectl get pods -w, kubectl wait and logs --tail/--since are not on the fetched quick reference: ⚠ unverified, test in lab.
  • Set the namespace once: kubectl config set-context --current --namespace=NAME. Wrong-namespace mistakes cost more time than any command you forget.
  • source <(kubectl completion bash) enables tab completion in the current shell.

Micro-drill (about 10 min)

Target: a local cluster (k3s or kind on HORNLAB01 per the tracker; no cluster is built yet, so this drill is blocked until one exists). Not a network device task. If you have no cluster today, read the drill and do it when one is up.

Requirement. In namespace probe-lab, run a Deployment web with 3 replicas of busybox:1.28. Each Pod creates /tmp/ready at start and keeps running. A readiness probe uses exec on that file. Put a Service web in front of it. Then:

  1. Scale to 5, then back to 3. Confirm the rollout finishes.
  2. Make exactly one Pod unready without restarting it. Show that it drops out of the Service's endpoints and that the Deployment still reports the other Pods ready.
  3. Add a liveness probe that fails after 30 s on one container so it restarts. Retrieve the log of the killed instance and the event that explains the restart.

Reference fields: spec.replicas, spec.selector.matchLabels, spec.template.spec.containers[].readinessProbe.exec.command, .livenessProbe, .initialDelaySeconds, .periodSeconds, .failureThreshold; Service spec.selector, spec.ports[].port/targetPort.

Verify: kubectl get deploy web (READY x/y, AVAILABLE), kubectl get pods -o wide, kubectl describe pod P (Events, Restart Count), kubectl logs P --previous, endpoints via kubectl get endpointslices ⚠ unverified output wording.

Hint
  • Command: sh -c 'touch /tmp/ready; sleep 3600'. Probe: exec: command: [cat, /tmp/ready].
  • Making a Pod unready without restart: remove the file with kubectl exec P -- rm /tmp/ready (a restart only happens if liveness also fails).
  • For step 3, a second container or a file that disappears after 30 s is the easiest way to make liveness fail on a timer.
Solution (⚠ unverified — test in lab) 
kubectl create namespace probe-lab
kubectl config set-context --current --namespace=probe-lab
cat <<'YAML' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata: {name: web}
spec:
  replicas: 3
  selector: {matchLabels: {app: web}}
  template:
    metadata: {labels: {app: web}}
    spec:
      containers:
      - name: c
        image: busybox:1.28
        command: ["sh","-c","touch /tmp/ready; sleep 3600"]

          exec: {command: ["cat","/tmp/ready"]}

kind: Service
metadata: {name: web}
spec:
  selector: {app: web}
  ports: [{port: 80, targetPort: 80}]

kubectl rollout status deployment/web
kubectl scale deployment/web --replicas=3
POD=$(kubectl get pods -l app=web -o name | head -1)
kubectl exec $POD -- rm /tmp/ready

Recall check

Four on today's topic, two from earlier pages (10-21, 10-22). Answers are collapsed.

  1. A Deployment's Pod shows CrashLoopBackOff and RESTARTS keeps rising. Name the command that shows the output of the crashed instance and the three timing facts about the restart delay.
    Answerkubectl logs POD --previous (add -c for multi-container). Delay doubles from 10 s (10, 20, 40...), caps at 300 s, resets after 10 minutes of clean running.
  2. Your app takes 4 minutes to boot and the liveness probe (period 10, threshold 3) keeps killing it. What do you add, and with which numbers?
    AnswerA startup probe on the same endpoint with periodSeconds: 10 and failureThreshold ≥ 24 (e.g. 30 gives 300 s). Liveness and readiness do not run until startup succeeds; leave liveness settings alone.
  3. A rollout hangs and rollout status returns exit code 1 after a while. What happened and what is the default limit?
    AnswerProgress deadline exceeded (progressDeadlineSeconds default 600 s): the Deployment condition Progressing goes False, reason ProgressDeadlineExceeded. Kubernetes only reports it; roll back with kubectl rollout undo if needed. The new Pods are not becoming available, so check readiness and the image.
  4. Readiness probe fails on one Pod. Is the container restarted? What changes for the Service?
    AnswerNo restart. The Pod IP is removed from matching EndpointSlices; it gets no Service traffic until readiness passes again.
  5. (from 2026-10-22) What does gnxi secure-client-auth add, and what are the secure and insecure default ports?
    AnswerClient certificate checking (mutual TLS). Secure 9339, insecure 50052 (17.5 gNMI guide).
  6. (from 2026-10-21) Default port and controller-side library for the Ansible netconf connection, and what happens if network_os is unset?
    AnswerPort 830, ncclient. Unset network_os makes the plugin try to guess it and fall back to the default behavior.
