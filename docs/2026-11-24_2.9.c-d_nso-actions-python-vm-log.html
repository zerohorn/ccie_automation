NSO Actions and Logs

Lab status: NSO is still unbuilt (tracker). This page is reading plus a paper drill until an NSO 6.5 local install exists.

Mental snapshot

  • An action is an on-demand operation modelled in YANG, with input and output. It does not create configuration. NSO uses actions for tests, checks and one-off tasks; services handle configuration.
  • Two families matter for 2.9.c. Built-in actions ship with NSO: devices device X connect, ping, check-sync, compare-config, and per-service check-sync, deep-check-sync, get-modifications, re-deploy dry-run. Custom actions are ones you write: YANG action + tailf:actionpoint + a Python ncs.dp.Action class.
  • Custom actions use the same callback pattern as services. The actionpoint name in YANG must equal the first argument of register_action() in Application.setup().
  • The trans handed to cb_action is read-only. An action reads CDB and the device, then writes to output.
  • Python package code runs in an NSO-managed Python VM. self.log output goes to logs/ncs-python-vm-<pkg>.log. Stdout and Python compile errors go to the shared logs/ncs-python-vm.log.
  • Default Python VM log level is info. python-vm logging level level-debug raises it for every VM. vm-levels <pkg> raises one VM and wins over the global setting.
  • The cisco-ios-cli NED is Java. Its device traffic shows in the NED trace file and ncs-java-vm.log, not in the Python VM log.

Where this fits

Fundamentals to exam depth

L1: concept — what an action is, and why NSO has them

You already know NETCONF RPCs: a named operation with input and output, separate from the datastore. YANG 1.1 adds the action statement, which is an RPC bound to a node in the data tree. RFC 7950 section 7.15 ✅ states the difference: an action is tied to a datastore node, an rpc is not. It also bars actions at the top level of a module or under a keyless list, which is why NSO examples wrap them in a container or put them inside a list entry.

NSO's guide frames the split between services and actions plainly. Services own configuration through FASTMAP. Actions cover the rest: verification, one-time tasks and tests. It names a self-test action inside a service package as a common case (Applications in NSO ✅). For 2.9.c, "verify operational status" means read-only questions. Can NSO reach the device? Does NSO's copy match the device? Is the service's config still there? What does the device report right now?

2.9.d is the other half. Your service and action code runs in a separate Python process. When it fails, the CLI often shows little, and the details are in the Python VM log. Knowing which file to open, and how to make it verbose, is the skill.

L2: mechanics — wiring a custom action

Four pieces have to line up. Each one maps to something you already did in 2.9.a and 2.9.b:

  1. YANG: an action with tailf:actionpoint NAME, an input and an output. YANG 1.1 is required for action; YANG 1.0 models use the older tailf:action extension.
  2. Registration: package-meta-data.xml names a python-class-name. NSO starts a Python VM, creates that ncs.application.Application subclass and calls setup(), where you call self.register_action('NAME', MyAction).
  3. Callback: MyAction(ncs.dp.Action) implements cb_action(self, uinfo, name, kp, input, output, trans) under the @Action.action decorator. The decorator turns input and output into Maagic nodes. kp is the keypath of the node the action was called on, so a list-level action knows which instance it serves.
  4. Compile and load: YANG changes need make -C packages/<pkg>/src and packages reload. Code-only or template-only changes can use packages package <pkg> redeploy.

You can also call actions from Python. The Python API overview shows root.devices.check_sync() and input objects built with get_input(), then called like a function (Python API Overview ✅). That is how a custom action calls built-in actions such as connect, sync_from, or the NED's live-status exec any. Hyphens become underscores in Maagic. When two loaded modules use the same name, a prefix__name form picks one.

The Python levels map to the standard library: level-critical down to level-debug, matching CRITICAL 50 to DEBUG 10 (Python logging levels ✅). Messages below the configured level are dropped, so self.log.debug() writes nothing at the default info level. Operational state is under python-vm status: start lists each class NSO tried to start and whether it worked, with error-info. current lists the threads that are running now (NSO Python VM ✅).

Timeouts finish the picture. /ncs-config/api/action-timeout defaults to PT240S (ncs.conf ✅). When it fires, NSO kills only the worker socket for that call and invokes cb_abort() if you defined one. The Python VM is not restarted. Without cb_abort, the user has to wait for the callback to finish before running the action again. The other API timeouts are different: when query-timeout, connect-timeout or new-session-timeout fires, NSO closes the socket and the VM exits. python-vm/start-timeout (PT30S) bounds startup, and auto-restart (true) brings a VM back after it exits.

Anatomy

Pinned to NSO 6.5 docs. Snippets follow the guide's count-devices and double examples; lines marked ⚠ are not on a fetched page.

// src/yang/svc-check.yang
module svc-check {
  yang-version 1.1;                       // 'action' needs YANG 1.1
  namespace "urn:hornlab:svc-check";
  prefix svc-check;
  import tailf-common { prefix tailf; }
  import tailf-ncs    { prefix ncs; }

  container svc-check {                   // actions can't be top-level (RFC 7950 s7.15)
    action reach {
      tailf:actionpoint reach-action;     // NAME #1
      input  { leaf device { type leafref { path "/ncs:devices/ncs:device/ncs:name"; } } }
      output { leaf result { type boolean; } leaf info { type string; } }
    }
  }
}
# python/svc_check/main.py
import ncs
from ncs.dp import Action

class Reach(Action):
    @Action.action
    def cb_action(self, uinfo, name, kp, input, output, trans):
        self.log.info('action ', name, ' device ', input.device)   # ncs.log.Log joins *args
        root = ncs.maagic.get_root(trans)                           # read-only transaction
        res = root.devices.device[input.device].connect()          # ⚠ connect() output leaf names
        output.result = res.result
        output.info = res.info
        self.log.debug('connect info: ', res.info)                 # dropped at default level-info

class Main(ncs.application.Application):
    def setup(self):
        self.log.info('Main RUNNING')
        self.register_action('reach-action', Reach)                 # NAME #2 == NAME #1
    def teardown(self):
        self.log.info('Main FINISHED')
admin@ncs# svc-check reach device r1                 ⚠ output shape
admin@ncs# show python-vm status start
admin@ncs# config
admin@ncs(config)# python-vm logging level level-debug    # all VMs
admin@ncs(config)# commit
$ tail -f logs/ncs-python-vm-svc-check.log

Speed notes (offline on the workstation)

  • ncs-make-package --service-skeleton python --action-example mypkg gives you correct YANG, Python and package-meta-data.xml to copy from. Diff it against your package when wiring breaks.
  • NSO CLI: type devices device r1 then ? to list device actions; <svc> <key> ? lists service actions; show python-vm ? and python-vm logging ? in config mode show the knobs.
  • man ncs.conf (System Management points there), then search /action-timeout or /python-vm for defaults.
  • tail -f logs/ncs-python-vm-<pkg>.log in a second terminal while you run the action. grep -n Traceback logs/ncs-python-vm*.log finds crashes fast.
  • ncs --status | less shows loaded packages and daemon state. show packages package <pkg> oper-status narrows to one package.
  • Python API help: source $NCS_DIR/ncsrc, then python3 -c "import ncs.dp; help(ncs.dp.Action)" ⚠ unverified: test in lab.

Micro-drill (about 10 min, paper until NSO is built)

Target: NSO 6.5 local install with one cisco-ios-cli device r1 (netsim or IOSv 15.9; IOSv may need legacy SSH algorithms ⚠). Service from last week's drill: list loopback with leafs device (leafref), id (uint16), ip.

Requirement:

  1. Add a self-test action to each loopback service instance. Output: success (boolean) and message (string).
  2. The action runs show ip interface brief on the instance's device and reports success only when Loopback<id> is present and up.
  3. Log one info line per call (instance, device, result) and the raw device output at debug.
  4. Show the debug line appears for this package only, without raising every VM.

Reference: tailf:actionpoint, register_action(), @Action.action, cb_action(self, uinfo, name, kp, input, output, trans), ncs.maagic.get_node(), live-status exec any, python-vm logging vm-levels.

Verify: loopback L10 self-test returns success true. Shut Loopback10 on r1 and re-run: success false. The logs/ncs-python-vm-loopback.log file shows the info line at default level and the raw output only after the per-VM debug setting. show python-vm status current lists the package.

Hint

Put the action inside the service list, after uses ncs:service-data. kp is the keypath of that list entry, so turn it into the service node, read device and id, then call the NED's exec action through root.devices.device[...]. Build the live-status input with get_input() and call the action object with it. You need yang-version 1.1 at the top of the module.

Solution 
// add inside: list loopback { ... uses ncs:service-data; ncs:servicepoint loopback-servicepoint; ...
    action self-test {
      tailf:actionpoint loopback-self-test;
      output {
        leaf success { type boolean; }
        leaf message { type string; }
      }
    }
# python/loopback/main.py (additions)
from ncs.dp import Action

class SelfTest(Action):
    @Action.action
    def cb_action(self, uinfo, name, kp, input, output, trans):
        svc  = ncs.maagic.get_node(trans, kp)              # ⚠ kp accepted directly
        root = ncs.maagic.get_root(trans)
        ex   = root.devices.device[svc.device].live_status.ios_stats__exec.any   # ⚠ path/prefix
        inp  = ex.get_input()
        inp.args = ['show ip interface brief']             # ⚠ input leaf name 'args'
        raw  = ex(inp).result                              # ⚠ output leaf name 'result'
        self.log.debug('raw output: ', raw)
        want = 'Loopback%d' % svc.id
        line = next((l for l in raw.splitlines() if l.startswith(want)), '')
        output.success = bool(line) and line.split()[-1] == 'up'    # ⚠ column layout
        output.message = line or want + ' not found'
        self.log.info('self-test ', svc.name, ' on ', svc.device, ': ', output.success)

class Main(ncs.application.Application):
    def setup(self):
        self.register_service('loopback-servicepoint', ServiceCallbacks)
        self.register_action('loopback-self-test', SelfTest)

admin@ncs# config

Recall check

Today

  1. For a custom action, which two names must match, and where does each live? They match but the action still fails. What do you check first?
    AnswerThe tailf:actionpoint name in YANG and the first argument of register_action() in Application.setup(). Next, show python-vm status start for the class status and error-info, and logs/ncs-python-vm.log for a traceback that stopped setup(). Then package oper-status.
  2. What does each compare: devices device r1 check-sync, service check-sync, service deep-check-sync?
    AnswerDevice: the device's config signature vs NSO's stored copy (may be unsupported for some NEDs). Service check-sync: FASTMAP output vs CDB, with no device contact. Deep: the service's forward diff vs config fetched from the devices it touched. Only deep catches an out-of-band change to service config.
  3. Where do self.log.debug(), print() and a SyntaxError in main.py each end up, and what must change before you see the debug line?
    AnswerDebug: logs/ncs-python-vm-<pkg>.log, but only after python-vm logging level level-debug or a vm-levels entry for that VM (default is info). print/stdout: shared logs/ncs-python-vm.log. SyntaxError: ncs-python-vm.log, and packages reload reports result false with the error.
  4. An action that runs live-status exec any against a slow device fails after about four minutes. Which setting and default apply, what does NSO do, and what does cb_abort change?
    Answer/ncs-config/api/action-timeout, default PT240S. NSO closes that action's worker socket; the Python VM is not restarted. With cb_abort() defined, NSO calls it and releases the user's session for that action. Without it, the user waits for the callback to finish.
