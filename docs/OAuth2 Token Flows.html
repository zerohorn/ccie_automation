Mental snapshot

  • OAuth2 is a delegation protocol: a client gets a short-lived access token from an authorization server, then presents it to a resource server. The token is not a login; it is a scoped, expiring capability.
  • For a human consenting in a browser (Webex integration, Meraki integration), the grant is authorization code, plus PKCE for any client that cannot hold a secret.
  • No browser (appliance, CLI on a jump host): device grant. No human at all: client credentials or a vendor's service-app equivalent.
  • Password grant (ROPC) is still in RFC 6749 and in the FastAPI tutorial, but RFC 9700 says not to use it.
  • The access token goes in Authorization: Bearer. Query-string tokens are discouraged and RFC 9700 prohibits them in clients.
  • Refresh tokens can rotate. Meraki revokes the old one on every refresh, so a script that does not persist the new one breaks on the second run.
  • Most exam failures here are plumbing: redirect URI mismatch, expired code, wrong header, missing scope.

Where this fits

Fundamentals to exam depth

L1: Concept

Four roles. The resource owner is the person. The client is your script or app. The authorization server issues tokens. The resource server is the API. RFC 6749 defines four grant types: authorization code, implicit, resource-owner password credentials, and client credentials, and allows extension grants. The device grant (RFC 8628 ✅) is one such extension.

You pick the grant by who is present. A person who can open a browser: authorization code. A person with no browser on the device: device grant. No person: client credentials. You are the architect, so think of it as choosing an authentication mode by what the client can prove and who can consent.

L2: Mechanics of authorization code with PKCE

The client sends the user's browser to the authorize endpoint with response_type=code, client_id, redirect_uri, scope and a random state (RFC 6749 s4.1.1; state is the CSRF check). The server authenticates the user, shows consent, and redirects back with a single-use code and your state. The RFC recommends the code expire within 10 minutes; Meraki states 10 minutes for its access grant.

The client then POSTs the code to the token endpoint. For a confidential client that includes client authentication. The response is JSON: access_token and token_type are required, expires_in is recommended, refresh_token is optional (RFC 6749 s5.1). Failures return 400 with invalid_grant, invalid_client, invalid_request, unauthorized_client, unsupported_grant_type or invalid_scope (s5.2).

PKCE (RFC 7636 ✅) binds the code to the client that asked for it. The client invents a code_verifier of 43 to 128 unreserved characters, sends only its S256 hash as code_challenge on the authorize request, and reveals the verifier on the token request. If the server's hash of the verifier does not match, you get invalid_grant. A stolen code is useless without the verifier.

L3: Exam detail

Vendor shapes you can verify. Webex integrations: authorize at /v1/authorize on webexapis.com with response_type=code, scope, state, client_id, redirect_uri; token POST to /v1/access_token with a URL-encoded body including client_secret. The sample response carries expires_in (about 14 days in the example) and refresh_token_expires_in (about 90 days), and the refresh lifetime renews on use. Meraki: authorize, token and revoke endpoints on as.meraki.com, client_id and client_secret sent as HTTP Basic on token requests, access token valid 60 minutes, refresh token revoked after 90 days idle, and each refresh returns a new refresh token and revokes the old. Scope strings are colon-delimited, such as dashboard:iam:config:read.

Sending the token. The Authorization header with the Bearer scheme is the supported method. RFC 6750 ✅ allows a form body and a query parameter but discourages both; RFC 9700 s4.3.2 prohibits clients from using the query form. On failure the resource server answers with a WWW-Authenticate: Bearer challenge: invalid_token is 401, insufficient_scope is 403, invalid_request is usually 400. The Meraki Authentication page ✅ says v1 uses the standard header and warns that curl, Postman or PowerShell can drop it on a redirect, which surfaces as "Missing API key".

Security BCP. RFC 9700 requires exact string matching of redirect URIs (localhost port may vary for native apps), requires PKCE for public clients and recommends it for confidential ones, discourages implicit, forbids ROPC, and requires refresh tokens for public clients to be sender-constrained or rotated.

PKCE pair in Python 3.13

import secrets, hashlib, base64
verifier  = secrets.token_urlsafe(32)          # 43 chars; RFC 7636 allows 43-128  ⚠ length unverified
digest    = hashlib.sha256(verifier.encode("ascii")).digest()
challenge = base64.urlsafe_b64encode(digest).rstrip(b"=").decode()   # ⚠ padding strip unverified here
state     = secrets.token_urlsafe(16)

secrets is the right module for these values; the Python docs ✅ say to prefer it over random for security tokens, and offer compare_digest for constant-time checks, which is what you want for the state comparison.

Micro-drill (about 10 min)

Target: Candidate Workstation only. No device, no live vendor account. You build both ends of a small flow and test with curl.

Requirement.

  • Part A: a script that prints an authorize URL carrying response_type, client_id, redirect_uri, scope, state, code_challenge (S256) and prints the verifier it must keep.
  • Part B: a FastAPI service with a /token endpoint that reads form fields, returns JSON with access_token and token_type of bearer, signs a JWT HS256 with 30 minute expiry, and a /users/me endpoint that requires it.

Reference names. secrets.token_urlsafe, hashlib.sha256, base64.urlsafe_b64encode; OAuth2PasswordBearer(tokenUrl="token"), OAuth2PasswordRequestForm, jwt.encode, jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM]), claim sub, claim exp.

Verify.

  • curl -i localhost:8000/users/me returns 401 and a WWW-Authenticate: Bearer header.
  • curl -d username=x -d password=y localhost:8000/token (form-encoded) returns the token JSON for a valid user. The same call with a JSON body fails.
  • curl -H "Authorization: Bearer $T" localhost:8000/users/me returns the user.
  • Edit one character of $T and confirm 401.
Hint

The form-field names are fixed by the spec: username and password. tokenUrl only documents the endpoint; you still have to write it. Put the user id in sub, and set exp as a UTC datetime. Remember this is the password grant, which is here only because it is the cheapest local exercise.

print("https://auth.example.invalid/authorize?"+q); print("verifier:", v)   # placeholder host

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="token")
@app.post("/token")
async def login(f: Annotated[OAuth2PasswordRequestForm, Depends()]):
    # check user, then:
    tok = jwt.encode({"sub": f.username, "exp": datetime.now(timezone.utc)+timedelta(minutes=30)},

Recall check

1. A token POST returns invalid_grant. List three causes you can check from the client side.

Code expired or reused; redirect_uri not identical to the authorize request; PKCE verifier does not hash to the stored challenge.

2. Meraki rotates refresh tokens. What does your script do after every refresh?

Stores the new refresh token (the old one is revoked) before it relies on the new access token.

3. Name the HTTP status and challenge error for an expired token versus a token lacking the scope.

401 invalid_token versus 403 insufficient_scope, both in WWW-Authenticate: Bearer (RFC 6750 s3.1).

4. Which grant would you pick for a CLI on a host with no browser, and what does the polling loop do on slow_down?

Device grant. Keep polling, but lengthen the interval by 5 seconds. authorization_pending continues; access_denied and expired_token stop.

5. (from 2026-10-27) You want 201 on create and a response that omits password. Which two arguments do you use, and which wins if you give both a model and an annotation?

status_code=201 plus response_model (or return annotation). response_model wins.

6. (from 2026-10-29) The CSR carried a SAN but the issued cert has none. Why, and name two fixes.

openssl x509 ignores request extensions by default. Use -extfile/-extensions, or -copy_extensions copy.
