Mental snapshot

  • Sort every failure into one of four places before touching anything: pipeline never created, job never scheduled, job ran and failed, or job passed but the merge is blocked.
  • The three blueprint phrases map to those places. Pipeline issues: creation and scheduling. Code failures: the script and its exit codes. Tool incompatibility: image, runner, and version drift.
  • A pipeline that shows yaml invalid never runs. The pipeline editor and CI Lint are your first tools, not the job log.
  • Jobs that don't appear are almost always rules or workflow:rules. Do not mix rules with only/except.
  • Reruns reuse the config from when the pipeline was created. Edit the YAML, then start a new pipeline.
  • Debug output is dangerous: export and CI_DEBUG_TRACE expose secret values in the log.
  • Pin images and tool versions. Unpinned images are the main source of "worked yesterday" failures.

Where this fits

Fundamentals to exam depth

L1: concept

A pipeline is a set of jobs created from .gitlab-ci.yml when an event happens (push, merge request, schedule). A runner picks up each job, starts an executor (often a Docker container from the job's image), and runs the script. The job passes if the script's last command, or the first failing one, exits 0.

You know this from network troubleshooting: isolate the layer, then test it. The layers here are config parsing, job selection, execution, and result handling. A failure at one layer looks like silence at the next. A rules mistake produces no job, so there is no log to read. That is why "check the job log" fails as a first reflex.

L2: mechanics

Config layer. Syntax problems show a yaml invalid badge and the pipeline does not run. The pipeline editor validates continuously against the schema. Its Validate tab simulates a push pipeline to expose wrong rules and needs logic. Its Full configuration tab shows include content merged and extends resolved, which is the view you want when a job is missing. Includes have their own limits: variables defined in jobs or in a global variables block can't be used in include, and a loop of includes ends in a 150-nested-include error. See the include page.

Scheduling layer. rules are evaluated in order and the first match wins. If none match, the job is not added. This surprises people on branches with an open merge request: a job with a rule such as when: always and no if runs in both the branch pipeline and the merge request pipeline, giving two pipelines per push. GitLab warns about it with "Job may allow multiple pipelines to run for a single action". The fix is workflow:rules or tighter job rules. See job rules and merge request pipeline troubleshooting. A related trap: changes is always true in scheduled pipelines and for new branches or tags, so a job you expected to skip runs anyway.

Runner layer. A job can sit pending with nothing wrong in your YAML. GitLab drops pending jobs after about an hour when no runner matches, running jobs with no updates after about 30 minutes, and running jobs past their timeout plus 15 minutes. Check failure_reason and add retry:when for transient causes. Runner-side oddities such as "Job failed (system failure): preparing environment" usually trace to a shell profile script that fails on the runner host, or SELinux. See the runner FAQ.

Execution layer (code failures). Three YAML-in-shell traps cover many script failures. An unquoted colon in a script line gives "Syntax is incorrect". A chained && line can return 0 even when a command in it failed, so the job keeps going; wrap the whole line in parentheses. A folded block (- >) with extra indentation keeps line breaks, and the shell then runs each line separately, producing "command not found" on what was meant to be arguments. Details on the script troubleshooting page.

Variables. A job variable with the same name as a default variable overrides it, so MY_VAR: $MY_VAR expands to empty. A trailing slash in a path variable gives double slashes after expansion. Large variable sets can hit "argument list too long"; use File-type variables. See variables troubleshooting.

L3: exam detail

Tool incompatibility is the least defined of the three blueprint phrases, so expect it to show up as version drift. Examples with a source behind them:

  • ansible-core 2.19 supports Python 3.11 to 3.13 on the control node and 3.8 to 3.13 on targets. A job image with Python outside that range on the control side fails before your playbook runs. Your Python 3.13 pin is inside the range. (release matrix)
  • Docker-in-Docker from v19.03 starts with TLS. Jobs that talk to tcp://docker:2375 get "Cannot connect to the Docker daemon". If the host runs Docker Engine 20.10 or newer and the docker:dind service is older, you get a cgroups mountpoint error. (Docker build troubleshooting)
  • A service image name that includes a registry hostname changes the derived hostname, so docker no longer resolves. Add alias: docker.
  • Private CA certificates (a TLS-inspecting proxy, for example) must be present in both the build container and the dind service container, or you get an x509 unknown authority error.
  • Config is read at pipeline creation. A rerun of an old pipeline will not pick up your YAML fix, including fixes in included files.

Anatomy

Short snippets of the failing shape and the repaired shape. These are pieces, not the drill answer.

# 1. Debug trace for one job (shows ALL variables in the log; restrict log access)
job:
  variables:
    CI_DEBUG_TRACE: "true"

# 2. Colon in a script line: quote the whole line
script:
  - 'echo "Result: done"'

# 3. Self-reference empties the variable
variables:
  API_URL: $API_URL        # expands to empty
  API_URL_FROM_DEFAULTS: $API_URL   # rename the target instead (pattern from the variables page)

# 4. Service name with a registry host: restore the hostname
services:
  - name: registry.example.internal/mirror/docker:dind   # hypothetical path
    alias: docker
# 5. Duplicate pipeline guard (common pattern)
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS
      when: never
    - if: $CI_COMMIT_BRANCH

Speed notes

  • Reproduce the job's commands locally: run the job's image on a machine and execute the script there (the debugging page describes this). ⚠ unverified — whether Docker or a container runtime exists on the Candidate Workstation; test in lab.
  • For Ansible jobs: ansible-playbook --syntax-check, ansible-doc -l | grep netcommon, and ansible --version to print the Python and core versions. ⚠ unverified — run on the workstation to confirm.
  • Put python3 --version, ansible --version, and terraform version in before_script so version drift is visible in every log.
  • Use --verbose over --silent for tools in jobs, and save reports as artifacts. Never store secrets in artifacts.
  • Add a blank DEBUG_VARS style flag you set on manual runs to turn on extra output without editing the file.
  • Use workflow:name so pipeline types are labeled in the list and you can see which kind ran.
  • Bare export in a script lists all variables; masked values show as masked, but the list is still sensitive.

Micro-drill (about 10 min)

Requirement. The pipeline below should lint, run an Ansible check against Cat8000V, and publish a report. It misbehaves in five ways. Name each fault and its fix without running anything first.

Target device. Cat8000V (IOS XE 17.16) for the Ansible step; no cisco.ios collection on the workstation, so the playbook only uses netcommon modules. This is a reading drill; no device access needed.

stages: [lint, test, report]

lint:
  stage: lint
  script:
    - echo "Result: $(ansible-lint site.yml)"

check:
  stage: test
  variables:
    RESTCONF_HOST: $RESTCONF_HOST
  script:
    - ansible-playbook -i inv.yml site.yml --check && echo checked
  artifacts:
    paths: [reports/check.xml]

report:
  stage: report
  script: [echo publish]
  rules:
    - when: always

Reference. Keywords: script, variables, artifacts:paths, rules, workflow:rules. Pages: script troubleshooting, variables troubleshooting, artifacts troubleshooting, job rules.

Verification. Paste the file into the pipeline editor or CI Lint. Check the Validate tab for the pipelines created on a push to an MR branch. After fixes, confirm in the job log that the artifact upload prints no "No files to upload" error.

Hint

One fault each in: YAML parsing of a script line, a variable assignment, a shell chain, a file path expectation, and rule scope.

Solution
  • echo "Result: ..." unquoted in YAML: the colon-space breaks parsing. Wrap the whole line in single quotes.
  • RESTCONF_HOST: $RESTCONF_HOST: same-name self-assignment expands empty. Use the default variable directly or assign to a new name.
  • ... --check && echo checked: a chained line can mask a failure. Wrap the line in parentheses so the job fails when a command fails.
  • reports/check.xml is never written by the script: the artifact upload reports no files. Create it or fix the path.
  • rules: - when: always with no if: runs in branch and MR pipelines. Add workflow:rules or an if.

⚠ unverified — whether --check works with the restconf modules in lab; the faults above are YAML and GitLab behavior, not Ansible behavior.

Recall check

Today's topic

1. A push to an MR branch creates two pipelines. Name the cause in one line and two ways to fix it.

A job rule has when with no if, so it runs in both the branch and MR pipelines. Fix with workflow:rules that pick one pipeline type, or add an if to the job rules.

2. You fixed the YAML but rerunning the failed job still fails the old way. Why?

Reruns reuse the config captured when the pipeline was created, including included files. Start a new pipeline.

3. A job needs docker builds. The log says it cannot connect to tcp://docker:2375. What changed in Docker-in-Docker, and what second error appears if the dind image is too old for the host?

From v19.03 dind starts with TLS, so the plain port fails. A dind image older than 20.10 on a 20.10+ host gives a cgroups mountpoint error; use a newer dind tag.

4. A script line - echo "Status: ok" breaks the whole file, and a different line using && lets a failing job continue. Explain each and the fix.

The colon-space is read as a YAML key separator; quote the whole line in single quotes. The chained line can return 0 despite a failure; wrap the whole line in parentheses.

From earlier days

5. (from 2026-10-01) Why does a NETCONF dial-in subscription disappear after a switchover, and where would you see (or not see) it in the router config?

Dynamic dial-in subscriptions live in device state, not the configuration, so they don't survive a switchover and do not appear in running-config; check the telemetry subscription show output. ⚠ restated from the 2026-10-01 page, not re-verified today.

6. (from 2026-10-05) A GraphQL call returns HTTP 200 and data.field is null. Where do you look and why can the status be 200?

Look at the errors array in the response body. GraphQL can return 200 with partial data and per-field errors, so the status code does not tell you the field succeeded. ⚠ restated from the 2026-10-05 page.
