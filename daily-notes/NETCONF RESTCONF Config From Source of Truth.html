2.6 Configure devices via NETCONF/RESTCONF using YANG analysis tools, driven by a source of truth

Thursday 2026-10-15Domain 2 (weight not verified ⚠)Read time ~18 minBlueprint verb: Build

Mental snapshot

  • 2.4 was "write one payload from YANG". 2.6 is "generate many payloads from data, push them, prove the result". The input is a data file, not you at a keyboard.
  • The source of truth (SoT) holds intent in a neutral shape (YAML in host_vars, a database, NSO). The YANG model fixes the shape the device accepts. Your job is the mapping between them.
  • YANG analysis tools answer three questions before you push: what is the path, what are the keys and types, what is config versus state. pyang -f tree and YANG Suite are the two named here.
  • Render the payload as data (a dict, then to_json), not as text templated by hand. Types stay correct and quoting problems disappear.
  • RESTCONF applies each request on its own. NETCONF with the candidate datastore lets you stage, lock, commit, or roll back. Choose by how much transaction control the task wants.
  • A push is not done until you read back and compare to the SoT. "HTTP 204" proves the device accepted it, not that it matches intent.
  • Lab reminder: only Cat8000V has NETCONF/RESTCONF, and the workstation has no cisco.ios collection. Everything below uses ansible.netcommon.

Where this fits

Fundamentals to exam depth

L1 Concept. A source of truth is the one place that says what the network should look like. A device CLI is a result, not the truth. Automation reads the SoT, turns each record into the structure the device's YANG model defines, and sends it with NETCONF or RESTCONF. The YANG model is the contract: it names every node, its type, which nodes are keys, and which nodes are writable. Analysis tools exist so you read that contract in seconds instead of guessing at payloads.
L2 Mechanics.

Read the model. pyang -f tree prints the schema as a tree in the notation from RFC 8340. rw is configuration, ro is state, ? is optional, * is a list or leaf-list, [keys] follow a list name, and ! marks a presence container. Anything ro must never appear in a payload. Every list key must.

Map the SoT. Each key in the tree becomes a field your data must carry. A list key also becomes part of the RESTCONF URI as list=value; several keys are comma-separated in key order, and reserved characters are percent-encoded (RFC 8040 section 3.5.3). The module prefix appears on the first node and wherever the module changes.

Render. Build a dict in the model's shape in Jinja or Python, then serialize with to_json. Hand-templating JSON text fails on booleans, quotes and trailing commas.

Push. RESTCONF methods per the IOS XE guide: PUT creates or replaces, PATCH updates, POST creates or invokes an operation, DELETE removes. The guide's logging examples return 201 for POST and 204 for PUT, PATCH and DELETE. NETCONF edit-config against the candidate stages the change; commit copies candidate to running; discard reverts candidate to running.

Verify. Read the same path back (restconf_get or netconf_get), then compare the result with the dict you sent. Compare parsed data, not text.

L3 Exam detail.
  • Candidate on IOS XE. Enable with netconf-yang feature candidate-datastore. Once enabled, running is not writable through NETCONF. The candidate is shared, so lock it before editing (IOS XE 17.5 NETCONF guide). Confirm with show netconf-yang datastores.
  • netconf_config defaults. target: auto uses candidate and falls back to running. commit: true, lock: always, validate: false, default_operation is merge, replace or none, with no listed default. Format is guessed if unset and falls back to XML.
  • Per-node operations. The module's own example removes an NTP server with operation="remove" on the element. That is how you delete one list entry inside a merge.
  • restconf_config defaults. method: post, format: json, path required, content required unless method is delete. Default POST means rerunning a create fails if the resource exists. Set method: put or patch for repeatable pushes.
  • Check mode and diff. Neither module page documents check mode. netconf_config returns a diff key when diff is on. Plan on your own compare step. ⚠ unverified: check-mode behavior on 8.4.0, test in lab
  • YANG Patch. RFC 8072 defines an ordered list of edits applied atomically with application/yang-patch+json. The IOS XE 17.5 RESTCONF page lists YANG Patch in its restrictions and also in its feature history (17.1.1). Do not rely on it on the lab device without testing.

Anatomy

Short pieces, pinned to what the sources show. They are not a full solution to the drill.

1. Read the model (shape from RFC 8340's example)

+--rw interfaces
   +--rw interface* [name]
      +--rw name           string
      +--rw description?   string
      +--rw type           identityref
      +--rw enabled?       boolean

interface* is a list with key name. type has no ?, so it is mandatory in the payload. Your SoT record needs name and type; description and enabled are optional.

2. Source of truth record

# host_vars/r1.yml
loopbacks:
  - { name: Loopback100, description: "SoT: mgmt anchor", enabled: true, ip: 10.100.0.1, mask: 255.255.255.255 }
  - { name: Loopback101, description: "SoT: test",        enabled: false, ip: 10.100.0.2, mask: 255.255.255.255 }

Ansible reads host_vars/<host> files in YAML or JSON and merges them with group variables; group_vars or host_vars next to the playbook override those next to the inventory.

3. Connection variables for RESTCONF

# group_vars/cat8k.yml
ansible_connection: ansible.netcommon.httpapi
ansible_network_os: ansible.netcommon.restconf
ansible_httpapi_use_ssl: true          # ⚠ unverified on the fetched pages
ansible_httpapi_validate_certs: false  # ⚠ lab self-signed cert; unverified name
# ansible_httpapi_restconf_root: /restconf   (default per the httpapi plugin page)

4. Push with RESTCONF (module options from the 8.7.1 page)

- ansible.netcommon.restconf_config:
    path: "/data/ietf-interfaces:interfaces/interface={{ lo.name }}"   # ⚠ path prefix: module page example uses /config/..., IOS XE guide uses /restconf/data/...
    method: put
    format: json
    content: "{{ {'ietf-interfaces:interface': [body]} | to_json }}"
  loop: "{{ loopbacks }}"
  loop_control: { loop_var: lo, label: "{{ lo.name }}" }

⚠ unverified: whether the httpapi plugin prepends /restconf so path starts at /data/.... The module example uses /config/... and the IOS XE guide uses /restconf/data/.... Test with one GET before looping.

5. Push with NETCONF (module options from the 8.7.1 page)

- ansible.netcommon.netconf_config:
    target: candidate
    default_operation: merge
    lock: always
    validate: true
    content: "{{ lookup('ansible.builtin.template', 'interfaces.xml.j2') }}"

The module commits by default (commit: true) when the candidate capability exists. With commit: false you own the commit or discard.

Micro-drill (about 10 min)

Target: Cat8000V. Requirement: from the SoT file above, create Loopback100 and Loopback101 with their descriptions and enabled state using RESTCONF. Then change Loopback101's description in the SoT only, rerun, and prove only that field changed on the device. Finish by reading both interfaces back and comparing to the SoT.

Reference: model ietf-interfaces; list interface, key name; leaves description, type, enabled. Loopback type identity iana-if-type:softwareLoopback ⚠ unverified on 17.16. IPv4 under ietf-ip:ipv4 ⚠ unverified.

Verify: show ip interface brief | include Loopback10; show running-config interface Loopback101; a restconf_get on the interface path and an assert on the description.

Hint

Use method: put so reruns converge. Build the body dict once in set_fact, serialize it with to_json in the task. Check the exact path with a single GET first.

Solution outline 
- hosts: cat8k
  gather_facts: false
  tasks:
    - ansible.netcommon.restconf_config:
        path: "/data/ietf-interfaces:interfaces/interface={{ lo.name }}"
        method: put
        content: >-
          {{ {'ietf-interfaces:interface': [{'name': lo.name, 'description': lo.description,
               'type': 'iana-if-type:softwareLoopback', 'enabled': lo.enabled}]} | to_json }}
      loop: "{{ loopbacks }}"
      loop_control: { loop_var: lo, label: "{{ lo.name }}" }
    - ansible.netcommon.restconf_get:
        path: "/data/ietf-interfaces:interfaces/interface={{ lo.name }}"
      loop: "{{ loopbacks }}"
      loop_control: { loop_var: lo, label: "{{ lo.name }}" }
      register: rb
    # assert on rb.results[*].response after confirming the response key name with a debug task  ⚠ unverified

If the path form fails, try the /restconf/data/... form noted in Anatomy 4. Skip IPv4 first, add it after the base push works.

Recall check

  1. Your payload passes pyang but the device returns 400. Name two mismatches between the URI and the body of a RESTCONF PUT on a list entry.
    Answer

    The list key value in the URI differs from the key leaf in the body, or the body's top node lacks the module: prefix (or is not wrapped as the single list entry). Also a mandatory leaf like type missing.

  2. Why does restconf_config with its defaults fail on the second run of a create, and what two settings make the run repeatable?
    Answer

    Default method is post, which creates and fails when the resource exists. Use put (replace) or patch (merge).

  3. On a device with candidate enabled, netconf_config returns ok but show run is unchanged. List two causes.
    Answer

    commit: false with no manual commit; or another session's lock and a failed earlier run left a stale candidate. Also check you did not target a different datastore. Verify with show netconf-yang datastores and get-config on running.

  4. Give the confirmed-commit default timer on IOS XE 17.5 and say whether RESTCONF supports it.
    Answer

    600 seconds; RESTCONF does not support confirmed commit.

  5. (from 2026-10-07) An XPath filter returns success and empty data. List the two most likely causes and how you tell them apart.
    Answer

    Path, key or namespace prefix does not match the model, versus the data genuinely has no matching entry. Fetch the parent node without a filter: if the entry is there, the filter is wrong; if not, the data is absent. Answer reconstructed from earlier pages.

  6. (from 2026-10-12) On ansible-core 2.19, when: interfaces with a list fails. What is the fix?
    Answer

    Conditionals must yield a boolean in 2.19. Use an explicit test such as interfaces | length > 0. Exact error text ⚠ unverified; reconstructed from earlier pages.
