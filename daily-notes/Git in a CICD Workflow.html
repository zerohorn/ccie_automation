Mental snapshot

  • Git is the trigger. A push, a merge request (MR), or a tag creates a pipeline, and the pipeline definition lives in the repo as .gitlab-ci.yml.
  • One branch push can create more than one kind of pipeline: a branch pipeline, an MR pipeline, or a merged results pipeline. Which one you get depends on the rules you wrote.
  • The most common defect in this area is two pipelines per push. The standard fix is workflow:rules with $CI_OPEN_MERGE_REQUESTS.
  • $CI_COMMIT_BRANCH is empty in MR pipelines. Jobs that read it silently misbehave when they move from a branch pipeline to an MR pipeline.
  • Merge and rebase produce the same final tree. They differ in history shape and in what they do to commits other people already have.
  • Protected branches decide who can push or merge, and they gate access to protected CI variables and runners.
  • The lab GitLab edition is unknown. Merged results pipelines need Premium or Ultimate, so do not build a solution that depends on them.

Where this fits

Fundamentals → exam depth

L1Concept

A Git repository is a graph of commits. A branch is a movable pointer to one commit. Merging joins two lines of work; rebasing replays one line onto another. All of that happens locally with no server involved, which is why the Pro Git chapter on branching workflows ✅ stresses that branches are cheap.

CI/CD adds a server that watches the remote. Every relevant event (push, MR update, tag) creates a pipeline: an ordered set of jobs the runner executes. The pipeline is defined in YAML in the same repo, so the workflow itself is versioned and reviewed like code. For you that means a change to a playbook, a Terraform module, or an NSO package goes through the same gate as any other change.

The standard flow that the blueprint verb "Use" implies is a topic branch per change, an MR into the default branch, a pipeline that must pass, then a merge that triggers the deploy pipeline. The Pro Git chapter calls the short-lived branch a topic branch and the stable one a long-running branch.

L2Mechanics

Pipeline types. GitLab has three that matter here. A branch pipeline runs on a push. An MR pipeline ✅ runs on the contents of the source branch only and ignores the target branch. A merged results pipeline ✅ tests a temporary commit that combines source and target, so it catches integration failures before the merge.

Why duplicates happen. If a job has no rules, or its rules match both push and merge_request_event, a push to a branch with an open MR creates two pipelines. The documented fix is a workflow:rules ✅ block evaluated before any job. workflow decides whether a pipeline exists at all, and rules inside a job decides whether that job exists in it.

Merge or rebase. Both integrate a branch. Merge does a three-way merge of two tips and the common ancestor and creates a merge commit when the branches diverged. Rebase replays your commits on the new base for a linear history, and a rebase followed by a merge gives a fast-forward. See Basic Branching and Merging ✅ and Rebasing ✅.

L3Exam detail

  • Variables differ by pipeline type. Per the predefined variables reference ✅, CI_COMMIT_BRANCH is unavailable in MR and tag pipelines, while CI_MERGE_REQUEST_IID, CI_MERGE_REQUEST_SOURCE_BRANCH_NAME and CI_MERGE_REQUEST_TARGET_BRANCH_NAME exist only in MR pipelines. CI_COMMIT_REF_NAME works in both. CI_DEFAULT_BRANCH lets you write deploy rules without hard-coding main.
  • Merge methods. GitLab offers three per project, documented under Merge methods ✅: merge commit (the default, like --no-ff), merge commit with semi-linear history (merges only if a fast-forward is possible, so a stale branch needs a rebase), and fast-forward merge (no merge commits, only when the target has not diverged). Squash is a separate setting with four modes: do not allow, allow, encourage, require.
  • Protected branches (docs ✅). "Allowed to merge" and "Allowed to push and merge" are separate settings. The default branch is protected by default. Users get protected variables and protected runners only when they can update both source and target of a merge between protected branches.
  • Conflict resolution flow. After a conflicted merge: git status, edit the marked files, git add, then git commit. In a rebase you resume with git rebase --continue, skip a patch with --skip, or bail out with --abort (git-rebase docs ✅).
  • Job ordering. Stages run in order by default. needs ✅ makes jobs start when their dependencies finish, forming a DAG. Keyword inventory is in the CI/CD YAML syntax reference ✅; only/except are deprecated, so use rules.
  • Merged results and conflicts. If the target has conflicting changes, merged results pipelines cannot run and GitLab falls back to a normal MR pipeline. A passing pipeline in that state does not prove the merge is clean.
Version drift. The GitLab docs pages I fetched are the current docs (they show 19.x version notes); your pin is GitLab 18.4. Features I saw that are newer than 18.4: custom inputs for MR pipelines (18.11) and automatic rebase before merge going GA (19.x). Do not rely on them in the lab. Features at or below 18.4: merged results (17.9+), CI_MERGE_REQUEST_DRAFT (17.10), protected variable access rules (18.1).
Push back. Blueprint 1.3 is one line, so it is easy to over-study Git trivia. In a lab where you work against a running GitLab, the likely task shapes (consistent with "Use" under [Build]) are: fix a pipeline that fires twice or not at all, resolve a conflict and get an MR merged, or wire a job to the right branch condition. Spend time on those, not on Git plumbing.

Anatomy

Pinned to the docs above. A working skeleton, not the drill solution: it shows the shape of workflow rules plus a job that only runs in MR pipelines.

# .gitlab-ci.yml (skeleton; keywords confirmed in the YAML reference)
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS
      when: never
    - if: $CI_COMMIT_BRANCH

stages: [check, apply]

check-job:
  stage: check            # job-level "stage" not fetched this run: verify
  script:
    - echo "source=$CI_MERGE_REQUEST_SOURCE_BRANCH_NAME target=$CI_MERGE_REQUEST_TARGET_BRANCH_NAME"
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

The three workflow:rules lines and the MR job rule follow the documented examples. Conflict markers, from Pro Git, look like this. The block between <<<<<<< and ======= is the current branch's version, and the block down to >>>>>>> is the incoming one.

<<<<<<< HEAD
vlan 110 name USERS
=======
vlan 110 name CORP-USERS
>>>>>>> feature/rename-vlan

Speed notes

  • The GitLab docs may not be reachable in the exam. Memorize the four names that matter: workflow:rules, rules:if, CI_PIPELINE_SOURCE, CI_OPEN_MERGE_REQUESTS.
  • Use the pipeline editor or CI lint tool in GitLab to catch YAML errors before pushing. The troubleshooting page names both.
  • Offline Git help: git rebase --help and git merge --help should open the man pages ⚠ unverified — test on the workstation.
  • Add a throwaway echo $CI_PIPELINE_SOURCE job when unsure which pipeline type fired. It is the fastest diagnostic.
  • Keep a snippet of the three-rule workflow block in your notes and type it from memory until it takes under 30 seconds.

Micro-drill (about 10 min)

Target: the GitLab instance in your lab (HORNLAB01 for your practice; exam instance unknown). A small repo with a text file vlans.txt is enough. No device needed.

Requirement:

  • Create .gitlab-ci.yml with two jobs: check-job runs only in MR pipelines; apply-job runs only on pushes to the default branch.
  • Pushing a commit to a feature branch that has an open MR must produce exactly one pipeline.
  • Create a conflict on vlans.txt between the feature branch and the default branch, resolve it by rebasing the feature branch, and merge the MR.

Reference names: workflow:rules, rules:if, $CI_PIPELINE_SOURCE, $CI_OPEN_MERGE_REQUESTS, $CI_COMMIT_BRANCH, $CI_DEFAULT_BRANCH.

Verify:

  • Pipeline list for the MR shows one pipeline per push, labeled merge request.
  • check-job log prints both branch names; apply-job does not exist in the MR pipeline.
  • After the merge, the default branch shows a pipeline containing only apply-job.
Hint

Job rules: $CI_PIPELINE_SOURCE == "merge_request_event" for the check; $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH for the apply. Workflow: the three-rule block from the Anatomy section. Rebase flow: fetch, rebase onto the default branch, resolve, git add, git rebase --continue, then push the branch.

Solution 
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS
      when: never
    - if: $CI_COMMIT_BRANCH

stages: [check, apply]

check-job:
  stage: check
  script:
    - echo "$CI_MERGE_REQUEST_SOURCE_BRANCH_NAME into $CI_MERGE_REQUEST_TARGET_BRANCH_NAME"
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

apply-job:
  stage: apply
  script:
    - echo "deploy from $CI_COMMIT_BRANCH"
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

Shell side: git checkout feature, git rebase main, edit vlans.txt at the markers, git add vlans.txt, git rebase --continue. Then push the branch. Because rebase rewrote the branch, the push may be rejected as non-fast-forward. A force push with lease is the usual answer ⚠ unverified — check the flag in git push --help in the lab. Only do this on a branch nobody else has pulled.

If the default branch is not called main, substitute your name for it in the rebase command.

Recall check

Today.

1. A push to a branch with an open MR creates two pipelines. Give the fix and say what each line does.

Add a workflow:rules block: run when source is merge_request_event; skip (when: never) when there is a branch and $CI_OPEN_MERGE_REQUESTS is set; otherwise run when $CI_COMMIT_BRANCH is set. The first match wins, so branches with an MR get only the MR pipeline.

2. Why does a job that prints $CI_COMMIT_BRANCH show an empty value after you add MR rules?

That variable is not available in MR pipelines. Use the MR source-branch variable or $CI_COMMIT_REF_NAME.

3. Which GitLab merge method requires a rebase when the source branch is behind, and what does it guarantee?

Merge commit with semi-linear history. It merges only when a fast-forward is possible, so the target branch build outcome matches what was tested.

4. A merged results pipeline is expected but a plain MR pipeline runs. Name two possible reasons.

The source branch conflicts with the target (GitLab falls back), or the feature is unavailable: it needs Premium or Ultimate, a Maintainer or Owner to enable it, and a project hosted on GitLab.

From history. The history file has only one entry, from yesterday (1 day old), so no 3–10 day old entries exist yet. These two are an early spaced review instead.

5. (2026-09-28) In a RESTCONF URI, where does the module-qualified name (e.g. Cisco-IOS-XE-native:) appear, and why is repeating it on nested containers wrong?

It prefixes the first (top-level) data node after the data root. Child nodes from the same module inherit the namespace, so repeating it is incorrect; the prefix reappears only where the module changes. Answer carried from the earlier page; not re-verified today.

6. (2026-09-28) Why does IOSvL2 accepting restconf into its configuration not mean RESTCONF actually works there?

In this lab context IOSvL2 has no working RESTCONF. The command is accepted but there is no service behind it. Use Cat8000V for RESTCONF and NETCONF.
