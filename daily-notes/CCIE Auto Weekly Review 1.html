2.4 RESTCONF/NETCONF payloads (Mon)

1. In a RESTCONF URI, where does the module-qualified name (e.g. Cisco-IOS-XE-native:) appear, and why is repeating it on nested containers wrong?

AnswerOnly on the first segment after /restconf/data/, and again on a child only if that child belongs to a different module/namespace (RFC 8040 naming rule). Same-module children are unqualified, so a repeated prefix is not the identifier the server expects and the request fails. The Cisco 17.5 page shows Cisco-IOS-XE-native:native/interface/GigabitEthernet=0%2F0%2F2: one prefix, list key after =, slash URL-encoded.

2. RESTCONF PATCH vs NETCONF edit-config against the candidate: when does the change take effect?

AnswerRESTCONF has no candidate step on IOS XE: the PATCH is applied to the running datastore as the call completes. NETCONF edit-config to candidate changes nothing live until a commit. The candidate datastore itself must be enabled on IOS XE (netconf-yang feature candidate-datastore, per the 17.5 NETCONF page).

3. A YANG list in RESTCONF JSON vs NETCONF XML: how does its shape differ?

AnswerJSON: one member named after the list whose value is an array of objects, each carrying the key leaf(s). XML: one repeated element per list entry, namespace declared via xmlns on the top element. JSON carries the module prefix on the member name; XML carries it as a namespace.

1.3 Git in CI/CD (Tue)

4. A push to a branch with an open MR creates two pipelines. What is the fix?

AnswerA workflow:rules block: run on $CI_PIPELINE_SOURCE == "merge_request_event"; skip (when: never) when $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS; otherwise run when $CI_COMMIT_BRANCH is set. Branch pipeline suppressed, MR pipeline kept. ⚠ exact rule text is from the workflow docs verified 2026-09-29, not re-fetched today.

5. After adding MR rules, a job printing $CI_COMMIT_BRANCH shows blank. Why?

AnswerMR pipelines don't set CI_COMMIT_BRANCH; they set the MR variables such as CI_MERGE_REQUEST_SOURCE_BRANCH_NAME. Check the predefined variables reference.

6. Which merge method forces a rebase when the source is behind, and what does it guarantee?

AnswerFast-forward merge: no merge commit, linear history, and the MR can only merge if it can fast-forward. (Semi-linear history also needs a fast-forwardable branch but still creates a merge commit.)

2.7.a-b Ansible loops and conditionals (Wed)

7. A looped task is registered as r. A later when: r.stdout is search('x') fails. Why?

AnswerWith a loop, the registered variable holds a results list (one entry per item, per the Loops page). r.stdout doesn't exist at the top level. Loop over r.results and test item.stdout, or filter with selectattr.

8. Import with when vs include with when: what changes?

AnswerImport: the condition is applied to every task in the imported file (static, evaluated per task, so a variable set by an early task can flip later tasks). Include: the condition gates only the include task itself. Both statements are on the Conditionals page.

9. Which three loop_control settings: hide all but a name, avoid collision in a nested include, stop on a condition?

Answerlabel, loop_var, break_when.

3.4 MDT dial-in (Thu)

10. Why does a NETCONF dial-in subscription disappear after a switchover, and where would you see it?

AnswerDynamic subscriptions are created by the subscriber over its session via RPC and aren't stored as configuration, so reload, switchover or session loss drops them. Visible with show telemetry ietf subscription while alive; never in running-config. The Cisco MDT chapter says dynamic subscriptions are created by the subscriber over the connection.

11. Default insecure and secure gNMI ports on the 17.5 guide, and the state command?

Answer50052 insecure, 9339 secure; show gnxi state; change with gnxi port / gnxi secure-port. ⚠ lab runs 17.16; confirm defaults there.

12. Periodic vs on-change in one line each?

AnswerPeriodic: update at each timer expiry regardless of change. On-change: update when the data changes (RFC 8641 covers both). On-change is supported only for some paths on IOS XE; a container holding many rows is a common failure. ⚠ per-platform support: check the model's on-change support in lab.

Integration drill (~20 min, 2.4 + 2.7 + 1.3 + 3.4)

Target: Cat8000V (IOS XE 17.16). RESTCONF and NETCONF enabled. Workstation: ansible.netcommon 8.4.0. No cisco.ios collection.

Requirement:

  • Given a variable list of three loopbacks (number, IP, mask), create them on Cat8000V using RESTCONF PATCH inside one Ansible loop.
  • Print only the loopback number per iteration (not the whole item).
  • Stop the loop on the first failure.
  • Read each loopback back with RESTCONF GET, and fail if the IP doesn't match.
  • Write a GitLab CI job that runs the playbook with --check only in merge request pipelines, with no duplicate branch pipeline.
  • Open a NETCONF dynamic subscription (on-change or periodic) to the interface path, change a loopback, and show the notification.

Reference field names/paths ⚠ unverified — confirm with ansible-doc ansible.netcommon.restconf_config and pyang -f tree

  • Modules: ansible.netcommon.restconf_config (path, content, method, format), ansible.netcommon.restconf_get (path, output).
  • Path pattern: /data/Cisco-IOS-XE-native:native/interface/Loopback=101 (list key after =, as the Cisco page shows for GigabitEthernet).
  • Connection vars: ansible_connection=ansible.netcommon.httpapi, ansible_network_os=ansible.netcommon.restconf, ansible_httpapi_use_ssl.
  • Loop: loop_control: {label, loop_var, break_when}.
HintRegister the PATCH result, then in the GET task loop over the same list and use assert with that comparing the returned address to item.ip. For the CI job, combine a workflow:rules block with $CI_PIPELINE_SOURCE == "merge_request_event". For the subscription, use any NETCONF client you have on the workstation ⚠ which client is installed is unverified and the establish-subscription RPC from RFC 8639.
Solution sketch 
# playbook (sketch, fields ⚠ verify with ansible-doc)
- hosts: c8kv
  gather_facts: false
  vars:
    lbs:
      - {num: 101, ip: 10.99.1.1, mask: 255.255.255.255}
      - {num: 102, ip: 10.99.1.2, mask: 255.255.255.255}
      - {num: 103, ip: 10.99.1.3, mask: 255.255.255.255}
  tasks:
    - name: Create loopbacks
      ansible.netcommon.restconf_config:
        path: "/data/Cisco-IOS-XE-native:native/interface"
        method: patch
        format: json
        content: |
          {"Cisco-IOS-XE-native:interface": {"Loopback": [{"name": {{ item.num }},
           "ip": {"address": {"primary": {"address": "{{ item.ip }}", "mask": "{{ item.mask }}"}}}}]}}
      loop: "{{ lbs }}"
      loop_control:
        label: "Loopback{{ item.num }}"
        break_when: r is failed
      register: r

    - name: Read back
      ansible.netcommon.restconf_get:
        path: "/data/Cisco-IOS-XE-native:native/interface/Loopback={{ item.num }}"
        output: json
      loop: "{{ lbs }}"
      loop_control: {label: "Loopback{{ item.num }}"}
      register: got

# .gitlab-ci.yml (sketch)
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS
      when: never
    - if: $CI_COMMIT_BRANCH

check:
  script: ansible-playbook site.yml --check

Known soft spots: whether break_when can reference the loop's own register mid-loop (⚠ test it), whether RESTCONF PATCH with a list under the parent container returns 204 or needs the child URI (⚠ test it), and whether --check is honored by restconf_config (⚠ test it).
