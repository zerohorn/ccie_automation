2.4 — Create a RESTCONF or NETCONF payload from a YANG module; interpret the response
2026-09-28 (Monday) · Estimated read: 18 min

Mental snapshot

  • YANG defines the schema (containers, leaves, lists). RESTCONF and NETCONF are two different wire protocols that carry data conforming to that same schema — the exam tests whether you can go from a YANG tree to a correct payload in either.
  • RESTCONF payload = JSON or XML shaped exactly like the YANG hierarchy, addressed by a URI path that mirrors the schema path (RFC 8040 §3.5.3).
  • NETCONF payload = XML wrapped in <rpc> operation envelopes (get-config, edit-config, …), always scoped to an explicit datastore — running or candidate (RFC 6241 §4).
  • On IOS XE, Cisco-IOS-XE-native is the "entire CLI as YANG" umbrella model. Most RESTCONF/NETCONF payloads you'll write against IOS XE traverse it.
  • Both protocols return errors as structured data, not free text: RESTCONF gives an HTTP status + a yang-data error body; NETCONF gives an <rpc-error> element. Interpreting a response is a parsing exercise, not a grep exercise.
  • Lab reality check: Cat8000V is the only device in the lab with a working NETCONF/RESTCONF agent. IOSvL2 accepts restconf into its running-config (shared classic-IOS parser) but every endpoint 404s — confirmed by direct test, not assumed from IOL-L2 behavior.
  • This unit is the foundation for 2.5 (XPath filters) and 2.6 (source-of-truth-driven config) — both assume you can already build and read a raw payload.

Where this fits

2.4 sits directly downstream of the YANG module and feeds both filtering (2.5) and source-of-truth automation (2.6). The same payload shape you build here is what a Python client (3.1) constructs programmatically instead of by hand.

Model-driven telemetry (3.4/3.5) is a different read path entirely — it streams data out via gNMI or dial-out subscriptions instead of you polling with a request/response call. Don't conflate the two: 2.4 is pull, on demand, request/response; 3.4/3.5 is push, continuous, subscription-based. Same underlying YANG schema, different transport family.

Fundamentals → exam depth

L1 — Concept

YANG (RFC 7950) is a modeling language, not a protocol. It defines containers (structural groupings, §7.5), leaves (single scalar values, §7.6), and lists (repeated, keyed entries, §7.8) — nothing more. A YANG module on its own moves no data anywhere. RESTCONF (RFC 8040) and NETCONF (RFC 6241) are the two protocols the exam expects you to speak against that schema: RESTCONF maps YANG onto HTTP methods and a JSON/XML body; NETCONF wraps YANG data inside XML RPC envelopes over an SSH subsystem. Same tree, two very different envelopes.

L2 — Mechanics

RESTCONF turns a YANG path into a URI. Cisco's RESTCONF chapter shows the pattern directly against Cisco-IOS-XE-native:

https://10.104.50.97/restconf/data/Cisco-IOS-XE-native:native/interface/GigabitEthernet=0%2F0%2F2

Module name only at the root (Cisco-IOS-XE-native:), then plain container/list names, then the list key after = — 0/0/2 is percent-encoded because / is the URI path separator.

NETCONF instead opens an SSH session on port 830 (configurable, per the Cisco guide), exchanges <hello> capabilities, then sends operations as <rpc> elements. The guide documents these operations: get, get-config, edit-config, copy-config, lock/unlock, commit, discard, kill-session, validate. Enabling it is one line:

Device(config)# netconf-yang
Device(config)# netconf-yang feature candidate-datastore

The candidate-datastore feature turns on the two-stage candidate → commit workflow. Without it you're editing running directly — no rollback buffer.

L3 — Exam detail

Building a payload "from a YANG module" means: open the tree (mentally, or with pyang -f tree — see Speed notes), find the container/leaf/list path to the node you need, then reproduce that nesting in JSON or XML. Three traps show up constantly:

Trap 1 — module-qualified name placement. The module prefix (Cisco-IOS-XE-native:) belongs only on the top-level resource in the RESTCONF URI/body. Repeating it on every nested container is a fabricated path that will 400.
Trap 2 — NETCONF needs the outer datastore target. An <edit-config> without a correctly-namespaced <target><running/></target> (or <candidate/> if that feature is enabled) is rejected before the schema is even checked.
Trap 3 — list keys. A YANG list becomes a JSON array of objects in RESTCONF, but stays a repeated sibling element in XML/NETCONF — don't try to XML-ify a JSON array shape or vice versa.

RESTCONF collapses "edit + apply" into a single HTTP call. NETCONF with the candidate datastore separates them — you can stage several edits, then commit (or discard) as one transaction.

Anatomy

Two real, source-verified snippets. Neither is the drill below — they're worked references for the shape, not the answer.

RESTCONF — from the Cisco 17.5 guide's own POST example (creating a logging-monitor leaf, adapted to show annotation):

curl -X "POST" "https://10.85.116.30:443/restconf/data/Cisco-IOS-XE-native:native/logging/monitor" \
  -H 'Content-Type: application/yang-data+json' \
  -u 'admin:admin' -d '{"severity": "alerts"}'

URI: .../native/logging/monitor — native is the RESTCONF resource root (module-qualified once), logging and monitor are plain containers/leaves below it, no repeated prefix. Body key severity matches the YANG leaf name exactly. -u admin:admin is the doc's own demo credential — never reuse literally; the lab workstation has its own accounts.

NETCONF — from the Cisco 17.5 guide's own edit-config example (hostname change, annotated):

<nc:edit-config>
  <nc:target><nc:running/></nc:target>
  <nc:config>
    <native xmlns="http://cisco.com/ns/yang/Cisco-IOS-XE-native">
      <hostname>new-ott-c9300-35</hostname>
    </native>
  </nc:config>
</nc:edit-config>

<target><running/> makes the datastore explicit (Trap 2, above). The xmlns on <native> is the module namespace — XML's equivalent of RESTCONF's Cisco-IOS-XE-native: prefix, declared once, inherited by children. Response for a clean apply is simply <rpc-reply><ok/></rpc-reply> — no body means no error.

Speed notes — finding this fast, offline

  • pyang -f tree <module>.yang — renders a YANG module as an indented tree so you can read container/leaf/list nesting directly instead of guessing it from memory. ⚠ unverified this run — confirm syntax and output format on the actual candidate workstation.
  • On-box capability check: the Cisco 17.5 guide documents restconf / ip http secure-server and netconf-yang as the enabling commands — if a payload is being rejected, confirm these are actually configured before debugging the payload itself.
  • Cisco's own vendor YANG modules live in github.com/YangModels/yang (source priority list) under a per-release vendor path — pull the exact Cisco-IOS-XE-native module for 17.5 rather than guessing leaf names from an older or newer release. (Not fetchable this run — GitHub blocked the directory listing via robots.txt; browse it directly in your own browser, not through this pipeline.)
  • curl -k -u <user>:<pass> https://<dev>/restconf/data/Cisco-IOS-XE-native:native?depth=1 — a shallow GET is the fastest way to confirm a top-level container name before you build a full payload against it. ⚠ unverified this run — the depth query parameter is a general RESTCONF (RFC 8040) mechanism; confirm IOS XE honors it before relying on it live.

Micro-drill (~10 min)

Requirement: On the Cat8000V, set the description of Loopback100 to ccie-auto-drill two ways: once via a RESTCONF PATCH, once via a NETCONF edit-config. Then read it back and confirm both agree.

Reference field names / paths

Target container family: Cisco-IOS-XE-native:native/interface/Loopback, list key name = 100, leaf description. (Confirm the exact list-key leaf name against the module tree on your workstation before assuming — don't hardcode from this page.)

Verification steps

1) GET the same resource back over RESTCONF and confirm description reads ccie-auto-drill. 2) Run show running-config interface Loopback100 over SSH and confirm the CLI shows the same description. 3) Repeat via a NETCONF get-config filtered to the same container.

Target lab device

Cat8000V only — this is the only device with a working RESTCONF/NETCONF agent in this lab build.

Hint

Build the RESTCONF PATCH body as nested JSON that mirrors native → interface → Loopback[] — the list entry needs its key (name) present in the body even though it's also in the URI. For NETCONF, wrap the same nesting inside <edit-config><target><running/></target><config><native xmlns="...">...</native></config></edit-config>.

Solution shape (not the literal answer)

RESTCONF: PATCH /restconf/data/Cisco-IOS-XE-native:native/interface/Loopback=100 with a JSON body whose root key is the list entry object containing name and description. NETCONF: an <rpc> containing <edit-config>, target running, config payload nesting native/interface/Loopback/name + description as sibling XML elements. Both should return a clean success (RESTCONF 204; NETCONF <ok/>) with no error body — if either returns an error element, that's Trap 1, 2, or 3 from the L3 section above, not a new problem.

Recall check

1. Today — In a RESTCONF URI, where does the module-qualified name (e.g. Cisco-IOS-XE-native:) appear, and why is repeating it on nested containers wrong?

Only on the top-level/root resource. Nested containers below it use plain names because the module namespace is already established by the root — repeating the prefix produces a path that doesn't exist in the schema, yielding a 400.

2. Today — What's the functional difference between issuing a RESTCONF PATCH versus a NETCONF edit-config against the candidate datastore, in terms of when the change takes effect?

RESTCONF PATCH applies immediately as part of the single HTTP call. NETCONF against candidate stages the change; it isn't live until a separate <commit> RPC is sent (and can be reverted with <discard> before that).

3. Today — Why does IOSvL2 accepting restconf into its configuration not mean RESTCONF actually works there?

IOSvL2 shares the classic-IOS CLI parser, which will accept the command syntactically, but there's no RESTCONF/YANG agent behind it on that platform — every endpoint returns 404 when actually tested. Config acceptance and functional support are two different things; verify by testing the API, not by checking whether the CLI took the command.

4. Today — A YANG list node appears in a RESTCONF JSON body and in a NETCONF XML body. How does its shape differ between the two encodings?

In JSON/RESTCONF it becomes an array of objects under the list's name. In XML/NETCONF it becomes repeated sibling elements, each a full instance of the list's structure — there's no array container in XML.
